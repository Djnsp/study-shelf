Foundations · 01

What is a relational database?

A relational database stores data as a set of tables. Each table holds one kind of thing — customers, orders, products — and tables are linked to each other through shared values called keys. The software that manages all this is an RDBMS (Relational Database Management System): PostgreSQL, MySQL, SQL Server, Oracle, SQLite.

SQL (Structured Query Language) is the language you use to talk to an RDBMS — to define tables, put data in, change it, and ask questions of it.

The anatomy of a table

A table is a grid. Columns define what you store and their type; rows are the actual records.

A table = columns (structure) + rows (data). Each row is one record.

Keys — how tables connect

  • Primary key (PK): a column whose value uniquely identifies each row. customer_id in customers. No duplicates, never NULL.
  • Foreign key (FK): a column that points to the primary key of another table. orders.customer_id references customers.customer_id — that's the "relation" in relational.
A foreign key creates a relationship. This is "one-to-many": each customer can have many orders.
Relationship types One-to-many (customer → orders), many-to-many (orders ↔ products, joined through an order_items table), and one-to-one (rarer; e.g. user → user_profile). Almost everything you'll model is one-to-many.

Why relational? Why not one giant spreadsheet?

Splitting data into related tables avoids repetition and contradiction. If a customer's city lived inside every one of their order rows, you'd repeat it dozens of times and risk it disagreeing with itself. Store each fact once, in the table it belongs to, and link by key. That principle — store facts once — is called normalisation, and we'll formalise it later.

The five families of SQL

SQL is one language, but its commands fall into five groups by what they do. Knowing which family a command belongs to tells you what it affects and whether it can be rolled back.

FamilyStands forCommandsPurpose
DDLData DefinitionCREATE ALTER DROP TRUNCATEDefine and change the structure — tables, columns, indexes.
DMLData ManipulationINSERT UPDATE DELETEChange the rows inside tables.
DQLData QuerySELECTRead data. This is where you'll spend 90% of your time.
DCLData ControlGRANT REVOKEPermissions — who can do what.

Mnemonic "Define, Manipulate, Query, Control, Transact." DQL (SELECT) is the star; the other four set the stage.

Adding & changing rows

DML moves data in and out of tables: INSERT to add, UPDATE to change, DELETE to remove. These change the database, so we'll demonstrate on a scratch table you can freely run.

INSERT — add rows

You can insert several rows in one statement (comma-separated value lists). Press Run above — the final SELECT shows what now lives in the table.

UPDATE — change existing rows

Always include a WHERE clause, or you'll update every row.

DELETE — remove rows

The most expensive mistake in SQL DELETE FROM customers; with no WHERE empties the entire table. Same for UPDATE. Before running either, select first: replace the verb with SELECT * and confirm you're touching exactly the rows you intend.

Querying · 06

Filtering rows with WHERE

WHERE keeps only the rows where a condition is true. Master its operators and you can isolate any subset of your data.

Comparison operators

Operators: =, <> (or !=), <, <=, >, >=.

Combine conditions: AND, OR, NOT

Precedence AND binds tighter than OR. A OR B AND C means A OR (B AND C). When in doubt, add parentheses — they cost nothing and prevent bugs.

IN — match any of a list

BETWEEN — an inclusive range

LIKE — pattern matching on text

% matches any number of characters; _ matches exactly one.

NULL — the absence of a value

NULL is not zero and not empty text — it's "unknown". You can't test it with =; use IS NULL / IS NOT NULL.

NULL gotcha Any comparison with NULL yields "unknown", which is not true — so price = NULL never matches anything. Always use IS NULL.

Ordering, deduping & limiting

ORDER BY — sort the result

Default is ascending (ASC). Add DESC for descending. Sort by several columns to break ties.

DISTINCT — unique values only

LIMIT — cap the number of rows

Combine with ORDER BY to get "top N" answers — the single most common reporting pattern.

You write SELECT first, but the engine runs FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. This explains why you can't use a SELECT alias in WHERE, but can in ORDER BY.

Querying · 09

Aggregation: GROUP BY & HAVING

Aggregate functions collapse many rows into one summary number. GROUP BY says "compute that summary once per group". This is how you turn raw rows into insight.

The five core aggregates

GROUP BY — one summary row per group

This counts products and averages their price within each category.

GROUP BY folds all rows that share a key into a single summary row.

HAVING — filter the groups

WHERE filters rows before grouping; HAVING filters groups after. Use HAVING when your condition involves an aggregate.

WHERE vs HAVING "Only USA customers, grouped by city, keeping cities with > 5" → WHERE country='USA' (row filter) … GROUP BY city … HAVING COUNT(*) > 5 (group filter). They work together, not interchangeably.
Relationships · 10 · the big one

JOINs: combining tables

A JOIN stitches rows from two tables together based on a matching condition — usually a foreign key meeting its primary key. This is what makes a relational database powerful: data lives in separate tables, and joins reassemble it on demand.

Every join answers the same shape of question: "for each row on the left, which rows on the right match — and what should happen to rows that don't match?" The five join types differ only in how they treat non-matching rows.

Left circle = left table, right circle = right table. Shaded = rows kept. CROSS pairs every row with every row.

INNER JOIN

Keeps only rows that match in both tables. The most common join. Rows with no match on either side are dropped.

Attach each product to its category. A product whose category_id matched no category would simply not appear.

Example 2 — three tables. Join order_items → orders → products to build a readable line-item report. Joins chain: each new JOIN attaches another table.

Example 3 — join + aggregate. Total revenue per category. Joins feed naturally into GROUP BY.

Shorthand JOIN with no prefix means INNER JOIN. Table aliases (products p) keep multi-table queries short and unambiguous.

LEFT JOIN

Keeps every row from the left table, plus matching data from the right. Where the right has no match, its columns come back NULL. Use it for "all X, and their Y if any".

Example 1. Count products per category — including categories with zero products. An INNER JOIN would hide empty categories; LEFT JOIN keeps them (count 0).

Example 2 — the anti-join. "Which customers have never ordered?" Keep all customers, then keep only rows where the order side is NULL.

Anti-join pattern LEFT JOIN … WHERE right_key IS NULL is the standard way to find "rows in A with no match in B" — unmatched customers, unsold products, orphaned records.

RIGHT JOIN

The mirror image of LEFT: keeps every row from the right table. In practice it's rare — most people just swap the table order and use LEFT, which reads more naturally. It's shown here for completeness.

This keeps all categories (right table) even if a category had no products — identical in spirit to a LEFT JOIN with the tables flipped.

FULL OUTER JOIN

Keeps every row from both tables, matching where possible and filling NULL on whichever side is missing. Use it to reconcile two sets and spot what exists only on one side.

CROSS JOIN

Pairs every row of the left with every row of the right — the Cartesian product. No ON condition. m rows × n rows = m·n rows, so it explodes fast. Useful for generating all combinations (e.g. every size × every colour).

Accidental cross join Forgetting the ON clause (or joining with no shared key) silently produces a Cartesian explosion. If a query returns way more rows than expected, a missing join condition is the usual culprit.

SELF JOIN

A table joined to itself, using two aliases. The classic case is a hierarchy stored in one table — each employee row carries its manager's id, which is itself an employee id.

Same table, two roles: e is the employee, m is their manager.

A LEFT self join keeps the top-level people (whose manager_id is NULL); an INNER self join would drop them.

Join checklist 1) What's my left table? 2) Do I want unmatched left rows kept? → LEFT, else INNER. 3) What's the ON condition (which columns match)? 4) Am I aggregating after? Answer those four and the join writes itself.
Relationships

Subqueries

A subquery is a query inside another query. The inner query runs first and hands its result up to the outer query — letting you filter or compute against a value you don't know in advance.

Scalar subquery — returns one value

When a subquery returns a single value, you can drop it anywhere a value is expected: in WHERE, in SELECT, or in a computed column. Here we compare each product against the average price — a number we compute on the fly.

How to read it The engine first runs SELECT AVG(price) FROM products → one number (say 512.40). The outer query then becomes WHERE price > 512.40. The inner query runs once.

A scalar subquery can also sit in the SELECT list to show a value alongside every row:

IN subquery — match against a list

When the subquery returns a column of values, use IN to keep outer rows whose value appears in that list. Here: every product belonging to a category named "Laptops" or "Phones", without hard-coding category ids.

Correlated subquery — runs per row

A correlated subquery references a column from the outer query, so it can't run just once — it re-runs for every outer row. Here, for each customer we count their orders. The inner query depends on c.customer_id, which changes row by row.

Performance A correlated subquery executes once per outer row, so on large tables it can be slow. A JOIN + GROUP BY often does the same job faster — but correlated subqueries read more clearly for "per-row lookups".

EXISTS — does a match exist?

EXISTS returns true the moment the subquery finds any matching row, then stops. It doesn't care about values, only existence. "Customers who have placed at least one order":

IN vs EXISTS Both can express "is there a match?". IN builds the full list first, then checks membership — great for small, fixed lists. EXISTS short-circuits on the first hit — usually better for correlated existence checks on big tables.
Relationships

Set operations

Set operators stack the results of two queries vertically (rows on top of rows), where joins combine them horizontally (columns beside columns). Both queries must return the same number of columns with compatible types.

Three ways to combine two result sets that share the same columns.

UNION — combine and remove duplicates

UNION stacks both result sets and removes duplicate rows. Here: every country that has a Business customer, combined with every country that has an Education customer — each country listed once.

UNION ALL — keep every row

UNION ALL skips the duplicate-removal step, so it's faster and keeps every row including repeats. Use it when you know there are no duplicates, or when you actually want the repeats (e.g. concatenating monthly tables).

INTERSECT & EXCEPT

INTERSECT returns rows present in both queries; EXCEPT (called MINUS in Oracle) returns rows in the first query but not the second.

Engine support varies UNION is universal. INTERSECT / EXCEPT are standard SQL but weren't supported in MySQL until 8.0.31, and some engines deduplicate them differently. The two queries above are shown un-run for that reason — the same results are reliably reproduced with a JOIN or NOT EXISTS when portability matters.
Column rules Every query in a set operation must expose the same number of columns, in the same order, with compatible types. Column names come from the first query. Put a single ORDER BY at the very end — it sorts the combined result.
Relationships

CTEs & views

As queries grow, nesting subqueries becomes hard to read. Common Table Expressions (CTEs) and views let you name a query and reuse it — turning one dense statement into clear, labelled building blocks.

WITH — common table expressions

A CTE defines a temporary, named result set with WITH name AS (…) that exists only for the duration of the query. You then select from it as if it were a table. Here we first build a per-customer revenue set, then join it back to customer names to get a clean top-spenders list.

Why it's clearer The same logic as a subquery in the FROM clause — but the heavy aggregation is named revenue and lifted to the top, so the final SELECT reads like plain English. You can chain several CTEs separated by commas, and later ones can reference earlier ones.

You can define multiple CTEs and build a small pipeline. Here: compute department averages, then list everyone earning above their own department's average.

Views — a saved query

A view is a CTE that lives permanently in the database. You create it once; afterwards anyone can SELECT from it like a table. The view stores the query, not the data — so it's always up to date when the underlying tables change.

CTE vs view A CTE is scoped to a single query — perfect for one-off readability. A view is reusable across many queries and users, and is the right tool when the same derived table is needed again and again. Neither stores its own copy of the data (unless it's a materialized view).

Window functions

A window function performs a calculation across a set of rows related to the current row — without collapsing them the way GROUP BY does. You keep every row and get the aggregate beside it. This is one of the most powerful features in modern SQL.

Anatomy of the OVER clause

RANK() OVER (
  PARTITION BY department  -- split rows into groups (optional)

Advanced

Design & internals

Writing queries is half the story. Knowing how the database stores, protects, and speeds up data is what turns a query-writer into a database expert. Three pillars: indexes, transactions, and normalization.

Indexes — the speed lever

An index is a sorted lookup structure (usually a B-tree) the database keeps alongside a table. Without one, finding rows means scanning every row (a "full table scan"). With one, the engine jumps straight to the matches — the difference between flipping through a whole book and using its index.

Index helps

WHERE filters, JOIN keys, ORDER BY columns, and UNIQUE / primary-key enforcement.

Index costs

Every INSERT/UPDATE/DELETE must also update the index, and indexes take disk space. Don't index everything.

Rule of thumb Index the columns you search by, not the columns you only display. A primary key is indexed automatically. Foreign-key columns are the next best candidates because they drive joins.

Transactions & ACID

A transaction groups several statements so they succeed or fail as one unit. The classic example is a bank transfer: debit one account, credit another. If the second step fails, the first must be undone — you can never lose the money in between.

Transactions guarantee four properties, abbreviated ACID:

PropertyGuarantee
AtomicityAll statements in the transaction happen, or none do. No half-finished states.
ConsistencyThe database moves from one valid state to another — all constraints stay satisfied.
IsolationConcurrent transactions don't see each other's partial work; the result is as if they ran one-by-one.
DurabilityOnce committed, the change survives crashes and power loss — it's written to durable storage.

Normalization — organizing without redundancy

Normalization is the process of structuring tables so each fact is stored once. Redundant data is the enemy: store a customer's city in every order row and the day they move, you have ten rows to fix and nine chances to get it wrong. The first three "normal forms" cover the vast majority of real designs.

The same data, split so each fact lives in exactly one row of one table.
Normal formRuleFixes
1NF — FirstEvery cell holds a single value; no repeating groups or lists in a column.The "P12, P12, L4" cell → separate order_items rows.
2NF — SecondAlready 1NF, and every non-key column depends on the whole primary key (matters for composite keys).A product's name doesn't belong in order_items — it depends on product_id alone, not the order.
3NF — ThirdAlready 2NF, and no non-key column depends on another non-key column (no "transitive" dependencies).A customer's city depends on the customer, not the order — move it to customers.
The trade-off Normalization removes redundancy and update anomalies, but heavy normalization means more joins. Analytics systems often denormalize on purpose — duplicating data to avoid joins and read faster. Transactional systems (orders, payments) stay normalized to keep writes safe. Know which world you're in.
