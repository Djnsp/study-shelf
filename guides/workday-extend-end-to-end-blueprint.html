1. APPLICATION CONCEPT

1.1 Business use case

A Global Contingent Worker (CW) Compliance Orchestrator. When an organization engages a contingent worker (contractor, SOW resource, agency temp), several jurisdiction-dependent compliance gates must clear before the worker is contracted and provisioned: criminal/background screening, sanctions & watchlist (OFAC/PEP) screening, right-to-work / identity verification, and document validity (visa, work permit, certifications). Today this is email-and-spreadsheet glue across HR ops, legal, the staffing vendor, and 2–4 external screening providers.

This app collapses that into a single Extend application that: - Ingests a worker context from Workday (Worker / Contingent Worker WDBOs). - Resolves which screenings are mandatory based on the worker's country (a config-driven jurisdiction rules engine). - Fans those screenings out in parallel to external providers via Orchestrate, with retry/backoff and failure routing. - Aggregates the multi-vendor results into a single composite compliance disposition (CLEARED / REVIEW / REJECTED). - Conditionally drives the downstream action: contract the worker (Workday SOAP Contract_Contingent_Worker), spawn a remediation task, or hard-stop. - Surfaces the whole lifecycle in a rich PMD UI with jurisdiction-aware sections, live document-expiry validation, and color-coded disposition badges.

Why this scenario: it forces genuine use of every requested capability. Parallelism and aggregation aren't bolted on — they're intrinsic to "screen against N providers and reconcile." Conditional PMD rendering is intrinsic to "US needs E-Verify, Germany needs a different set." That's the point: the architecture is driven by the domain, not by a feature checklist.

1.2 Personas & end-to-end workflow

Persona Touchpoint
HR Ops Coordinator Initiates a case from a worker, monitors progress, uploads/maintains documents
Compliance Officer Owns REVIEW dispositions, sees raw screening detail (PII-gated), approves/rejects
Hiring Manager Read-only summary of their worker's case status (no PII, no raw screening)
Compliance Admin Maintains the Jurisdiction Rules config
Integration System User (ISU) The headless identity the orchestration runs as

Flow: 1. HR Ops opens New Case, selects a worker → app pre-fills worker context from WDBOs and derives jurisdiction. 2. App shows the jurisdiction-specific required screenings + a document checklist. Coordinator uploads/attaches required docs; PMD validates expiry in-grid. 3. On submit, PMD guards completeness, persists the ComplianceCase (+ child ComplianceDocument rows), and triggers the Orchestrate flow. 4. Orchestrate fans out screenings in parallel, retries transient failures, aggregates, and writes ScreeningResult children back + sets the case disposition. 5. Routing: CLEARED → SOAP contract + notification; REVIEW → RemediationTask to a Compliance Officer; REJECTED → terminal status + notification. 6. Compliance Officer works the REVIEW queue in the Case Detail page (PII-gated panel), resolves, re-runs or finalizes.

2.2 Data Layer (CBOs + WDBOs)

Custom Business Objects

CBO Key fields Relationships
ComplianceCase caseStatus (CLEARED/REVIEW/REJECTED/IN_PROGRESS), overallScore, jurisdiction, initiatedOn, slaDueOn, assignedOfficer 1:1 ref → Worker (WDBO); 1:M → ScreeningResult; 1:M → ComplianceDocument; 0:M → RemediationTask

Modeling note: ComplianceCase → ScreeningResult/ComplianceDocument are true parent–child (cascade-scoped) relationships, so child instance security and lifecycle follow the parent. The Worker link is a single-instance reference field to the WDBO, not ownership.

Required Workday-Delivered Business Objects (WDBOs): Worker, Contingent Worker, Company, Cost Center, Supplier, Location, Country, Worker Document, plus the Contract Contingent Worker business process for the downstream SOAP write.

2.3 Security Layer

Custom Functional Area: Contingent Compliance (groups all domains so they can be administered/reported as a unit).

Security Domain Grants Mapped security group
Manage Compliance Case R/W on ComplianceCase, ComplianceDocument, RemediationTask Compliance Officer / HR Ops (role-based)
View Compliance Case (Limited) Read summary fields only of own-team cases Hiring Manager (constrained, manager-hierarchy)
View Screening PII / Raw Result Read rawResponseRef, raw ScreeningResult detail Compliance Lead only — separated domain so raw OFAC/background detail is gated independently of case access
Configure Jurisdiction Rules R/W on JurisdictionRule Compliance Admin
Integrate Compliance Orchestration API write to CBOs + SOAP Contract_Contingent_Worker ISSG for the ISU running Orchestrate

Design principles worth internalizing here: - PII isolation as its own domain. Raw screening payloads (criminal history, watchlist hits) are split into a dedicated domain so that "can see the case exists" and "can see the derogatory detail" are independently grantable. This is the single most important security move in the app. - Constrained vs unconstrained. Hiring Manager access is constrained to the supervisory org / manager hierarchy; Compliance roles are unconstrained within the functional area. - Headless context. The orchestration runs as an ISU whose ISSG holds Integrate Compliance Orchestration only — least privilege, no interactive login, no UI domains.

3. WORKDAY ORCHESTRATION SPECS & LOGICAL ALGORITHMS

3.1 Algorithmic breakdown

TEXT
INPUT: { caseId, workerId, jurisdiction }

1.  FETCH worker context
      1a. Workday REST  GET /workers/{workerId}           → identity, location, company
      1b. RAAS          GET <compliance_profile_report>    → enriched attributes
      JOIN 1a+1b into ctx

2.  RESOLVE rules
      lookup JurisdictionRule by ctx.country
      requiredScreenings := rule.requiredScreenings   (e.g. [BGC, SANCTIONS, RTW])
      slaDueOn          := today + rule.slaDays
      IF requiredScreenings is empty → set case = CLEARED, skip to step 7

3.  PARALLEL FAN-OUT  (fork per required screening; this is the join-loop pattern)
      branch BGC       : POST <backgroundProvider>     [try/retry x3, backoff]
      branch SANCTIONS : POST <sanctionsProvider>      [try/retry x3, backoff]
      branch RTW       : POST <rightToWorkProvider>    [try/retry x3, backoff]
      each branch:
        on success → emit ScreeningResult{type,status,score,raw}
        on terminal failure (retries exhausted) → emit ScreeningResult{type,status=ERROR}
                                                  AND flag branchFailed=true

4.  JOIN / AGGREGATE
      collect all branch outputs into results[]
      IF any branchFailed → disposition = REVIEW   (never auto-clear on a failed gate)
      ELSE compute:
           IF all results.status == PASS                 → CLEARED
           ELSE IF any results.status == FAIL/HIT         → REJECTED
           ELSE                                           → REVIEW
      overallScore := weighted aggregate(results)

5.  TRANSFORM
      shape results[] + disposition + overallScore into the CBO write payload
      (Transform step: PMD-transform or XSLT, depending on target shape)

6.  CONDITIONAL ROUTING (branch step)
      CLEARED  → 6a. SOAP  Contract_Contingent_Worker
                 6b. notify HR Ops (success)
      REVIEW   → 6c. create RemediationTask → assign Compliance Officer
                 6d. notify Compliance Officer
      REJECTED → 6e. set terminal status
                 6f. notify HR Ops (rejection)

7.  PERSIST
      Workday API write-back:
        update ComplianceCase{ status, overallScore, slaDueOn }
        create child ScreeningResult[] (batch loop over results[])
8.  END

Standard integration step notes: - Internal reads use Workday REST (/workers/...) for live attributes and RAAS for report-shaped enrichment — REST for the canonical object, RAAS where you want the report builder's joins/derived fields. - External calls are HTTP steps against named connections holding the provider credentials (OAuth2 client-credentials or API key in a secure connection, never inline). - Failure recovery: each external HTTP step is wrapped in try/catch with a bounded retry (e.g., 3 attempts, exponential backoff) for transient (5x/timeout) classes only; auth/4xx fail fast. Retries exhausted → the branch emits an ERROR result and the join forces REVIEW (a failed gate must never silently clear). - Batch loop vs join loop (the distinction you studied): Step 3 fan-out uses the join loop / parallel semantics — iterations execute concurrently and the flow blocks until all join. Step 7 write-back uses a batch loop — iterate the results[] sequentially (or in tenant-sized batches) to create child instances, where ordering/throttling matters more than concurrency.

4.1 PMD — Case Detail (dynamic rendering, validation, conditional formatting, multi-value)

JSONC
{
  "id": "complianceCaseDetail",
  "securityDomains": ["Manage Compliance Case"],

  // --- Endpoints: invoked on load; data referenced as <name>.data ---
  "endPoints": [
    {
      "name": "getCase",
      "baseUrlType": "workday-app",
      "url": "<% 'instances/complianceCase/' + queryParams.caseId %>",
      "httpMethod": "get"
    },
    {
      "name": "getWorker",
      "baseUrlType": "workday-common",
      "url": "<% 'workers/' + getCase.data.worker.id %>",
      "httpMethod": "get"
    },
    {
      "name": "getJurisdictionRule",
      "baseUrlType": "workday-app",
      "url": "<% 'instances/jurisdictionRule?country=' + getCase.data.jurisdiction %>",
      "httpMethod": "get"
    }
  ],

  // --- onLoad: derive page variables from joined endpoint data ---
  "onLoad": "<%
      var c = getCase.data;
      pageVariables.country           = c.jurisdiction;
      pageVariables.documents         = c.documents;
      pageVariables.requiredScreenings = getJurisdictionRule.data.data[0].requiredScreenings;

      // conditional formatting: compute a disposition descriptor once, reuse in UI
      var styleMap = {
        'CLEARED':  { 'label': 'Cleared',  'cls': 'wd-text-color-green'  },
        'REVIEW':   { 'label': 'In Review','cls': 'wd-text-color-amber'  },
        'REJECTED': { 'label': 'Rejected', 'cls': 'wd-text-color-red'    }
      };
      pageVariables.badge = styleMap[c.caseStatus];
  %>",

  "presentation": {
    "title": { "type": "title", "label": "<% 'Compliance Case · ' + getWorker.data.descriptor %>" },
    "body": {
      "type": "section",
      "children": [

        // ---- Disposition badge (conditional formatting via computed valueClass) ----
        {
          "type": "text",
          "id": "dispositionBadge",
          "label": "Disposition",
          "value":      "<% pageVariables.badge.label %>",
          "valueClass": "<% pageVariables.badge.cls %>"
        },

        // ---- US-only section: conditional VISIBILITY keyed on jurisdiction ----
        {
          "type": "fieldSet",
          "id": "usWorkAuthSection",
          "label": "U.S. Work Authorization (E-Verify)",
          "visible": "<% pageVariables.country == 'US' %>",
          "children": [
            {
              "type": "text",
              "label": "Required",
              "value": "<% list:contains(pageVariables.requiredScreenings, 'EVERIFY') ? 'Yes' : 'No' %>"
            }
          ]
        },

        // ---- Documents grid: per-row onChange validation + row-level formatting ----
        {
          "type": "grid",
          "id": "documentsGrid",
          "label": "Compliance Documents",
          "value": "<% pageVariables.documents %>",
          "columns": [
            { "type": "text", "label": "Type", "value": "<% item.docType %>" },
            {
              "type": "date",
              "id": "expiryDate",
              "label": "Expiry",
              "value": "<% item.expiryDate %>",
              "required": true,
              // v-model equivalent: write the edited value back into the row,
              // then derive a per-row validation flag.
              "onChange": "<%
                  item.expiryDate = self.value;
                  item.expiringSoon =
                    date:daysBetween(date:getTodaysDate(), self.value) < 30;
              %>",
              // conditional formatting at the cell level
              "valueClass": "<% item.expiringSoon ? 'wd-text-color-red' : '' %>"
            }
          ]
        },

        // ---- Submit guard: block trigger until every required screening is mapped ----
        {
          "type": "button",
          "id": "triggerCompliance",
          "label": "Run Compliance Check",
          "enabled": "<% !list:isEmpty(pageVariables.requiredScreenings)
                         && !list:isEmpty(pageVariables.documents) %>",
          "onClick": "<%
              if (list:isEmpty(pageVariables.documents)) {
                pageVariables.error = 'Upload required documents before running checks.';
              } else {
                // hands off to the orchestration (endpoint omitted for brevity)
                runOrchestration.invoke();
              }
          %>"
        }
      ]
    }
  }
}

What this snippet is teaching: endpoint chaining (getWorker URL depends on getCase.data), onLoad-derived page variables, conditional visibility (usWorkAuthSection), conditional formatting (computed valueClass at both field and cell level), multi-value / per-row onChange writing self.value back into the row object (the v-model analog), and an onClick/submit guard built from list:isEmpty / list:contains.

4.2 Orchestrate — orchestration definition (API call → transform → conditional routing)

Representative shape. The visual editor will own the real JSON; this shows the topology and step config you'd reproduce.

JSONC
{
  "name": "cwComplianceOrchestration",
  "input":  { "caseId": "string", "workerId": "string", "jurisdiction": "string" },
  "variables": { "ctx": {}, "results": [], "disposition": "" },

  "steps": [
    { "id": "start", "type": "start", "transitions": [{ "to": "fetchWorker" }] },

    // 1. Internal Workday REST read
    {
      "id": "fetchWorker",
      "type": "http",
      "config": {
        "connection": "workdayRestConnection",
        "method": "GET",
        "url": "/workers/${input.workerId}?expand=primaryWorkPosition,location"
      },
      "output": "ctx.worker",
      "transitions": [{ "to": "screenSanctions" }]
    },

    // 2. External call wrapped in try/catch with bounded retry
    {
      "id": "screenSanctions",
      "type": "http",
      "config": {
        "connection": "sanctionsProviderConnection",   // OAuth2 creds held by the connection
        "method": "POST",
        "url": "https://api.sanctions-provider.example/v2/screen",
        "headers": { "Content-Type": "application/json" },
        "body": {
          "fullName": "${ctx.worker.descriptor}",
          "country":  "${input.jurisdiction}"
        },
        "retry": { "maxAttempts": 3, "backoff": "exponential", "retryOn": ["5xx", "timeout"] }
      },
      "onError": { "to": "markScreeningError" },        // catch branch
      "output": "rawSanctions",
      "transitions": [{ "to": "transformResult" }]
    },

    // 3. Transform: shape raw provider payload into a normalized result + disposition
    {
      "id": "transformResult",
      "type": "transform",
      "config": {
        "language": "pmd-script",
        "script": "<%
            var hit = rawSanctions.body.matchCount > 0;
            variables.results = [{
              'screeningType': 'SANCTIONS',
              'vendor': 'sanctions-provider',
              'status': hit ? 'HIT' : 'PASS',
              'score':  rawSanctions.body.riskScore
            }];
            // never auto-clear on a hit; a hit routes to human REVIEW
            variables.disposition = hit ? 'REVIEW' : 'CLEARED';
            return variables;
        %>"
      },
      "transitions": [{ "to": "routeDisposition" }]
    },

    // 4. Conditional routing
    {
      "id": "routeDisposition",
      "type": "branch",
      "branches": [
        { "when": "${variables.disposition == 'CLEARED'}",  "to": "contractWorker" },
        { "when": "${variables.disposition == 'REVIEW'}",    "to": "createRemediation" },
        { "when": "${variables.disposition == 'REJECTED'}",  "to": "persist" }
      ],
      "default": { "to": "persist" }
    },

    // 5a. CLEARED → Workday SOAP contract
    {
      "id": "contractWorker",
      "type": "http",
      "config": {
        "connection": "workdaySoapConnection",
        "method": "POST",
        "url": "/ccx/service/Staffing/v44.0",
        "soapAction": "Contract_Contingent_Worker",
        "bodyTemplate": "contractContingentWorker.xml"   // SOAP envelope template
      },
      "transitions": [{ "to": "persist" }]
    },

    // 5b. REVIEW → create remediation task instance
    {
      "id": "createRemediation",
      "type": "http",
      "config": {
        "connection": "workdayRestConnection",
        "method": "POST",
        "url": "/extend/instances/remediationTask",
        "body": {
          "case": "${input.caseId}",
          "reason": "Sanctions match requires manual review",
          "status": "OPEN"
        }
      },
      "transitions": [{ "to": "persist" }]
    },

    // catch branch: a failed external gate forces REVIEW, never CLEARED
    {
      "id": "markScreeningError",
      "type": "transform",
      "config": {
        "language": "pmd-script",
        "script": "<% variables.disposition = 'REVIEW';
                      variables.results = [{ 'screeningType':'SANCTIONS','status':'ERROR' }];
                      return variables; %>"
      },
      "transitions": [{ "to": "createRemediation" }]
    },

    // 6. Persist case + children (batch loop in the full design)
    {
      "id": "persist",
      "type": "http",
      "config": {
        "connection": "workdayRestConnection",
        "method": "PATCH",
        "url": "/extend/instances/complianceCase/${input.caseId}",
        "body": {
          "caseStatus":  "${variables.disposition}",
          "overallScore": "${variables.results[0].score}"
        }
      },
      "transitions": [{ "to": "end" }]
    },

    { "id": "end", "type": "end" }
  ]
}

Compacted to a single screening branch for readability. The full Step-3 design replicates screenSanctions into a parallel/join-loop block over requiredScreenings[], and Step 7 wraps the child writes in a batch loop. The two patterns you studied — join loop (concurrent fan-out, blocks at join) vs batch loop (sequential/throttled iteration) — map exactly onto fan-out vs write-back here.

5. WHAT EACH PIECE IS DESIGNED TO TEACH

A quick map so the build doubles as a curriculum:

  • CBO modeling & relationships → the Case → Result/Document parent–child vs Case → Worker reference distinction (cascade scope, child security inheritance).
  • PMD dynamic rendering → onLoad hydration, conditional visible, computed valueClass, per-row onChange with self.value write-back.
  • Security depth → splitting case access from raw-PII access into separate domains; constrained vs unconstrained groups; least-privilege ISU/ISSG for the headless orchestration.
  • Orchestrate → internal REST + RAAS reads, external HTTP with connection-held credentials, try/catch + bounded retry, transform (PMD-script & XSLT), branch routing, and the join-loop vs batch-loop contrast.
  • The one rule that ties it together → a failed or uncertain gate routes to human REVIEW; the system never auto-clears on ambiguity. That single invariant is what makes the aggregation logic non-trivial and worth modeling carefully.

Build it in this order: CBOs → security → a static PMD against seeded data → the orchestration against one provider → parallelize → wire the PMD trigger last. Each layer is testable before the next exists.
