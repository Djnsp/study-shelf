00

Studio Fundamentals

Orientation before the patterns. Studio is an Eclipse-based IDE where you assemble integrations on a canvas as a left-to-right flow of components that pass a message between them.

The pieces you keep reaching for

ConceptWhat it is
AssemblyThe integration itself — a .clar project containing components wired together on the canvas.
ComponentA node from the palette (Splitter, Router, Eval, Write, SOAP Out, etc.). Custom components add to this palette.
Message streamThe payload flowing through the assembly. Read the current message text with parts[0].text.
Properties propsMutable state that lives for the whole integration run — counters, hash maps, logs. props['p.count'].
Variables varsScoped values, typically holding message fragments you build up. vars['v.batch_header'].text.
Launch params lpRuntime inputs/attributes configured in the tenant. lp.getReferenceData(...).
Integration system intsysTenant-side integration config — attributes, maps, RaaS services.

MVEL comes in two flavours

You will constantly choose between the two MVEL editor types — they are distinguished by their palette icons and by how they treat strings.

TypeStringsHow to embed logic
Expression CapableMust be quotedNo wrapper. props['p.msg'] = 'Hi ' # props['p.name']
Template CapableNot quotedWrap logic in @{ … }. My name is @{props['p.first.name']}!
Rule of thumb. Template-capable is what you use inside Write steps and component fields that build text/XML. Expression-capable is what you use in Eval steps and conditions.
01

Build a Studio Integration, Step by Step

A representative outbound pattern: take an inbound file, split it, build a repeatable web-service payload per record, wrap it with a header/footer, and submit it as a batch. This is the backbone of most Payroll-Input-style integrations.

The assembly shape

File In
CSV→XML
Splitter
Eval
Create Msg
Batch Out
  1. Write the header and footer into variables Use two Write steps — one builds the static opening of the SOAP request, the other the closing. Store each in a variable so the batch step can wrap every record.
  2. Split the inbound file After converting CSV to XML with a text schema, drop a Splitter so each record is processed individually. Inside a splitter you get util.isLastMessageInBatch() for free.
  3. Eval per record Increment counters, set log values, or compute derived fields. This is expression-capable MVEL territory.
  4. Create the repeatable message For Payroll Input the repeatable element is <wd:Payroll_Input_Data>. A Write step dumps the built XML into the message stream, which becomes the unit the batch tool aggregates.
  5. Submit as a batch Pass the message plus your header/footer variables into a batching component. It aggregates records, appends the header/footer, and submits to Workday when the batch fills (or on the last record).

Write step — header into a variable (template capable)

<env:Envelope xmlns:env="http://schemas.xmlsoap.org/soap/envelope/">
  <env:Body>
    <wd:Submit_Payroll_Input_Request xmlns:wd="urn:com.workday/bsvc" wd:version="v23.2">

Passing the variables into the batch tool's parameters

vars['v.batch_header'].text
vars['v.batch_footer'].text
Why batch? Batching offers significant performance gains over per-record SOAP calls. The catch: a single bad record fails the entire batch unless you handle the SOAP fault — which is exactly what the Batch with Fallback custom component in the next section automates.
02

Custom Components

Community-built Studio components that appear in your palette like any delivered component. They encapsulate complex logic so you only configure the high-level parameters.

Unsupported. Custom components are built by consultants, not by Workday. They are not supported by Workday Support or Product Development — you assume all responsibility when deploying them.

Installing a custom component

  1. Download the tool (it is just a Studio project) and save it somewhere memorable.
  2. Unzip to your Studio workspace.
  3. Import: File → Import → General → Existing Projects into Workspace, browse to the unzipped folder, Finish. The icon now appears under Workspace Components in your palette.
  4. Add it to your collection: Workday → Manage Collections, pick your project on the left, select the tool on the right, click the arrow. This guarantees the tool's code deploys with your project.

Reference component — Batch with Fallback

You pass it the repeatable portion of a SOAP message; it batches records and submits. If a batch fails, it inspects the SOAP fault, removes the offending messages, logs them, and resubmits the clean batch — automatically.

Required parameters
ParameterPurpose
Message Header requiredThe header that wraps the overall batch message.
Message Footer requiredThe footer that closes the overall batch message.
SOAP Application requiredPass-through to the SOAP Out application field, e.g. Payroll.
SOAP Version requiredPass-through to the SOAP Out version field, e.g. v23.2.
Optional parameters
ParameterDefaultPurpose
Batch Size opt150Records per submitted batch; 150 is a good starting point.
Custom Error Message optemptyExtra text logged with a failed record — e.g. the emplid — for troubleshooting. Set it per record so it stays dynamic.
Last Input optutil.isLastMessageInBatch()Tells the component when the final record arrives so it flushes the remaining batch. Override only when not in a normal splitter.
What it outputs
  • A context message on the Messages tab, e.g. "1000 out of 1012 submissions were successful. 7 batches were processed."
  • On failure, an Error-severity message, e.g. "12 Submission Errors Encountered!"
  • On failure, a CSV on the Output Documents tab named Submission_Errors.csv with columns: Error Number, Title, Location, Message, Custom Message.
Overriding Last Input. If two input types need two different calls (one batchable, one not), the last record might be the un-batched type and never trigger a flush. The fix: manually call the component with last_input = true and an empty message — the component ignores the empty message but flushes everything remaining.
Known limits. One instance at a time (no two different header/footer sets simultaneously); not suited for GET calls (response squelching makes it pointless); won't work with Import web services (generic response is incompatible).
03

Integration Events & Messages

How you surface progress and errors back to the tenant — and how to avoid the web-service cost of doing it naively.

Log files instead of integration messages

Each PutIntegrationMessage fires a web service call. On large files that adds up fast. Instead, accumulate errors and successes in a Java StringBuilder, then write a single log file at the end and attach it once.

Hard cap. Workday 24 introduced a limit of 500 integration event messages. The log-file approach is the recommended alternative for high-volume error capture.
  1. Create Java String Builders — one for the error log, one for the success log.
  2. At the "employee exists?" router, route failures to an async-mediation step whose eval appends a CSV line plus a line feed (a real line feed opens cleanly in Excel rather than one long line).
  3. After splitting finishes, write props['p.error.log'] out, optionally with a header row.
  4. Store to the Blobitory and attach the file to the event with a single PutIntegrationMessage.

Percentage / progress messages

Rather than a message per record, post one at chosen milestones (e.g. 25%, 50%, 75%) and update the progress bar on the event.

  1. Initialize properties in initialProps: a current count (0), the reportable percentages ([25,50,75]), a change flag (false), and the current percentage (0).
  2. Count all records up front with an xpath in countRecords.
  3. Per record in processRecord: increment the count, compute the current percentage, check it against the reportable list, and store the most recent reportable percentage.
  4. Call a sub-routine when the count hits a milestone; copy the current stream into a variable, post a PutIntegrationMessage summary, then a PutIntegrationEvent with is.percent.complete to move the progress bar, then restore the stream.

Report messages to a parent event

When a packaged integration launches your Studio integration inside its business process, you can attach output/messages to the parent event instead of the Studio event.

  1. Add a launch parameter (e.g. "Parent Process") referencing the Business Process multi-instance object.
  2. Get its WID: props['p.parent.process.wid'] = lp.getReferenceData("Parent Process","WID")
  3. On PutIntegrationMessage, add the delivered parameter is.event.wid and set it to that WID property.
  4. On the packaged integration's BP, configure the launch parameter as Determine Value at Runtime → Subject.
04

Integration Hash Maps

The single biggest performance lever for repetitive work — repeated web-service calls, full-file comparisons, change detection. Load the lookup set once, then get() in O(1) instead of calling the API per record.

Array to hash map

Convert a multi-value integration attribute into a map so you can cheaply test membership (a returned '1' means the key exists).

// 1) declare the map
props['p.myHashMap'] = new java.util.HashMap()

// 2) get the multi-value attribute as a list
props['p.myAttributeList'] = intsys.getAttributeReferenceDataList('AttributeName', 'RefIDType')

// 3) size it, 4) load each value keyed to '1'
props['p.myAttributesList.count'] = props['p.myAttributeList'].size()
foreach(x : props['p.myAttributesList.count']){
    props['p.myHashMap'].put(props['p.myAttributeList'].get(x-1), '1')
}

Custom report (RaaS) hash map

Split a RaaS response into wd:Report_Entry nodes and key each one by, say, Employee ID. The .put() takes (lookupValue, valueToPut) — store the whole XML node as the value so you can xpath into it later.

<wd:Report_Entry xmlns:wd="urn:com.workday/bsvc">
  <wd:Employee_ID>123456</wd:Employee_ID>
  <wd:Custom_ID>C123</wd:Custom_ID>
</wd:Report_Entry>
Namespace gotcha. Make sure your wd: namespace matches the report's. Studio defaults to urn:com.workday/bsvc; for custom reports it is more efficient to set the report's namespace on the Advanced tab so they match.

Web-service hash map

When you need the whole tenant set (e.g. all organizations to decide create-vs-update), pull it via a Paged Get and load each entry into a map keyed by its ID.

<wd:Get_Organizations_Request xmlns:wd="urn:com.workday/bsvc" wd:version="v19">
  <wd:Response_Filter><wd:Count>999</wd:Count></wd:Response_Filter>
</wd:Get_Organizations_Request>

Point is.paged.get.process.endpoint at a sub-routine, split the paged response, and add parts[0].text to the map keyed by Organization ID.

Cleaning up leftover data

Some integrations must process whatever is left in the map after the main run (e.g. records present in the tenant but absent from the file). Retrieve the keySet(), turn it into XML, split it, and process each remaining key.

<root>
  @foreach{props['p.remaining.keys'] as id}
    <ee>@{id}</ee>
  @end{}
</root>
05

Document Field Overrides

Return data not available through the standard web-service operation — e.g. the Manager Name via Get_Workers — by wiring a Field Override Service into the request.

  1. In the tenant, create the service with Create Integration Field Override Service, choosing the right business object (here, Worker).
  2. In the assembly, add a service-reference to your workday-in component with the same name as the Field Override Service.
  3. Deploy, then configure the overrides via the UI as you would any packaged integration.
  4. In the request, pass the integration system WID through Field_And_Parameter_Criteria_Data.
<wd:Request_Criteria>
  <wd:Field_And_Parameter_Criteria_Data>
    <wd:Provider_Reference>
      <wd:ID wd:type="WID">@{lp.integrationSystemRefWID}</wd:ID>
    </wd:Provider_Reference>
  </wd:Field_And_Parameter_Criteria_Data>
</wd:Request_Criteria>

The response carries the override under wd:Integration_Field_Override_Data with the field descriptor and its wd:Value.

MVEL Expression Reference

The everyday language of Studio Eval, Write and condition steps. New to it? Start with the basics below, then use the recipes as a copy-paste cookbook. Workday uses MVEL 1.3, and custom Java should be a last resort — only when no palette component does the job.

New to MVEL? Start here

MVEL is a tiny scripting language you type into Studio to grab a value, reshape it, store it, or decide which path the integration takes. You're not writing whole programs — just short expressions that act as the glue between components.

Where you actually type it
PlaceWhat you write there
Eval stepSet or calculate values, e.g. bump a counter or build a name. Expression-capable.
Router / conditionA true/false test that decides which branch a record takes.
Write stepBuild text or XML, dropping values in with @{ }. Template-capable.
Where your data lives — the buckets

Almost every line reads from or writes to one of these. Learn the buckets and the rest falls into place.

BucketThink of it as…Example
props[…]A sticky notepad that lasts the whole run — counters, hash maps, logs.props['p.count']
vars[…]Scratch values, usually pieces of the message you're assembling. Read its text with .text.vars['v.header'].text
parts[0]The message flowing through right now.parts[0].text · parts[0].xpath('wd:ID')
lpInputs set up in the tenant (launch parameters / attributes).lp.getReferenceData('Company','WID')
intsysTenant integration config — value maps, RaaS report services.intsys.integrationMapLookup(…)
utilBuilt-in Studio helpers.util.isLastMessageInBatch()
The rules you can't skip
  1. Store a value with = props['p.name'] = 'Bob' puts the text "Bob" into the notepad slot called p.name.
  2. Quote text, not values Wrap text in single or double quotes. Numbers and buckets get no quotes. 'Bob' is text; props['p.age'] is a value; 21 is a number.
  3. The last line is the answer In a condition or Eval field, whatever the final line works out to is what the step hands back — you rarely need the word return.
  4. One thing per line, or separate with ; a = 1; b = 2; a # b runs three statements in a row.
  5. Leave notes with comments // comments to the end of the line; /* … */ comments a block.

A complete little Eval, reading top to bottom

// build a full name from two props
props['p.full'] = props['p.first'] #' '# props['p.last']   // 'Ada Lovelace'

// is this person a manager? (a true/false value)
props['p.isMgr'] = props['p.reports'] > 0

props['p.isMgr']   // <- last line = what a condition step would return
Operators at a glance
GroupOperatorsReads as
Maths+ - * /add, subtract, multiply, divide (for joining text use # — see gotchas)
Compare== != < > <= >=equal, not equal, less / greater than…
Logic&& || !and, or, not
Pick onetest ? a : bif test is true use a, otherwise b
Three things that trip up beginners
+ adds, # joins. 1 + 1 is 2, but 1 # 1 is '11'. When you mean "stick these strings together," always reach for #.
== compares the real value. Unlike plain Java, props['p.x'] == '124' just works for text — no .equals() needed.
Checking for "nothing". Use the empty keyword for null-or-blank tests: props['p.list'] != empty ? 'has items' : 'is empty'.
Common recipes

The basics applied to real Studio tasks. Copy, paste, adapt.

Concatenation — prefer # over +

Both join strings, but + on numeric values adds them. Use # to always concatenate.

props['p.employeeFirstName'] = 'Bob'
props['p.employeeLastname']  = 'Rumpelstiltskin'
props['p.employeeFullName']  = props['p.employeeFirstName'] #' '# props['p.employeeLastname']
// -> 'Bob Rumpelstiltskin'   (1 # 1 -> '11', but 1 + 1 -> 2)

If statements — two forms

Expression capable uses the ternary: ? is "then", : is "else".

props['p.result'] = props['p.valueToCheck'] == '124' ? 'Value is Equal' : 'Value is NOT Equal'

Template capable uses block tags:

<root>
  @if{props['p.is.boolean']}            <ee>Do something</ee>
  @elseif{props['p.numeric.value'] == 1} <ee>Do something else</ee>
  @else{}                            <ee>Else</ee>
  @end{}
</root>

Foreach (template capable)

<root>
  @foreach{props['p.is.list'] as id}
    <ee>@{id}</ee>
  @end{}
</root>

Dates

Reformat with SimpleDateFormat — parse to a Date, then format.

props['p.parsed'] = new java.text.SimpleDateFormat("yyyy-MM-dd").parse('2013-10-03')
props['p.out']    = new java.text.SimpleDateFormat("MM/dd/yyyy").format(props['p.parsed'])
// -> 10/03/2013

Convert a dateTime to Zulu / GMT:

props['p.parse'] = new java.text.SimpleDateFormat("yyyy-MM-dd'T'HH:mm:ss.SSSXXX").parse(props['launch.parm.datetime'])
org.apache.commons.lang.time.DateFormatUtils.formatUTC(props['p.parse'], "yyyy-MM-dd'T'HH:mm:ss.SSSZZZ")
// -8:00 input  ->  ...+00:00 output

Numbers & padding

props['p.num'] = new java.text.DecimalFormat("##0.00").format(
              new java.text.DecimalFormat("##0.00").parse(props['p.salary']))

org.apache.commons.lang.StringUtils.leftPad('1234', 10, '0')   // 0000001234
org.apache.commons.lang.StringUtils.rightPad('1234', 10, '0')  // 1234000000

JSON

props['oauth.token'] = new org.json.JSONObject(parts[0].text).getString("access_token")

// JSON -> XML
props['json.msg']   = new org.json.JSONObject(parts[0].text)
vars['xml.variable'] = org.json.XML.toString(props['json.msg'])
Array input. If the JSON top level is an array, wrap it in curly braces with a key before loading; a single object needs no wrapping. The Write step treats { } as formatting, so stash them in properties and emit via @{}.

Integration maps

intsys.integrationMapLookup('Status', props['position.status'])
intsys.integrationMapReverseLookup('map_name', 'key').get(0).getReferenceData('REF_ID_TYPE')

07

XSLT Functions

Transformation patterns for outbound files. Recursive XSLT templates are discouraged — reach for the right padding strategy by integration type first.

Padding — pick by integration type

  • Document Transformation: use XTT or ETV fixed-length functions.
  • Studio integration: use a text-schema control to pad, or add Java's StringUtils via a namespace.
  • Stuck with XSLT (e.g. EIB): use a non-recursive pad function — it shortens a long padding string instead of recursing.
xmlns:nf="java:org.apache.commons.lang.StringUtils"
<xsl:value-of select="nf:leftPad('nick',2,'x')"/>

Change detection (connector XML)

Detect whether a node changed by testing for the connector's @pi:PriorValue marker:

<xsl:if test="descendant-or-self::pi:Pay_Data/*[@pi:PriorValue]"/>

Date arithmetic

<!-- add 1 day; needs xmlns:xs schema namespace -->
<xsl:value-of select="($date) + 1 * xs:dayTimeDuration('P1D')"/>

Max / min dates without sequence errors

Atomize to xs:date inside min() / max() to avoid "a sequence of more than one is not allowed":

<xsl:variable name="startDate"
  select="min(PaymentDates/wd:Company_Payment_Dates_Data/wd:Payment_Date/xs:date(.))"/>

Normalize namespaces

Force aggregated inputs (e.g. two reports with different namespaces) to the standard urn:com.workday/bsvc using identity-style element/attribute templates that re-create each node under one prefix.

Cheaper alternative. For custom reports, edit the report namespace on the Advanced tab so they already match — no transform needed.

Accent translation

Vendors like ADP can't always take the full UTF-8 range Workday allows. Map a handful of accents with translate(), or strip combining marks:

<xsl:value-of select="translate($s,'äöüáéíóú','aouaeiou')"/>
replace(normalize-unicode($word, 'NFKD'), '[\P{L}]', '')

XML to CSV

<xsl:variable name="sep" select="','"/>
<xsl:variable name="crlf" select="'&#10;'"/>
<!-- loop nodes, comma-separate children, emit a line feed per row -->

Also in the library: EBCDIC ↔ decimal conversions, integration map "ApplyMap" functions (text→object and text→text), and a working-days date-difference function that counts weekdays between two dates (no holidays).

Third-Party SSL CA Certificates

Add a Java keystore / truststore to your assembly so HTTPS-Out can reach an otherwise-untrusted endpoint.

  1. Export a .CER for every layer of the certificate chain from your browser (Base-64 X.509 / PEM) — bottom layer is the endpoint, top layer is the signing authority.
  2. Create an empty keystore.jks with keytool -genkey -alias Workday -keyalg RSA -keystore keystore.jks; press Enter through the prompts and confirm yes.
  3. Import the endpoint .CER into the keystore with keytool -import.
  4. Create a truststore.jks the same way and import a .CER for each chain layer (-alias labels the layer for later -list).
  5. Add both .JKS files to the WSAR-INF folder in Studio.
  6. On the HTTP-Out element, add https-properties: point Keystore File and Truststore File at the files and enter the passwords.
# PKCS12 (.p12 / .pfx) -> keystore.jks
keytool -importkeystore -srckeystore certificate.p12 \
        -destkeystore keystore.jks -srcstoretype pkcs12
Truststore vs keystore. If you only need to trust the endpoint, a truststore alone may suffice — you don't necessarily need a keystore. A truststore may still be required alongside a keystore when presenting client credentials.
