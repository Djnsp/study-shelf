1. Staffing Setup 25% of the exam

1.1 The job catalog

The job catalog is the library of jobs your company uses. It has three layers:

LayerWhat it isExample
Job family groupThe broadest grouping; contains job familiesInformation Technology
Job familyA set of related job profilesSoftware Engineering
Job profileThe actual job definition used to create positions/jobs and staff workersSenior Software Engineer
  • Job families and family groups exist mainly to organize and report on the catalog (for example, headcount by family).
  • A job profile can belong to more than one job family.
  • You create families and assign profiles to them with the job family maintenance tasks (for example, Create Job Family, Maintain Job Family).

1.2 Anatomy of a job profile

A job profile is a reusable template of job attributes. Fields you should know:

FieldWhy it matters
Job family / familiesPlaces the profile in the catalog for reporting and restrictions
Management levelConsistent seniority hierarchy (for example, Executive, Manager, Individual Contributor) used in reporting and configuration
Job levelGrading/leveling of jobs (for example, P1–P5)
Job classificationsCategories, often regulatory (for example, EEO), grouped in job classification groups
Exempt / non-exemptOvertime eligibility treatment per country
Pay rate typeDefaults salaried vs. hourly
Compensation gradeDefaults pay guidelines during staffing events
Critical jobFlags key jobs for reporting and planning
InactiveRemoves the profile from new staffing; history is preserved
Exam angle: expect questions on which fields are used to create and edit job profiles and what each defaults during staffing.

1.3 Staffing models — the big picture

  • The staffing model is chosen per supervisory organization, so different orgs in one tenant can use different models (a "hybrid" landscape).
  • Position Management is the default model for new supervisory organizations.
  • Organizations can be switched between models; existing filled staffing converts to the new model.

1.4 Position Management

  • Every hire requires an approved, individually created position (Create Position).
  • Each position carries its own position restrictions — job family/profile, worker type, location, availability date, earliest hire date — describing the "seat" itself.
  • Unfilled positions are real objects: you get vacancy tracking, time-to-fill by seat, and seat-level budgeting.
  • On termination the position by default becomes an unfilled position you can refill; you can instead close it (ends availability) or freeze it (temporary block, reversible).
  • Job overlap lets a replacement occupy the position while the incumbent is still active (knowledge-transfer scenarios).
  • Edit Position Restrictions changes the seat's rules for future incumbents; Edit Position is a staffing event that changes a filled position's details (business title, scheduled hours, and so on).

1.5 Job Management

  • No pre-created positions — you hire directly, and the job is created at hire time.
  • One set of hiring restrictions per supervisory organization (task: Edit Hiring Restrictions) constrains all hires there.
  • No unfilled position objects: no vacancy tracking, and nothing is "left behind" at termination.
  • Maximum hiring flexibility and speed, but headcount control depends on process, not per-seat approvals.

1.6 Restrictions in both models

 Position ManagementJob Management
Where definedPer position (position restrictions)Once per org (hiring restrictions)
Typical contentsJob family/profile, worker type (employee/contingent and their types), location, time-based dates
Availability dateWhen the position/restrictions become usable
Earliest hire dateFirst day a worker may actually start
Evaluated whenDuring staffing events (hire, change job) — they constrain and validate choices

1.7 Choosing (and changing) a model

NeedPick
Tight per-seat control, approvals, vacancy/time-to-fill reporting, seat budgetingPosition Management
Fast, flexible, high-volume hiring against a shared rule set (retail, seasonal)Job Management
Different needs in different parts of the companyDifferent models on different sup orgs

1.8 Commonly used staffing business processes

  • Preparing an org for staffing: Position Management → Create Position; Job Management → Edit Hiring Restrictions.
  • Hire: turns a pre-hire into a worker with an effective date. Key subprocesses: Propose Compensation Hire (starting pay), Assign Pay Group (payroll population), Assign Roles (organization role assignments), Onboarding (new-hire tasks).
  • Change Job: promotions, demotions, lateral moves, transfers between orgs, location and hours changes. During transfers, Assign Roles keeps role-based access aligned with the new situation; Propose Compensation Change and Assign Pay Group commonly ride along.
  • Termination: captures termination date, last day of work, pay-through date, reason, and eligibility for rehire; decides position disposition (open vs. close) in Position Management; Manage Business Processes for Worker reviews the worker's in-flight events so they can be reassigned or canceled.
  • Add Additional Job / End Additional Job: a worker holds, then ends, a secondary job without touching the primary one.
  • Contract Contingent Worker: the staffing event for external/contingent labor (worker type distinguishes employees on payroll from contingent workers).
Exam angle: know the purpose of Hire, Change Job, and Termination, and which subprocess does what — especially Assign Roles vs. Assign Pay Group vs. Propose Compensation.

2. Organizations 20% of the exam

2.1 Supervisory organizations — the foundation

  • Supervisory organizations group workers into a management hierarchy. They are the only place staffing happens — every worker is staffed into one through their position or job.
  • Business process definitions, routing, and role-based security all operate through the supervisory hierarchy.

2.2 Key supervisory organization attributes

AttributeNotes
Availability dateEarliest date the org can be used in transactions
Superior organizationExactly one, except the top-level org (which has none)
SubtypeLabel such as Department or Division; a subtype must be configured as allowable for the organization type to be selectable
Staffing modelPosition or Job Management, set per org
VisibilityHow broadly the org appears (for example, in search)
ManagerEstablished via the Manager role assignment, normally held by a position

Inheritance: subordinate organizations inherit configuration from superiors unless overridden — notably business process definitions and unfilled role assignments (if an org has no HR Partner of its own, Workday resolves the role by walking up the hierarchy).

2.3 Building and maintaining the hierarchy

TaskUse it to…
Create Supervisory OrganizationCreate a top-level org (rare)
Create SubordinateCreate an org beneath a superior, inheriting key settings — the everyday way to grow the hierarchy
Divide Supervisory OrganizationSplit a large org, moving selected workers into subordinate orgs
Assign SuperiorRe-parent an org under a different superior
Move WorkersMass-move workers between supervisory organizations
Inactivate OrganizationRetire an org — allowed only when it has no remaining workers/staffing; history is preserved (orgs with history are inactivated, not deleted)

Reorganization events bundle multiple org changes to take effect together on a planned date, keeping history clean.

2.4 Other organization types

TypePurpose
CompanyLegal entity; statutory, financial, and payroll significance
Cost centerFinancial responsibility for worker costs
RegionGeographic grouping for reporting/routing
Pay groupPopulation processed together in payroll; connected via Assign Pay Group
Custom organizationsCustomer-defined types when delivered ones don't fit; a custom type can be configured to allow multiple simultaneous memberships
Matrix organizationSecondary "dotted-line" reporting; the matrix manager gets team visibility, while staffing stays with the supervisory manager
Retiree organizationKeeps a relationship with retirees after employment ends
Watch out: locations are not organizations — they are separate instances representing physical places assigned to workers and positions.

2.5 Organization hierarchies

  • Types like company, cost center, region, and custom orgs can be arranged into hierarchies for rollup reporting (for example, a cost center hierarchy for consolidated views).
  • Workers/costs belong to the organizations, not to hierarchy nodes — hierarchies only aggregate.

2.6 Organization assignments (defaults and allowed values)

  • Supervisory organizations carry default organization assignments (commonly company, cost center, region) that prefill during staffing events, configured by maintaining organization assignments on the sup org.
  • Allowed values restrict which choices can be selected; defaults speed entry, allowed values constrain it.
  • Change Organization Assignments updates a worker's assignments (for example, a cost center move) without a job change.

2.7 Assignable roles

  • Roles (HR Partner, Compensation Partner, Manager…) connect responsibilities to positions in an organization context. Task: Assign Roles.
  • Because assignments attach to the position, a successor automatically takes on the same responsibilities.
  • Single assignment roles allow one holder per org; others allow multiple.
  • Roles drive business process routing (steps route to the role's holder on the relevant org, inheriting from superiors if unfilled) and role-based security group membership.

3. Business Processes 25% of the exam

3.1 Terminology and framework

TermMeaning
Business process definitionThe configured template: steps, order, groups, rules
Business process eventA live transaction created when someone initiates the process
Initiating actionThe task/action a user performs that creates the event
Order valuesAlphanumeric values (a, b, ba, c…) controlling step sequence; equal values run in parallel, and values like "ba" slot between "b" and "c"
Completion stepThe event is considered complete at this step even if later steps still run

3.2 Step types

StepWhat it does
InitiationAlways first (order "a"); represents the initiating action
ActionUser performs a Workday task that can add/change event data
ApprovalApprove / deny / send back — no editing of submitted data
Approval chainEscalates through a chain (for example, the management hierarchy) until its rule is satisfied
Consolidated approvalOne screen combining several approvals — decision-only, does not permit editing
To DoManual task outside the transaction; user marks complete to let the process continue
ChecklistA bundle of related To Dos
ServiceAutomated Workday service performed without user data entry
SubprocessA full business process embedded in a parent (for example, Propose Compensation inside Hire) with its own definition and its own security policy
QuestionnaireCollects structured responses inside the flow

3.3 Definitions: default vs. custom

  • The default definition applies tenant-wide. An organization can carry a custom definition that overrides it for that org and its subordinates.
  • Resolution when an event starts: use the org's own definition → else walk up the hierarchy → else the default.
  • Two ways to create an org-specific definition: copy (editable variant) or link (reuse another definition without duplicating).
  • Editing a definition affects new events only; in-flight events finish on the definition they started with.
  • Reference report: Business Process Configuration Options summarizes configurable options per process type.

3.4 Condition rules and validations

  • Condition rules are built from condition items: source field + relational operator + comparison value, combined with And/Or.
  • An entry condition on a step ("run this step only if…") that evaluates false causes the step to be skipped.
  • Validations attached to the initiation step evaluate first, stopping (critical error) or warning (alert) on bad data before anyone downstream spends time on it.
  • Conditions decide whether a step runs; routing decides who performs it — a favorite exam distinction.

3.5 Routing, due dates, delays, help text

  • Steps route to groups/roles; role holders resolve from the relevant organization, inheriting from superiors when unfilled. If no holder exists anywhere, the step cannot resolve and must be addressed.
  • Advanced routing refines who receives a step — for example, excluding the initiator or targeting a specific role member.
  • Due dates set targets used for aging, alerts, and escalation (they never auto-complete a step). Maintain Step Delay postpones a step's start; Maintain Step Help Text shows instructions to the assignee.

3.6 Custom notifications

  • Configure the trigger (on entry or exit of a step), the recipients (roles, security groups, specific Workday accounts), and the message content (subject/body, dynamic fields).
  • Notifications inform only; unlike To Dos they require no completion and never block the process.

3.7 The event lifecycle and actions

ActionEffect
ApproveMoves the event forward
Send backReturns it to an earlier step (often the initiator) for correction; event stays in progress
DenyTerminates the entire event
CancelStops an in-progress event; its changes don't take effect
RescindReverses a completed event
CorrectEdits an in-progress event (with permission)
ReassignMoves an inbox task to the right person
DelegateTemporarily hands inbox tasks to another user for a period — a convenience, not a security change

Assigned steps appear in the user's inbox (My Tasks); the event's process history shows who acted, when, and who it awaits — your first stop when troubleshooting.

3.8 Business process security policies

  • Each process type has a security policy controlling who can initiate, approve, view, rescind, cancel, and correct its events.
  • Subprocesses have their own policies — participation there is controlled independently of the parent.
  • Like all security policy edits, changes take effect only after activation (see chapter 5).

4. Reporting 5% of the exam

4.1 Standard reports

  • Standard reports are delivered, predefined reports — ready to run subject to security.
  • They cannot be modified in place; many (Report Writer–based ones) can be copied via Copy Standard Report to Custom Report, and the copy edited freely.
  • Know the frequently referenced ones: Business Process Configuration Options (plan BP config), View Security for Securable Item, View Security Groups for User, and job-profile/organization tracking reports.

4.2 Report Writer concepts

ConceptMeaning
Business objectAn entity such as Worker or Position; fields hang off it
Data sourceA predefined, secured query returning instances of a primary business object
Related business objectsReachable through fields on the primary object (Worker → Positions), letting one report traverse entities

4.3 Building custom reports

  • Custom reports are built with Report Writer. The advanced report type unlocks the full tab set: Columns, Sort, Filter, Subfilter, Prompts, Output, Share, Advanced.
  • Filters restrict which instances return; prompts collect runtime criteria from the user (defined on the Prompts tab).
  • Temporary reports are flagged for automatic cleanup after a period; tags/categories keep the report catalog findable.

4.4 Report security and sharing

  • Sharing exposes a report to users/groups, but output is always constrained by the viewer's own security — two users can run the same report and see different rows.
  • To run a report, a user effectively needs access to the report and to the domains securing its data source and fields.

5. Security 25% of the exam

5.1 The configurable security framework

Access flows one way: users → security groups → security policies → securable items.

  • Securable items (tasks, reports, data) are grouped into domains; domains live inside functional areas (Staffing, Compensation…). Maintain Functional Areas enables/disables areas — a disabled area suppresses its contents regardless of policy grants.
  • Subdomains inherit the parent domain's policy unless deliberately overridden.
  • A user's effective access is the union of everything granted to all of their groups.

5.2 Domain vs. business process security policies

 Domain security policyBP security policy
SecuresTasks, reports, and dataActions on events of a process type
PermissionsView / Modify for users; Get / Put for integrations (modify implies view; put is the write analogue)Initiate, approve, view, rescind, cancel, correct

5.3 Activation — the two-speed rule

  • Policy edits are pending until you run Activate Pending Security Policy Changes (add a comment — it documents the timestamp for audit and rollback).
  • Security group membership changes are immediate — no activation needed.
  • Activate Previous Security Timestamp rolls policies back to a prior activation point.

5.4 Security group types

TypeMembership / access
User-basedNamed individuals; unconstrained (tenant-wide) — ideal for admins and auditors
Role-based (constrained)Members via role assignments; access limited to data of the orgs where they hold the role (plus configured subordinates)
Role-based (unconstrained)Members via role; access tenant-wide
Job-basedMembership from job attributes (job profile, family, management level, exempt status)
Location membershipMembership from assigned location
Segment-basedGrants groups access to a segment of secured values — for example, specific document categories or pay component groups
AggregationUnion (OR) of included groups
IntersectionMembers must be in all included groups (AND), optionally excluding groups — for example, HR Partner ∩ France
Service centerScopes shared-service/external representatives to supported populations
Integration system (ISSG)Holds integration system users (ISUs); best practice is a dedicated ISU per integration with least-privilege get/put grants
Note: a group's type is fixed at creation — to change approach, create a new group of the desired type.

5.5 Workday-delivered groups

GroupWho / what
All UsersEvery account holder (broader than employees)
All EmployeesEmployees only (contingent workers have their own group)
Employee as SelfSelf-service access to a worker's own data
ManagerRole-based, constrained to the manager's own organizations
ImplementersDeployment-time configuration access

Delivered groups can't be deleted; customers extend the model with their own groups.

5.6 Constrained vs. unconstrained — the heart of context

  • The distinction is scope: contextual access limited to specific organizations vs. tenant-wide reach.
  • Classic symptom: a user can see a task but retrieves no data for other orgs — their access comes from a constrained group scoped to their own organizations.
  • Two members of the same constrained group can legitimately see different data because they hold the role for different orgs.
  • Because role assignments ride on positions, access updates itself through staffing changes — prefer role/job/org-derived groups over hand-maintained user lists.

5.7 Analysis and troubleshooting

QuestionGo-to report
Which policy secures this task/report?View Security for Securable Item
Which groups does this user belong to?View Security Groups for User
What can this account access, and why?Security Analysis for Workday Account

Troubleshooting order for "I can't access X": find the securing domain/process → check whether any of the user's groups are in that policy → check constrained context → check pending (unactivated) changes.

6. Quick review — high-yield facts

  • Catalog: job family group → job family → job profile; a profile can sit in multiple families.
  • Position Management = default model; per-seat positions + restrictions; vacancies tracked; can freeze, close, or overlap positions.
  • Job Management = one set of org-level hiring restrictions; hire directly; nothing remains at termination.
  • Prepare for staffing: PM → Create Position; JM → Edit Hiring Restrictions.
  • Availability date = when usable; earliest hire date = first day someone can start.
  • Hire subprocesses: Propose Compensation (pay), Assign Pay Group (payroll), Assign Roles (roles), Onboarding (tasks).
  • Staffing model is set per supervisory organization and can be changed.
  • Every worker is staffed into a supervisory organization; locations are not organizations.
  • Create Subordinate builds the hierarchy with inheritance; unfilled roles resolve up the hierarchy.
  • Org subtypes must be allowable for the org type to appear.
  • Defaults prefill org assignments; allowed values restrict them; Change Organization Assignments moves cost centers without a job change.
  • Roles attach to positions → successors inherit; roles drive routing and role-based security.
  • Definition = template; event = live transaction. Order values sequence steps; equal values run in parallel; "ba" fits between "b" and "c".
  • Approvals don't edit; consolidated approvals combine but still don't edit; To Dos are manual and must be marked complete.
  • Validations go on the initiation step; entry condition false → step skipped; conditions = whether, routing = who.
  • Custom notifications: trigger on entry/exit, recipients (roles/groups/accounts), message.
  • Deny kills the event; send back returns it; cancel stops in-progress; rescind reverses completed; correct edits in-progress.
  • Definition edits affect new events only; org-specific definitions via copy or link; resolution walks up the hierarchy.
  • Standard reports: delivered, copy-to-custom to modify. Custom reports: Report Writer, data source = secured query on a business object; prompts = runtime criteria; sharing never overrides viewer security.
  • Security flow: users → groups → policies → securable items; items → domains → functional areas.
  • Domain permissions: view/modify + get/put (integrations). BP permissions: initiate/approve/view/rescind/cancel.
  • Policy edits need activation; group membership is immediate.
  • User-based = named + unconstrained. Role-based constrained = access only where the role is held. Segment-based = subset of secured values (document categories). Intersection = AND; aggregation = OR.
  • Employee as Self = self-service; All Users ⊃ All Employees; group type can't be changed after creation.
  • Diagnosis reports: View Security for Securable Item; View Security Groups for User; Security Analysis for Workday Account.
