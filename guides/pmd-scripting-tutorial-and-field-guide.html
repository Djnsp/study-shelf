1What PMD Scripting Is

PMD Scripting is Workday Extend's server-side scripting language for Presentation Model Definitions (PMDs). It lets you embed logic directly inside page JSON — transforming data, reacting to user interaction, validating input, and shaping outbound payloads — without any client-side JavaScript.

Despite the syntax resembling JavaScript, PMD Scripting is not JavaScript. It's a Java-based expression language executed on Workday's servers as part of Presentation Services. You cannot use JavaScript in Extend apps; PMD Scripting is the only supported logic layer in a PMD.

What you can do with it

  • Bind & transform data — compute widget values from endpoint responses using PMD functions (string:, list:, date:, number:, json:, …).
  • Call widget methods — get/set widget properties at runtime (setVisible, setError, setRows, …), replacing most needs for dynamic tag attributes.
  • Handle events — run logic on onLoad, onChange, onClick, onSubmit, onSend, and more.
  • Invoke deferred endpoints — fetch data lazily, only when your business logic actually needs it.
  • Shape outbound JSON — build or manipulate the exact request body sent to POST/PATCH/PUT endpoints.
  • Reuse logic — package functions in page-level script blocks or app-wide .script modules.

The one-line mental model

Mental model

A PMD page is a JSON document. Anywhere a value can appear, you can replace it with <% script %>. The script runs server-side, and its last evaluated expression becomes the value — unless you use an explicit return.

pmd · a value binding, a function call, and an event handler
{
  "type": "text",
  "id": "alias",
  "label": "Alternate name:",
  // instance-method style: call defaultIfBlank on the endpoint field
  "value": "<% getAlias.name.defaultIfBlank('None') %>",
  // react when the user edits the field
  "onChange": "<% console.info('New alias: ', self.value); %>"
}
PMD Scripting ≠ JavaScript

Key differences you'll trip on if you're coming from JS: && || ! only (no and/or/not word operators), the empty and size built-in functions, {:} for empty maps, the to/until range operators, backtick strings interpolate with {{var}} (not ${var}), closures cannot reassign outer variables, and there is no window, no DOM, no async.

From the field — real app footprint

In the Resource Management app that this guide dissects, the distribution looks like: 29 onLoad handlers, 50 onSend handlers, 39 onChange, 9 onClick, 7 onSubmit, 60 deferred endpoints with 59 .invoke() calls, and 1 shared script module (rafFunctions.script) included by 8+ pages. That ratio — heavy on onSend/onLoad/deferred, light on exotic events — is typical of production apps.

3Syntax Fundamentals

PMD Scripting reads like a strict, server-side dialect of JavaScript. This section covers every language element you'll actually use, per the official Reference: PMD Scripting Syntax.

3.1 Comments, identifiers, keywords

pmd-script
// single-line comment
/* multi-line
   comment */

var validName1 = 1;   // identifiers start with a-z A-Z _ $
var _a99 = 2;         // then may contain digits
// case-sensitive: var1 and Var1 are different variables

Reserved keywords you must not use as variable names include: and, break, catch, const, continue, div, do, else, eq, ge, gt, if, instanceof, le, let, lt, mod, ne, new, not, null, or, return, throw, true, try, typeof, var, while.

3.2 Variables: const, let, var

KeywordScopeReassignableWhen to use
constBlock { }NoDefault choice — guards against accidental mutation
letBlock { }YesWhen the value must change within the block
varEntire scriptYesFunction declarations; legacy code; when broad scope is intended
pmd-script
const tenant = 'gms';
tenant = 'amu';                 // ERROR: cannot reassign a const

if (condition) { let region = 'emea'; }
console.info(region);           // ERROR: region is out of scope here

// Inside a page-level "script" block you may NOT declare a bare variable
// outside a function declaration:
var someInvalidVariable;        // invalid at script-block top level
var ok = function() { var fine = 1; };  // valid

3.3 Operators

+ - * / %== !=< <= > >= && || !++ --?: ternary ?? null-coalescing?. safe access 1 to 10 (inclusive range)1 until 10 (exclusive)
pmd-script · the three null-safety tools
// ?? — return right side only when the left is null
var rows = documentList.data[0].workerDocuments ?? [];

// ?: — Elvis: return right side when left is null OR falsy/empty-ish
var userID = queryParams.userID ?: (flowVariables.userID ?: '');

// ?. — short-circuit to null instead of throwing on a missing property
console.info(map.foo.bar123?.upperCase());   // no error even if bar123 is absent

// null equality: null == null is true; null == anythingElse is false
Dot-notation trap

The dot notation interprets operators. someVariable.a-b is parsed as subtraction and fails validation. Any property containing an operator character or a reserved word needs bracket notation: someVariable['a-b'], event['for'].id.

3.4 Strings & template literals

pmd-script
var name = 'Logan McNeil';
var greeting = `Hi, {{name}}`;          // backticks interpolate with {{ }}

var message = `
Hi, {{name}}
How are you doing?
`;                                     // backticks also give you multiline
String interpolation in tag values

When a tag value mixes static text and variables, put everything inside one <% %>: "value": "<% 'static text ' + variable %>". Writing 'static text' + <%variable%> triggers a validation warning.

3.5 empty and size

pmd-script
empty(arg)   // true for: null, '', zero-length array/collection/map
size("Hello") // 5; size(null) is 0; works on arrays, strings, collections, maps

// Both also work in prefix form — very common in real code:
var customers = myEndPoint.data.customers;
empty customers ? '' : customers[0].name;
if (!empty raf.processComment) { /* ... */ }

3.6 Functions & closures

pmd-script
// named function (assigned to a variable)
var fun = function(x, y) { x + y };     // last expression is the return value
fun(17, 25);

// closure (arrow) — used heavily as arguments to list functions
var target = someEndpoint.data.find(item => {item.id == id});
var names  = memberGrid.selectedRows.map(row => {row.childrenMap.name.value});
Closures cannot reassign outer variables

This is the #1 closure gotcha. A closure may mutate an outer collection but never reassign an outer variable:

pmd-script
const items = [1, 2, 3];

let counter = 0;
items.forEach(item => { counter++; });      // ✗ FAILS — reassignment in closure

const collected = [];
items.forEach(item => { collected.add(item) }); // ✓ works — mutation is fine

let loopCount = 0;
for (var item : items) { loopCount++; }     // ✓ works — for loop is not a closure

3.7 Return semantics

The last-line rule

A script returns its last evaluated expression (or whatever follows an explicit return). This matters most after a console.* call — logging functions return nothing, so if a log is your last line, your script returns null. Always restate the value:

pmd-script
"value": "<%
  var result = getStaticText();
  console.info(result);
  result;                    // ← without this line, value would be null
%>"

4Predefined Variables

Every script runs with a set of predefined app variables in scope. Knowing which one to reach for — and their precedence — separates clean pages from fragile ones.

selfCurrent event handlerThe widget/tag that fired the event (or the endpoint in onSend, where self.data is the payload)
eventCertain eventsEvent payload: event.row (onFileAdd/Remove), event.query (onSearch)
pageVariablesCurrent page renderScratchpad map for passing data from onLoad to widgets, or between handlers
flowVariablesAcross pages in a flowState handed between wizard/flow steps (written by outboundVariable with variableScope: "flow")
sessionVariablesUser sessionLonger-lived state (same mechanism, variableScope: "session")

Null-check custom properties

Predefined variables holding maps of custom properties (pageVariables, flowVariables, queryParams) may simply not contain the key you expect. Guard every read: "<% flowVariables.aFlowVariable ?: 'fallback' %>".

The production fallback-chain idiom

Pages that can be entered from multiple routes (direct task, flow step, BP step) receive their context either via queryParams or flowVariables. The Resource Management app standardizes on this chain everywhere:

pmd-script · real pattern (rafRequest pages)
var userID = queryParams.userID ?: (flowVariables.userID ?: '');
var editWizard = queryParams.editWizard ?: (flowVariables.editWizard ?: 'false');

5Events & the Page Lifecycle

Event handlers are where PMD Scripting earns its keep. But every event fires at a precise point in the page lifecycle, and each point has different access to widgets and endpoints. Learn the three timelines below and 90% of "why is my widget null?" questions disappear.

5.1 The three timelines

lifecycle · page load (edit or view)
┌ PAGE LOAD ─────────────────────────────────────────────────────────┐
│ 1  Inbound endpoints invoked (1..*, concurrent unless dependent)   │
│      └─ onSend fires on POST inbound endpoints (shape request)     │
│ 2  onLoad fires  ← endpoints available, NO widgets yet            │
│ 3  PMD tag processing — widgets render, value scripts evaluate     │
└────────────────────────────────────────────────────────────────────┘

┌ USER INTERACTION (edit pages) ─────────────────────────────────────┐
│  onChange onClick onSearch onRowAdd onRowRemove onRowSelect       │
│  onFileAdd onFileRemove onPanelAdd onPanelRemove                  │
│  ← full widget access via self and widget ids; may .invoke()     │
└────────────────────────────────────────────────────────────────────┘

┌ PAGE SUBMIT (user clicks OK) ──────────────────────────────────────┐
│ 1  onSubmit fires (page level)  ← widget access; validation gate   │
│ 2  Outbound endpoints fire in order of placement (1..*)            │
│      └─ onSend / onMultiPartSend per endpoint (shape payload)      │
└────────────────────────────────────────────────────────────────────┘
The two rules people break most

1) onLoad cannot touch widgets. It fires before tag processing — no widget exists yet. Stash transformed data in pageVariables and let widget value scripts read from there. 2) View pages can't cross-reference widgets. Event handlers and tag attributes on a view page can't reference other widgets at all — widget interaction is an edit-page concept.

5.3 onChange essentials

pmd · official pattern — cascading widgets from a radioGroup
{
  "type": "radioGroup",
  "label": "Select a billing cycle:",
  "id": "billType",
  "instanceList": [
    { "id": "annual", "descriptor": "Annual" },
    { "id": "other",  "descriptor": "Other options" }
  ],
  "required": true,
  "onChange": "<%
    var myVal = self.value.get(0);
    if (myVal == 'annual') {
      billingRate.setValue(string:toString(40));
      billingFrequencyList.setVisible(false);
    } else {
      billingFrequencyList.setVisible(true);
      billingFrequencyList.setEnabled(true);
      billingFrequencyList.setRequired(true);
    }
  %>"
}
Always give widgets an id

Widget interaction and debugging both depend on the id attribute. Use self inside a handler instead of repeating the tag's own id — it's shorter and survives renames.

5.4 onLoad: transform once, render everywhere

pmd · real pattern (rafRequestSubmit) — cache document metadata for widgets
"onLoad": "<%
  pageVariables.employeeCVID =
      !empty getWorkersDocDtl.data[0].workerDocuments[0].referenceID1
        ? getWorkersDocDtl.data[0].workerDocuments[0].referenceID1 : '';
  pageVariables.employeeCVFileName =
      !empty getWorkersDocDtl.data[0].workerDocuments[0].fileName
        ? getWorkersDocDtl.data[0].workerDocuments[0].fileName : '';
%>"

Widgets then read pageVariables.employeeCVID in their value/visible scripts. One traversal of a deep response, zero duplication across widgets.

Reaching into grids: childrenMap

The single most-used composite pattern in production. Every grid row exposes its cell widgets keyed by columnId through childrenMap. Nested containers chain: row.childrenMap.valuesColumn.childrenMap.instanceSelectionsId.

pmd-script · official pattern — sum selected rows
var selectRow = function(grid) {
  var nameList = [];
  var expenses = 0;
  for (var row : grid.selectedRows) {
    nameList.add(row.childrenMap.fname.value + ' ' + row.childrenMap.lname.value);
    expenses += row.childrenMap.expense.value;
  }
};

7Endpoints & Scripting

Endpoints are where PMDs meet data — Workday REST APIs, your app's business objects, WQL, RaaS, and Orchestrations. Scripts appear on endpoints in three places: the url, the exclude condition, and (for deferred endpoints) explicit invoke() calls.

7.1 Dynamic URLs

pmd · real pattern (availability micro) — WQL query built in the url script
{
  "name": "clinicalAvailability",
  "baseUrlType": "WQL",
  "url": "<%
    var query = 'SELECT jan, feb, mar, apr, may, jun, jul, aug, sep, oct, nov, dec, functionalRole'
              + ' FROM ' + site.applicationId + '_clinicalAvailabilities'
              + ' WHERE resourceId in (' + queryParams.worker + ')';
    return '/data?query=' + query.urlEncode();
  %>",
  "authType": "WCPISU",
  "exclude": "<% empty(queryParams.worker) %>"
}

Three habits worth copying from this real endpoint: build the WQL as a string against site.applicationId + '_businessObject' so it survives tenant migration; always urlEncode() (or pathEncode()) query strings; and pair a parameter-driven URL with an exclude guard so the call is skipped when the parameter is absent instead of failing.

7.2 exclude: conditional invocation

pmd · real pattern (clinicalExperienceAdd) — POST vs PATCH on one page
// The same edit page serves Add and Edit. queryParams decides which outbound fires.
{ "name": "clinicalExperiencePOST",  "httpMethod": "POST",
  "exclude": "<% !empty(queryParams.clinicalExperienceId) %>" },

{ "name": "clinicalExperiencePATCH", "httpMethod": "PATCH",
  "url": "<% '/clinicalAssignments/' + queryParams.clinicalExperienceId %>",
  "exclude": "<% empty(queryParams.clinicalExperienceId) %>" }

7.3 Deferred endpoints & invoke()

Mark an endpoint "deferred": true and it does not fire at page load. Call it from any widget event handler with invoke(), optionally passing a map whose keys become variables inside the endpoint's url script.

pmd · official pattern — search-as-you-type
{
  "type": "text",
  "id": "searchName",
  "label": "Please enter a name to search",
  "onChange": "<%
    var result = workerData.invoke({'name': self.value});
    workersGrid.setVisible(true);
    workersGrid.setRows(result.data);
  %>"
}

// endpoint definition:
{
  "name": "workerData",
  "baseUrlType": "worker",
  "url": "<% 'workers?limit=10&search=' + name %>",   // ← 'name' from invoke() map
  "authType": "SSO",
  "deferred": true
}
Check the response before using it

Real code from the app validates the deferred response before touching widgets: if (!empty searchList && empty searchList.errors) { … }. Deferred calls can fail; a bare result.data[0].x becomes a page error.

From the field — inline invoke inside a value binding

Deferred invokes aren't limited to event handlers. The app resolves a therapeutic area at submit time inside an outbound value script: selectedIndication.value[0] ? therapeuticAreasSearch.invoke({'indication': selectedIndication.value[0]}).data[0].therapeuticAreaId.id : ''. Powerful — but each inline invoke is a network round-trip; don't put one in a grid cellTemplate.

7.4 Environment-conditional endpoint attributes

pmd · real pattern — different auth in dev vs deployed tenants
{
  "name": "convertRoleHistory",
  "baseUrlType": "ORCHESTRATE",
  "authType": "<% environment == 'WCPDEV' ? 'sso' : 'WCPISU' %>",
  "httpMethod": "POST",
  "url": "/ConvertRoleHistory/launch"
}

8Outbound Data & onSend

There are three ways to build the JSON your page submits, and they compose. Master the precedence rules and self.data and you control every byte that leaves the page.

8.1 The three payload mechanisms

MechanismHow it worksChoose it when
valueOutBinding (on widgets)Binds a widget's value into the payload at a path: "endpointName.fieldName"Simple field-to-field mapping
values + outboundPath (on the endpoint)Each entry computes one payload field with a scriptFields need per-field transformation
onSend (on the endpoint)Runs last; self.data is whatever the above produced; return the final payloadCross-field logic, restructuring, conditional skip
Precedence & the null contract

self.data inside onSend contains everything valueOutBinding/values built — or null if none exist. For outbound variables, values takes precedence over onSend. Returning null from onSend cancels a POST/PATCH/PUT (DELETE still fires — it needs no body). That makes onSend a legitimate last-second veto.

8.2 valueOutBinding + onSend enrichment

pmd · official pattern — bind, then enrich
{
  "type": "text",
  "id": "currentBusinessTitle",
  "value": "<% workerData.businessTitle %>",
  "valueOutBinding": "businessTitleChange.proposedBusinessTitle"
},
...
"outboundData": {
  "outboundEndPoints": [{
    "name": "businessTitleChange",
    "baseUrlType": "workday-common",
    "url": "<% '/workers/' + queryParams.workerId + '/businessTitleChanges' %>",
    "httpMethod": "POST",
    "onSend": "<%
      self.data.proposedBusinessTitle = getNewTitle();
      self.data.descriptor = 'Title Change : ' + name.value;
      self.data;                        // ← always end with the payload
    %>"
  }]
}

8.3 values with per-field scripts

pmd · real pattern (clinicalExperiencePATCH) — transform each field
"values": [
  {
    "outboundPath": "studyTypes",
    "value": "<%
      var studyTypeList = [];
      if (!empty selectedStudyTypes.value) {
        selectedStudyTypes.value.forEach(item => { studyTypeList.add({'id': item}) });
      };
      return studyTypeList;                 // multiselect → array of {id}
    %>"
  },
  {
    "outboundPath": "indicationID.id",       // dotted path builds nested JSON
    "value": "<% selectedIndication.value[0] ?: '' %>"
  }
]

8.4 onSend building the whole payload

pmd · real pattern — launch an Orchestration with a hand-built body
{
  "name": "convertRoleHistory",
  "baseUrlType": "ORCHESTRATE",
  "httpMethod": "POST",
  "url": "/ConvertRoleHistory/launch",
  "onSend": "<%
    var userID = queryParams.userID ?: (flowVariables.userID ?: '');
    return {'worker': userID, 'employeeID': employeeID.data[0].employeeID};
  %>"
}

8.5 outboundVariable: state across flow pages

pmd · real pattern — persist context into flowVariables
"outboundData": {
  "outboundEndPoints": [{
    "type": "outboundVariable",
    "name": "initiatingPage",
    "variableScope": "flow",
    "values": [
      { "outboundPath": "editWizard",
        "value": "<% queryParams.editWizard ?: (flowVariables.editWizard ?: 'false') %>" },
      { "outboundPath": "userID",
        "value": "<% queryParams.userID ?: (flowVariables.userID ?: '') %>" }
    ]
  }]
}
// The next page in the flow reads flowVariables.editWizard, flowVariables.userID.
// Note the pass-through idiom: re-emit incoming context so it survives every hop.

9Script Blocks & Script Modules

Three tiers of reuse: a page-level script block, an app-wide .script module, and nested modules (max 2 dependency levels). Choose the smallest tier that fits.

9.1 Page-level script block

pmd
"script": "<%
  var getRegistrationFee = function() {
    return 75;
  };
%>",
// any widget on the SAME page (and pods used by the page) can call it:
"value": "<% getRegistrationFee() + (12 * flowVariables.monthlyRate) %>"
  • Declare each function with var name = function() {…}. Put the block at the top of the PMD.
  • Inside one embedded script, define a function before the function that calls it.
  • No bare variable declarations at block top level — only function declarations.

9.2 Script modules (.script files)

A .script file lives in presentation/scripts. It contains plain function declarations (no <% %> wrapper) and ends with an export map. Pages opt in with "include", then call functions namespaced by the module name.

script · real module (rafFunctions.script, abridged)
var determineAvailabilityMonth = function(availabilityDate) {
  var availDate = availabilityDate.format('MMM');
  return availDate.toString().lowerCase();
}

var getComments = function(eventComments, raf) {
  var valuesArray = [];
  if (!empty raf.processComment) {
    var comment = {:};                       // {:} = empty map literal
    comment.dateVal = raf.processDateChange ?: '';
    comment.person  = 'Salesforce';
    comment.text    = raf.processComment ?: '';
    valuesArray.add(comment);
  }
  if (!empty eventComments.data) {
    for (var x : eventComments.data) {
      var comment = {:};
      comment.dateVal = x.commentDate ?: '';
      comment.person  = x.person.descriptor;
      comment.text    = x.comment ? '<p>' + x.comment + '</p>' : '';
      valuesArray.add(comment);
    };
  }
  return list:sort(valuesArray, 'dateVal', false);   // newest first
}

// ⬇ REQUIRED: the export map — only listed functions are callable from pages
{
  "getComments" : getComments,
  "determineAvailabilityMonth" : determineAvailabilityMonth
}
pmd · including and calling the module
{
  "id": "rafRequestApprove",
  "include": [ "rafFunctions.script" ],
  ...
  // call functions as moduleName.functionName(...)
  "rows": "<% rafFunctions.getComments(eventComments, getRafRequest) %>"
}
Module rules that bite

Don't wrap module content in <% %>. Only exported names are visible. Nested modules max out at 2 dependency levels (a.script → b.script → c.script; if c includes anything, validation fails). And note the self-reference quirk visible in the real module: when one module function calls another, it calls it through the module namespace — rafFunctions.isClinicalAssignmentField(...) — even inside rafFunctions.script itself.

11Logging & Debugging

The console object logs to the Extend developer console (View Extend Logs / app monitoring). Four levels, all variadic, none return a value.

pmd-script
console.debug('Debug the current value: ', self.value);
console.info('Informational value: ', self.value);
console.warn('Warning value: ', self.value);
console.error('Invalid value error: ', self.value);

Production debugging habits (from the app)

  • Log outbound payloads on every onSend: console.info('Clinical Experience POST: ' + json:asJSON(self.data)); return self.data; — visibility into exactly what was submitted, with the payload restated as the last line.
  • Tag log lines with a grep-able prefix: the app uses markers like DEBUG_CONNECT so log searches isolate one feature.
  • Log both sides of a comparison before acting on it: console.debug(' Sent Back ' + dateOfSentBack + ' Doc Created ' + latestCVDocCreated);
console kills your return value

console.* methods return nothing. If a log is the final statement of a value, onSend, or module function, the script returns null — silently blanking a widget or cancelling a POST. Always restate the value (self.data;) as the true last line. This is the single most common self-inflicted PMD bug.

Reading script failures

When a script throws at runtime, the page error contains the script error detail, and the same detail lands in the Extend logs. CPU time per script is capped (≈5s, excluding endpoint invocations and widget API calls, which run in separate execution contexts) — a runaway loop surfaces as a script timeout, not a hung page.

Scenario 1 — Per-row validation on a dynamic criteria grid

Problem: Users build a candidate search from a grid where each row is one criterion (criteria type, And/Or, operator, values, priority). Before running the search you must validate every row — required cells, conditional rules (a proficiency is required only when a priority is set on a skill row), and a cross-row rule (each priority number may be used only once) — and surface errors on the exact cell with the row number.

Show solution & why it works
script · rafFunctions.script (abridged real code)
var validateSearchCriteria = function(searchGrid) {
  var isErrorFound = false;
  var rowIndex = 1;

  for (let thisRow : searchGrid.rows) {
    let searchType = thisRow.childrenMap.searchCriteriaCol.value[0] ?: '';

    // 1) always clear ALL cell errors first — stale errors are worse than none
    thisRow.childrenMap.searchCriteriaCol.clearError();
    thisRow.childrenMap.andorCol.clearError();
    thisRow.childrenMap.operatorCol.clearError();
    thisRow.childrenMap.valuesColumn.childrenMap.instanceSelectionsId.clearError();

    // 2) required-cell checks, error message carries the row number
    if (empty thisRow.childrenMap.andorCol.value[0]) {
      thisRow.childrenMap.andorCol.setError('And/Or is required for row ' + rowIndex);
      isErrorFound = true;
    }

    // 3) conditional rule: proficiency needed only when priority is set on skills
    let ranking = !empty thisRow.childrenMap.includeYrAndSkillCol.value[0]
        ? number:convertStringToInt(thisRow.childrenMap.includeYrAndSkillCol.value[0]) : 0;
    if (searchType == 'seachSkills') {
      let prof = !empty thisRow.childrenMap.skillLevelsCol.value[0]
          ? number:convertStringToInt(thisRow.childrenMap.skillLevelsCol.value[0]) : 0;
      if (ranking > 0 && prof == 0) {
        thisRow.childrenMap.skillLevelsCol.setError(
          'A proficiency is required ... in row ' + rowIndex);
        isErrorFound = true;
      }
    }

    // 4) cross-row rule: a priority number may appear only once — filter the grid
    if (ranking > 0) {
      let priorityStr = thisRow.childrenMap.includeYrAndSkillCol.value[0];
      let priorityCount = 0;
      for (let row : searchGrid.rows.filter(row => {
              !empty row.childrenMap.includeYrAndSkillCol.value[0] &&
              row.childrenMap.includeYrAndSkillCol.value[0] == priorityStr }) ?? []) {
        priorityCount = priorityCount + 1;
      }
      if (priorityCount > 1) {
        thisRow.childrenMap.includeYrAndSkillCol.setError(
          'Priority ' + ranking + ' can only be specified once');
        isErrorFound = true;
      }
    }
    rowIndex = rowIndex + 1;
  }
  return isErrorFound;      // caller gates the search/submit on this flag
}

Why it works: clear-then-validate prevents stale errors; childrenMap reaches the exact cell so the error renders in place; counting inside a for loop sidesteps the closure-reassignment restriction (note: the real code increments the counter in the loop body, not inside the filter closure); and returning a boolean lets both onChange and the Search button share one function. Notice the priority-count loop iterates a filtered row list — filter for the value, count matches, error if >1: a general recipe for any "unique across rows" rule.

14Best Practices & Pitfalls

The ten commandments (earned the hard way)

  1. End onSend with the payload. After any console.* call, restate self.data (or your object). A trailing log = null return = cancelled POST.
  2. Selection widget values are lists of strings. Read self.value[0], and convert with number:convertStringToInt() before arithmetic.
  3. Guard every optional read. ?? [] for lists, ?: '' for strings, ?. for deep chains, empty checks before indexing data[0].
  4. onLoad transforms, widgets render. Never reference widgets in onLoad; write to pageVariables instead.
  5. Clear errors before setting them. Validation that doesn't clear first strands stale errors after the user fixes the input.
  6. exclude beats failure. A parameterized endpoint without an exclude guard is a page error waiting for a missing query param.
  7. Don't reassign outer variables in closures. Mutate collections, or use a plain for loop for counters.
  8. urlEncode every WQL query. And build table names from site.applicationId, never hardcoded reference IDs.
  9. One invoke, many fields. Prefer a single onSend lookup that fills several payload fields over inline invokes scattered across values — and never put an invoke in a grid cellTemplate.
  10. Give every widget an id, and prefer self. Debuggability and refactor-safety in one habit.

Performance mindset

PMD scripts run per page render or per event on Workday's servers under CPU and memory limits. Push heavy lifting down: filter in WQL (WHERE), not in list:filter; aggregate in the query, not in a loop; and reach for an Orchestration when the logic involves multiple API calls, loops over large datasets, or needs to run without a page.
