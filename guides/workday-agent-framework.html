Part 1 — The Foundations

How AI agents actually work

Before any Workday-specific terms, here is the whole idea in plain language: what an agent is, how it thinks, and how it uses tools and skills to get things done. Everything in Part 2 is just this, applied inside Workday.

1.1What an "agent" really is

A plain large language model (LLM) — the thing behind a chatbot — can only do one thing: read text and write text back. It is brilliant at language but it is sealed in a box. It can't look up your time-off balance, it can't submit a request, it can't read a live database. It only predicts words.

An AI agent is that same language model, but given two new things: a set of tools it is allowed to use, and the freedom to decide on its own when to use them, in a loop, until a goal is met. The model stops being a narrator and becomes a doer.

The simplest analogy

A chatbot is a brilliant colleague locked in a room with no phone — you can ask them anything and they'll talk, but they can't act. An agent is the same colleague, now handed a phone, a company directory, and permission to make calls. Same brain. Suddenly they can get things done — look things up, fill out forms, take actions — because they can reach the outside world and decide which "call" to make.

Three differences separate an agent from ordinary automation like a script or an integration:

  • It decides, you don't script it. A traditional integration follows a fixed, pre-written path. An agent is given a goal in plain language and works out the steps itself.
  • It loops. It can take an action, look at the result, and decide what to do next — adjusting as it goes, instead of running once top-to-bottom.
  • It speaks human. The instruction is "what is my time-off balance?", not a function signature. The model translates intent into the right tool calls.

1.2The agent loop — how it "thinks"

Functionally, every agent runs the same cycle. The model is handed your request plus a list of the tools available to it. It reasons about what's needed, optionally calls a tool, reads what comes back, and repeats until it can give a final answer. This loop is the entire mechanism.

The crucial point: the model never touches your systems directly. It only ever emits a request to call a tool. Something outside the model actually runs that tool and hands the result back as text. That separation is exactly where security and governance live — a theme that returns throughout Part 4.

1.3Tools and "function calling"

A tool is a single, well-defined capability the agent can use — "get a worker's details," "submit a time-off request," "run this query." Technically, a tool is described to the model as a small contract: a name, a plain-English description of what it does and when to use it, and a schema of the inputs it expects.

The model is given this list of contracts alongside your question. When it decides a tool is needed, it doesn't run code — it produces a structured message that says "call getTimeOff with {worker: "me"}." This is called function calling or tool calling. The runtime executes it and feeds the output back into the loop.

Why the descriptions matter so much: the model picks tools by reading their descriptions. A vague description ("does stuff with pay") makes the model choose badly; a precise one ("makes an ad-hoc percentage adjustment to base pay; use when asked to raise or lower compensation by a percent") makes it choose correctly. This is a detail Workday is explicit about — when you expose your own logic as a tool, the quality of the description directly drives whether the agent calls it at the right time.

1.4Skills — bundling capability with intent

If a tool is a single action, a skill is a higher-level capability that an agent advertises — for example "Staffing" or "Time Off Management." A skill packages together the instructions for how to handle a kind of request and the set of tools needed to fulfil it. One agent can have several skills; one skill can call several tools.

This three-level shape — Agent → Skill → Tool — is worth holding onto, because Workday uses these exact three words with exactly these meanings. The skill is also the level at which permissions are attached: you decide which users may invoke a given skill, not the agent as a whole.

1.5What MCP is — the universal adapter

Here's the problem MCP solves. Every AI platform (Claude, Cursor, Copilot, a homegrown agent) used to need its own custom code to connect to every system (Workday, Salesforce, your database). That's an N×M mess — every client times every system.

The Model Context Protocol (MCP) is an open standard that fixes this. A system exposes its tools once behind an MCP server. Any MCP-compatible client can connect to that one endpoint and immediately discover and call every tool, using one common language. It is, in effect, a USB-C port for AI tools: one shape that fits everything.

Technically MCP rides on JSON-RPC 2.0. A client calls a method named tools/list to discover what's available, and tools/call to run one. The model handles tool selection and call syntax automatically — you, the builder, mostly just point your agent at the endpoint and grant it access. Keep this picture; in Part 2 the "MCP server" becomes a specific Workday URL and the "300+ tools" become real Workday operations.

1.6One full request, end to end

Stitching 1.2–1.5 together, here is the complete shape of a single agent request against an MCP-connected system — still generic, no Workday yet:

  1. You ask in plain language. Your message, the conversation so far, and the agent's tool list all go to the model.
  2. The model reasons and decides a tool is needed. It emits a tools/call with a tool name and arguments.
  3. The runtime authenticates the call and routes it to the MCP server, which executes the real operation against the underlying system.
  4. The result returns to the model as data.
  5. The model loops or finishes — calling more tools if needed, then writing a human answer (or rendering a form / card) back to you.

That is the entire machine. The rest of this guide is Workday giving each of these boxes a concrete name, a real endpoint, and — critically — a wrapper of governance and security around every arrow.

Part 2 — Applied

The Workday Agent Framework

Now the same five boxes, with Workday names. The model is Workday's delivered LLM. The tools are 300+ Agent-Ready operations. The MCP server is a real URL. And a control plane called ASOR governs every one of those arrows.

2.1The big picture

Read this diagram top to bottom: a person (or another system) makes a request through some surface; the Agent Gateway authenticates and routes it; ASOR decides what the agent is allowed to do; the agent's skills call Agent-Ready tools over MCP; and those tools touch real Workday data and business processes — always under the user's own permissions.

2.2Agent · Skill · Tool, the Workday way

Workday uses the exact three-level vocabulary from Figure 3, with precise meanings. Internalize these — every other concept hangs off them.

Agent

The top-level entity — a persona or functional domain, like "Payroll Agent" or "Recruiting Assistant." This is what gets registered in ASOR and what administrators manage.

Skill

A discrete capability the agent can perform. An agent can have many skills. The skill is the unit that gets secured with permissions and activated for specific users.

Tool

A concrete Workday Agent-Ready operation a skill calls to do its work — e.g. getWorkers, terminateEmployee. One skill can call many tools.

When you build a Workday Custom Agent, these three things become real files: an agent definition (a .agent file) and one or more skill files (.agentskills) that declare the capabilities and the tools each skill is wired to.

2.3ASOR — the control plane for every agent

Agent System of Record (ASOR) is the single most important Workday-specific concept. It is the governed registry and control plane that sits between any agent and your Workday data. Nothing — no Workday-built agent, no custom agent, no external agent — can touch your tenant without being registered and activated here first.

ASOR answers three questions for every agent: Does it exist and is it active? (the Agent Registry) · Which of its skills may run, and for which users? (skill status + the "Available To" security groups) · Is it safe? (the Trust & Safety Passport, covered in Part 4).

Enabling ASOR is a one-time tenant setup: you turn on the Agent System of Record functional area and grant a security group permissions on its domains — Agent Management Hub, Manage: Agents, Setup: Agents, Reports: Agent Reporting, and Agent Compliance. One constraint worth flagging now: ASOR currently supports only Unconstrained security groups. The central interface where admins live day-to-day is the Agent Management Hub.

2.4The tools and the MCP server

Workday ships 300+ Agent-Ready tools spanning Workforce, Financials, Talent, Payroll, and Recruiting. "Agent-Ready" means Workday has wrapped a native operation as an MCP-callable tool with the right description and schema. They are the same tools whether they power a Workday Custom Agent or an external agent like Claude — the difference is only how the agent is registered.

Finding tools — two ways

  • MCP Explorer — a browsable web UI at developer.workday.com/mcp-explorer that lists every Agent-Ready tool and Workday-built agent. Filter by functional area, search by name, read descriptions, no code required. The recommended starting point.
  • Finder API (ASOR Agent Resource Search) — programmatic discovery for scripts and build pipelines. You search by searchString, filter by toolType (AGENT_READY or AGENT), operationType (CREATE / PATCH / VIEW), and protocol=MCP. Each result returns a wid — the identifier you drop into your agent definition to wire the tool in.
# Finder API — discover Agent-Ready tools for "time off"
GET https://us.agent.workday.com/asor/agentResourceSearch/v1
    ?searchString=time off &toolType=AGENT_READY &protocol=MCP

# → [{ "name":"getTimeOffEntries", "wid":"386c…0000", "mcpEnabled":true }]

The four kinds of tool a custom agent can call

When you build a Workday Custom Agent, its skills can reach for any of four tool families:

Tool familyWhat it does
Agent-Ready Tools MCPCalls Workday APIs that are agent-ready. Includes Workday's delivered LLM components.
Orchestrate Actions MCPCalls your own Orchestrations (registered as Agent Actions) as tools — your proprietary business logic, Pipedream connectors, custom processing, REST/SOAP calls.
Live Data Query (LDQ)Connects to Workday Data Cloud as a query tool for SQL generation against tenant data.
Agent-to-User Interface (A2UI)Lets the agent render real UI — forms, cards, buttons — in the Workday Chat Panel instead of plain text.

The single MCP endpoint

External agents connect to one URL — https://us.agent.workday.com/mcp — speaking standard JSON-RPC 2.0. Calling tools/list returns exactly the tools your registered agent is permitted to use; tools/call runs one. For Workday Custom Agents built in App Builder, tool discovery and registration are handled automatically when you Save & Deploy — you never hand-wire the endpoint.

# Verify your agent's tools are wired correctly
POST https://us.agent.workday.com/mcp
Authorization: Bearer <ASU token>
{ "jsonrpc":"2.0", "id":1, "method":"tools/list" }

2.5Building a custom agent with Developer Agent

The Developer Agent is an AI builder that lives in App Builder (and in your IDE via a VS Code extension for Claude, Cursor, Antigravity, and others). You describe the agent you want in plain English; it scaffolds the .agent and .agentskills files for you, which you can then refine by prompt or by editing the code directly.

Two safety-minded details are built into the workflow. Draft Mode: generated changes show as a side-by-side diff and don't touch your real app until you click Apply. Agent Traces: every message to a deployed agent captures a full execution trace — which tools were offered to the model, which it actually called, and what the chat panel rendered — so you can debug by comparing a working run against a broken one. If a tool is missing from the trace's inputs, the fix is almost always in your ASOR configuration.

2.6Orchestrate Agent Actions — your logic as a tool

This is how your own business logic enters the tool catalog. Any synchronous Workday Orchestration can be flagged as an Agent Action, which exposes it as an MCP tool that any compatible agent can discover and invoke by natural language. Rather than an agent stitching together dozens of low-level APIs, it calls the one deterministic orchestration you already built and trust.

When you enable an Agent Action you give it an action name, a description that explains what it does and when to use it, parameter descriptions (with formats and sample values), and — importantly — an effect annotation so the agent understands the stakes:

AnnotationMeaningAgent behavior
Read-OnlyReads data; can't modify or delete.May call without asking the user.
IdempotentSafe to retry; calling twice = calling once.Safe to repeat on failure.
DestructiveCan modify or delete data.May prompt the user to confirm first.

Builder's noteWorkday warns that empty parameter descriptions or stray empty header/query rows produce invalid tool schemas and badly degrade the agent's ability to pick and call the tool. The description quality is the interface.

2.7A2UI — when the agent needs to show, not tell

Sometimes a text reply isn't enough — the user needs a form to edit, a card highlighting a figure, or a button to approve something. Agent-to-User Interface (A2UI) lets a custom agent render real interactive components inside the Workday Chat Panel. You build an A2UI-enabled Extend page using a subset of page tags called chat tags (containers, editable fields, read-only fields, and invisible fields for tracking IDs), and a skill instructs the agent when to invoke that page.

Functionally this closes the loop back to the user: the agent can gather structured input (pre-populated from an endpoint if needed), the user edits and submits, and the agent's skills persist the change. It's how a conversational agent becomes a genuine mini-application rather than just a smart reply box.

2.8Delegate vs Ambient — the two ways an agent acts

Every agent skill runs in one of two execution modes, and the distinction is the heart of Workday's security model. It decides whose permissions apply when a tool runs.

 Delegate skillsAmbient skills
Acts asA specific signed-in userItself, with its own permissions
OAuth flowAuthorization Code Grantx509 Key Association
Primary credentialClient ID + Client Secretx509 Public Key
Activation needsA Redirect URIAn x509 association
Allowed whereAny tool the user can accessOnly domains whose Allowed Security Group Types permit ambient access

The single most reassuring sentence in the whole framework: in Delegate mode the agent cannot bypass the user's security. If the user can't see a worker's pay, neither can the agent acting for them. You validate this with the View Security for Agent Skill report.

2.9How agents actually get invoked

A registered, active agent can be reached three ways — the same agent, three front doors:

  • Conversationally — a user chats with it in the Workday Chat Panel (or in an external platform via A2A, next section).
  • Inside a business process — you add an Invoke Agent service step to a business process. Because no human is in the loop, you instruct the agent in the step's configuration (e.g. "Execute actions immediately; do not seek user confirmation") and pick a Run As security group for delegate skills. When the step fires, Workday confirms the agent is registered and active in ASOR, runs it, then continues the process.
  • File-driven — users can attach documents (up to 10 per message) in chat and ask the agent to process them, with the agent able to pull files into a sandbox for further work.

2.10A2A — agents talking to agents across platforms

Agent-to-Agent (A2A) is how a Workday agent becomes callable from outside Workday — from Google Gemini Enterprise, Microsoft Copilot Studio, or any A2A-compatible platform. The end user chats in their own tool; behind the scenes, a Workday agent (such as the delivered Self-Service Agent) does the real work and answers back in natural language. Every custom agent you build is automatically A2A-ready.

The bridge is the agent card — a JSON document at /.well-known/agent-card.json describing the agent's endpoints, capabilities, and auth requirements. The external platform fetches it, you paste in OAuth client details (Client ID/Secret, Auth URL, Token URL, Redirect URI) you created with Register API Client for agents, and grant your users an "Agent User" role on that side. From then on, users authenticate to Workday once and chat naturally — "what is my time off balance?", "show me my goals."

Traffic also runs the other direction. With Microsoft Agent Sync, agents built in Copilot Studio or Azure AI Foundry are pulled into ASOR, their Microsoft tools mapped to Workday tools, and then governed by ASOR like any native agent — one registry of record for agents wherever they were built.

Part 3 — Synthesis

How it all ties together

Two views of the whole machine in motion: the lifecycle of getting an agent live, and the runtime trace of a single user request travelling through every layer you've now met.

3.1The lifecycle — discover, register, activate, run

No matter how an agent is built, it follows the same path to becoming usable. The recurring lesson: building or registering an agent does nothing on its own — activation in ASOR plus a permitted security group is what flips it on.

3.2End to end — "What's my time off balance?"

Here is the payoff: a single, ordinary question traced through every component in this guide. Each numbered step maps to a concept you've already met — the agent loop (Part 1), the Gateway and ASOR (Part 2), and the security checks (Part 4).

Notice what had to be true for step 8 to succeed: the token was valid (Gateway), the skill was active and the user was in its permitted group (ASOR), and that same user independently had the right to view their own time-off balance (delegate-mode security). Three separate locks, all of which must open. That layered design is the entire subject of Part 4.

Part 4 — Trust

How it's kept secure

An agent that can read pay, terminate workers, and move money is only as good as the controls around it. Workday's answer is defense in depth: independent layers, any one of which can stop a bad action — and none of which an agent can talk its way past.

4.1Layers of defense

Security isn't one feature; it's five concentric checks a request crosses before it can change anything. They are independent on purpose — defeating one doesn't defeat the rest.

4.2OAuth, the Gateway, and agent identities

All agent access is built on the OAuth 2.0 framework, enforced at the Agent Gateway, which also routes each request to the correct regional endpoint. How an agent proves who it is depends on its mode (from §2.8):

  • Delegate skills use the Authorization Code Grant: the user logs in, the platform gets an authorization code, exchanges it for an access token, and every tool call rides on that token. The agent is, in effect, holding the user's session.
  • Ambient skills use x509 key association instead — a public-key credential tied to an Agent Service User (ASU) identity, governed by its own permissions and limited to domains explicitly opened to ambient skills.

Credentials are managed in the agent profile's Connectivity tab, and the OAuth client secrets shown at activation are displayed once — Workday is explicit that you must save them immediately. At runtime, these ASU/OAuth credentials are what let the agent call MCP tools on the user's behalf.

The principle that anchors everything

An agent never gets a master key. In delegate mode it borrows the user's permissions and can do nothing the user couldn't do by hand. In ambient mode it has its own narrowly-scoped identity, allowed only into domains that have explicitly opted in. There is no "agent override."

4.3Agent Passport — proving an agent is safe

Authentication proves who an agent is; it doesn't prove the agent is well-behaved. That's the job of the Trust & Safety Passport (Agent Passport). After you activate an agent, you run Scan Agent; Workday (with validation partners) probes it and records a set of stamps — pass/fail safety attestations visible on the agent's profile. The Passport tab only appears after activation, by design.

Runtime Guardrails

Live controls on what the agent may do as it runs. Target status: Passed.

PII Exfiltration Resistance

Can the agent be tricked into leaking personal data? Must resolve to Passed or Failed — never left Pending.

Jailbreak Resistance

Does it hold up against prompts engineered to break its instructions?

System-Prompt Confidentiality

Will it keep its own hidden instructions hidden when probed?

Output Safety Filtering

Are the agent's responses screened for unsafe content?

A failing stamp is a signal to fix the agent before trusting it with real work — Workday publishes guidance on addressing successful attacks surfaced by validation. The Passport turns "is this agent safe?" from a hopeful assumption into a checkable, ongoing status.

4.4Audit trails and token hygiene

Every agent action is accountable. Because delegate-mode calls run under the user's identity, the standard Workday audit trail shows the agent acting on that user's behalf, and the dedicated View AI Agent User Audit Trail report (secured to Reports: AI Agent Security) gives a purpose-built view of agent activity. Nothing an agent does is invisible.

Finally, tokens are deliberately short-lived so a leaked credential has a small blast radius:

CredentialLifetimeRenewal
MCP access token~60 minutesUse the refresh token before it expires
Refresh token~24 hoursUser re-authenticates after this
Orchestrate Agent Action token~1 hourMCP client must refresh to stay connected

Most agent platforms and API clients handle this refresh cycle automatically — but the design intent is clear: access is continuously re-proven, never granted once and forgotten.

The whole guide in three sentences

An agent is an LLM that can decide to call tools, grouped into skills, discovered and run over MCP. Workday delivers 300+ ready tools and a builder for your own, all governed by ASOR, which controls who exists, what runs, and for whom. And every action is wrapped in layered security — Gateway auth, ASOR permission, the user's own access, the tool's domain policy, and the Agent Passport — so an agent can be powerful without ever being a master key.
