PART 1 — ORIENTATION
§01

Why XSLT 3.0 for Workday

XSLT is the transformation layer of almost every outbound Workday integration: EIB custom transformations, Studio XSLT steps, and Document Transformation integrations all take the XML Workday produces (usually a RaaS report) and reshape it into whatever the vendor wants — CSV, fixed-width, vendor XML, JSON, or a Workday Web Services request going back in.

XSLT 3.0 (a W3C Recommendation since 2017, processed by Saxon-EE in the Workday cloud) matters for four practical reasons:

CapabilityWhat it replacesChapter
Streaming — transform gigabyte reports in flat memory Out-of-memory failures on full-file EIBs; awkward Studio splitters used purely to control memory§10
Maps & arrays — real in-memory lookup tables xsl:choose ladders, lookup documents walked with key(), Java extension hacks§06
Native JSON — parse-json(), xml-to-json(), json-to-xml() String-concatenation JSON building; external libraries§11–§12
Resilience & ergonomics — xsl:try/catch, text value templates, xsl:iterate, accumulators, higher-order functions One bad row killing the integration event; verbose xsl:value-of walls; fragile recursion for running totals§05, §08, §09, §13
WHERE EACH VERSION FITS TODAY
Workday's documented Studio best practice is still XSLT 2.0 with the Saxon Transformation Factory; XSLT 3.0 + streaming is taught mainly through the EIB-oriented "XSLT for Workday" path for high-volume files. In practice: write new transforms as version="3.0", keep them 2.0-compatible where you don't need 3.0 features (the boomerang in §17 is an example), and reach for streaming deliberately when volume demands it. Everything in this guide was validated with SaxonC-HE 13 — the same Saxon family Workday runs.
WHEN NOT TO USE XSLT
Core Connector outputs with simple field-level tweaks are usually better served by ETV/XTT (Document Transformation with Extended Transformation Vocabulary) — keep XSLT for structural reshaping, multi-record logic, JSON, and write-backs.
§02

The RaaS document model — and the namespace gotcha

Every example and problem in this guide runs against real-shaped Workday data. The primary input is a RaaS (Report-as-a-Service) document with three workers — the same document shape you get from any custom report enabled as a web service.

Structural facts you will use constantly:

  • Root is wd:Report_Data; each row of the report is one wd:Report_Entry.
  • Report fields are elements; reference fields carry a wd:Descriptor attribute alongside the value (Cost_Center above has both a code and a descriptor).
  • Multi-instance fields simply repeat (wd:Dependent) — Logan has two, John has none.
  • Typed attributes hang off values: wd:Annual_Salary/@wd:Currency.
THE #1 CAUSE OF EMPTY OUTPUT
The wd namespace URI is per-report: urn:com.workday.report/<Report_Name>. If the xmlns:wd in your stylesheet doesn't match the report's WWS namespace exactly, every template silently fails to match and you get an empty file — no error, no warning. Fix it at the source: in the report's Advanced ▸ Web Service options, override the namespace to a stable value (commonly urn:com.workday/bsvc for boomerangs) so renaming the report never breaks the transform. The prefix (wd, r, anything) is irrelevant; only the URI must match.

Secondary inputs used later: comp_dupes.xml (compensation rows with duplicates, §14/P07), cc_updates.json (inbound JSON, §12/P08), bad_salary.xml (dirty data, §13), and lookup_stream.xml (two-section lookup + payload, §09/P10). Each is shown at first use.

§04

xsl:mode — kill the boilerplate

In 1.0/2.0 the behaviour for unmatched nodes was fixed (copy text through, recurse into children). XSLT 3.0 lets you declare it once with xsl:mode, which eliminates the identity-template and "suppress everything" boilerplate that opened every stylesheet.

§06

Maps & arrays — real lookup tables at last

XPath 3.1 adds map(K,V) and array(T) as first-class values. For integration work, maps are the headline: O(1) code translations and cross-references without xsl:choose ladders, without walking a lookup document per row, and without Java extensions.

§07

XPath 3.1 turns functions into values. Three higher-order functions cover 90% of integration needs — sort(), filter(), fold-left() — and the arrow operator => makes chained calls read left-to-right like a pipeline.

§08

xsl:iterate — running state without recursion

Header/detail/trailer files are the bread and butter of payroll and benefits outbounds — and the trailer needs record counts and hash totals. Pre-3.0 you either walked the sequence twice or wrote tail-recursive templates. xsl:iterate is a for-each that carries parameters forward between items, emits a block on-completion, and can stop early with xsl:break. Crucially, it is streamable.

INPUT workers.xml

The header date line reflects the run date of validation. Note the discipline: derive sequence numbers from the carried state rather than position() so the identical code remains valid inside a streamed pass. P06 makes you build this pattern yourself.

§09

Accumulators — remember things while you stream

An accumulator is a named value that updates as the processor walks the document past matching nodes. Read it with accumulator-before() (value on arriving at the current node) or accumulator-after() (value after processing it). Because rules fire during the single forward pass, accumulators are the idiomatic way to keep state — counts, totals, and above all lookup maps — inside a streamed transform where you can never look backwards.

INPUT workers.xml

Two accumulators: a row counter and a decimal total that grows as each Annual_Salary text node streams past. (The output deliberately reminds you the total mixes USD and GBP — accumulators don't fix data-modelling sins.) A mode only sees accumulators it lists in use-accumulators.

The Workday signature move: an accumulator-built lookup map

Your Studio SSK's MapDemo.xsl pattern: a document contains a lookup section followed by a payload section. Two accumulators cooperate — one pins the most recent Employee_ID as it streams past, the second adds Other_ID → Employee_ID to a map when the sibling arrives. By the time the payload streams past, the map is complete and every payload row can be enriched with an O(1) lookup — one pass, flat memory, no Java. You build exactly this in P10.

§10

Streaming — the copy-of() snapshot pattern

Normally the processor builds the whole source tree in memory — a 2 GB full-file benefits extract can kill the transform. <xsl:mode streamable="yes"/> asks Saxon-EE to process the document as a forward-only stream instead: memory stays flat no matter the file size.

Streaming's price is the streamability rules: roughly, each template may make only one downward-selecting pass ("one consuming expression"), and you can never navigate backwards or sideways (preceding-sibling::, revisiting children twice, sorting the whole input…). Writing fully-streamable logic is hard. The canonical Workday escape hatch makes it easy:

THE PATTERN — STREAM THE LOOP, SNAPSHOT THE ROW
Stream the outer wd:Report_Entry loop forward-only. For each entry, call copy-of(.) — copying that one entry into a small ordinary in-memory tree — and hand it to a non-streamed mode where all XPath is legal again. Memory holds exactly one row at a time. Related: snapshot() does the same but preserves ancestor context (read-only) on the copy — see SSK107 in §18.
INPUT workers.xml

This is transform 01 from your uploaded library, verbatim, producing RFC 4180 CSV (quote-doubling handled by the wd:csv() function). Note the two modes: the streamable default and the named non-streamed in-memory mode that receives the snapshot. On Saxon-HE this runs non-streamed with identical output; under Saxon-EE / the Workday cloud it truly streams.

COMMON STREAMABILITY ERRORS
XTSE3430 ("template rule is not streamable") means a template in a streamable mode breaks the rules — usually two consuming expressions, e.g. reading wd:A and wd:B directly off the streamed node. Fix: snapshot first. And remember position()/last() semantics differ in streamed evaluation — carry counters via xsl:iterate params or accumulators instead.
§11

JSON out — xml-to-json()

REST endpoints, middleware, and Extend orchestrations increasingly want JSON. XSLT 3.0 does it natively: build the small W3C "JSON-XML" vocabulary (fn:map, fn:array, fn:string, fn:number, fn:boolean, fn:null in the http://www.w3.org/2005/xpath-functions namespace), then hand it to xml-to-json(). Escaping, commas, and nesting are the processor's problem, not yours.

INPUT workers.xml

Alternative for map-shaped data: set <xsl:output method="json"/> and let the stylesheet result be an XDM map/array directly. The JSON-XML route shown here is usually more natural when you are already template-matching over XML. xml-to-json() is core 3.0 — it runs on free Saxon-HE, no EE license needed.

§12

JSON in — parse-json(), json-doc(), json-to-xml()

Inbound is the mirror image, and this is where the ? lookup operator earns its keep. parse-json($string) / json-doc($uri) give you XDM maps and arrays you query directly; json-to-xml() instead gives you the JSON-XML vocabulary as a tree you can template-match — better when the JSON is deep and irregular.

INPUT cc_updates.json (via json-doc)

Read the selection out loud: $payload?updates?* — key updates, then every array member; each member is a map, so ?employeeId pulls fields. name="xsl:initial-template" is the 3.0 standard entry point for transforms that start from no XML source. In Studio you would more often receive the JSON as a string and use parse-json().

§13

xsl:try / xsl:catch — quarantine bad rows

Pre-3.0, one unparseable value aborted the whole transform — and with it the integration event. xsl:try scopes the failure to the row, so you can emit an error record (or route to an audit file) and keep going.

INPUT bad_salary.xml

errors="err:FORG0001" catches exactly the cast failure ("invalid value for type"); use errors="*" to catch anything. Inside the catch, $err:code, $err:description, and friends describe the failure. Caution: don't wrap the whole transform in one try — catch at the row boundary so good rows still flow.

§14

for-each-group — the dedup workhorse

Grouping arrived in 2.0, but it is so central to integration hygiene — duplicate detection, change collapsing, one-file-per-company splits — that it earns a chapter next to its 3.0 upgrades (composite="yes" group-by, grouping inside streamed transforms with care).

INPUT comp_dupes.xml

The composite key Employee_ID|Effective_Date is the classic comp-integration dedup key: worker 21001 has two rows for 2026-07-01 (a real duplicate) and one for 2026-08-01 (legitimately distinct). In XSLT 3.0 you can write group-by="wd:Employee_ID, wd:Effective_Date" composite="yes" instead of concatenating with a delimiter. P07 turns this into a full report that also decides which row survives.

§15

Static parameters & shadow attributes — the SSK trick

If you have opened a Workday Studio SSK starter template and wondered what <xsl:include _href="{$sskXsltLibMessage}"/> is — this chapter is the answer.

  • static="yes" on xsl:param makes the parameter available at compile time.
  • An attribute name prefixed with an underscore (_href) is a shadow attribute: its {…} value template is expanded at compile time using static parameters — even on declarations like xsl:include whose real attributes must be fixed.
  • Result: the path of an included library can be injected at runtime. The SSK uses a Studio mediation-context property; locally you flip one commented line to a file:/… path. Static params also drive use-when for compile-time feature switches.
INPUT workers.xml + lib/msglib.xsl

A miniature of the SSK112/SSK147 FunctionLib pattern: the included library contributes ssk:tag(), and which file gets included is decided by the static param. Change $libPath at invocation time — no stylesheet edit — to swap logging/function libraries per environment.
