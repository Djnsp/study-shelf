Learn by solving

Data structures, one problem at a time

A problem-first C++ guide built for short, focused sessions: one problem per sitting, solutions hidden until you're ready, and the Visual Studio debugger as your X-ray machine.

27 problems9 structures3 difficulty levels1 capstone projectVisual Studio workflow

This guide is built around one idea: you learn each data structure by solving problems, not by reading theory for hours. Every section follows the same rhythm so you always know what's next:

  1. How it works — a short, plain-language explanation of what's happening in memory.
  2. Real-world uses — where this structure actually shows up in software you use daily.
  3. Problems (Level 1 → Level 3) — each one slightly harder than the last. Try it for 15–20 minutes before looking at the solution.
  4. Full solutions — with line-by-line plain-language explanations and a note on why the approach is the most efficient one.

How to use this guide for focused, short sessions: - One problem = one session. Don't try to finish a whole section in a sitting. Solving even one Level 1 problem is a complete win. - Type every solution yourself, even when you peek at the answer. Typing it builds memory that reading never will. - Use the Visual Studio debugger (explained below) to watch the data structure change while your code runs. Seeing a linked list pointer move in the Watch window is worth 10 pages of theory. - Follow the order of the sections. Each structure builds on the previous one (e.g., stacks use the ideas from arrays and linked lists; graphs use queues and hash maps).

Sections: Setup → Arrays & Vectors → Strings → Linked Lists → Stacks → Queues & Deques → Hash Tables → Trees & BSTs → Heaps → Graphs → Capstone Mini Project.

Part 0 — Setting Up and Learning in Visual Studio

0.1 Creating your project (do this once)

  1. Open Visual Studio (2022 or newer, Community edition is free). Make sure the "Desktop development with C++" workload is installed (Visual Studio Installer → Modify → check that box).
  2. File → New → Project → "Console App" (C++). Name it something like DSA_Practice.
  3. Visual Studio creates a file with a main() function. This is where your program starts.
  4. Press Ctrl+F5 to build and run without the debugger, or F5 to run with the debugger.

Tip for this guide: keep ONE project, and for each new problem either (a) comment out the old main() code, or (b) create one .cpp file per problem, right-click the files you're not using → Properties → "Excluded From Build" → Yes. Option (b) keeps all your solved problems as a personal library you can revisit.

0.2 The debugger is your data-structure X-ray machine

This is the single most useful habit for learning data structures:

  1. Click in the gray margin to the left of a line of code → a red dot (breakpoint) appears. The program will pause there.
  2. Press F5. When the program pauses:
  3. F10 = run the current line and move to the next (Step Over).
  4. F11 = step into a function call (Step Into).
  5. While paused, look at the Autos / Locals windows (bottom of the screen) — they show every variable's current value.
  6. Open Debug → Windows → Watch → Watch 1 and type a variable name (like head for a linked list, or myVector). Visual Studio shows the structure's contents live, and you can expand pointers with the little arrow to follow a linked list node by node.
  7. For vectors/maps, Visual Studio's "Natvis" visualizers show [size] and each element — expand them and watch elements appear as you push_back in a loop.

Do this for every problem in this guide: put a breakpoint inside your main loop, press F5, then tap F10 repeatedly and watch the structure change. This turns abstract theory into something you can literally see.

0.3 Reading crashes and errors

  • "Access violation reading location..." → you dereferenced a bad pointer (very common with linked lists — usually you walked past nullptr). The debugger stops at the exact line; check your pointer values in Locals (a bad pointer often looks like 0x00000000 = nullptr, or garbage like 0xcccccccc = uninitialized).
  • "vector subscript out of range" → you used an index ≥ size(). Debug builds in Visual Studio catch this for you — one big reason to practice here.
  • Compile errors: double-click the error in the Error List window and Visual Studio jumps to the line.

0.4 Standard file template

Every solution in this guide assumes this at the top:

#include <iostream>
#include <vector>
#include <string>
#include <algorithm>
using namespace std;   // fine for practice; avoid in large production code

Additional headers (<stack>, <queue>, <unordered_map>, etc.) are noted per section.

Part 1 — Arrays & Vectors

How it works

An array is a row of boxes sitting next to each other in memory. If each box holds an int (4 bytes) and the array starts at memory address 1000, then element 0 is at 1000, element 1 at 1004, element 2 at 1008, and so on. Because the position of any element can be calculated (start + index × size), jumping to arr[500] takes the same time as arr[0]. That's called O(1) random access, and it's the array's superpower.

The trade-off: inserting in the middle means shifting everything after it (slow, O(n)), and a plain array can't grow.

std::vector is C++'s resizable array. It secretly keeps a bigger block of memory than it needs; when it runs out, it allocates a block roughly twice as big and copies everything over. Doubling means copies happen rarely, so push_back is O(1) on average ("amortized O(1)").

  • Access by index: O(1)
  • Add/remove at the end: O(1) amortized
  • Insert/remove in the middle: O(n) (shifting)
  • Search unsorted: O(n); search sorted: O(log n) with binary search

Real-world uses

  • Every image on your screen is a 2D array of pixels.
  • Spreadsheet rows, audio samples, video frames — all arrays.
  • Databases and game engines prefer arrays/vectors because contiguous memory is CPU-cache friendly (the CPU pre-loads neighbors, making loops extremely fast).
  • Your Workday-style integration files: a parsed CSV in memory is essentially a vector of rows.

Problem 1.1 (Level 1): Running Sum

Task: Given a vector like {1, 2, 3, 4}, produce a new vector where each element is the sum of everything up to that point: {1, 3, 6, 10}.

Reveal solution 
#include <iostream>
#include <vector>
using namespace std;

vector<int> runningSum(const vector<int>& nums) {
    vector<int> result;
    result.reserve(nums.size());   // pre-allocate space: we know the final size
    int sum = 0;
    for (int x : nums) {           // visit each element left to right
        sum += x;                  // keep a running total
        result.push_back(sum);     // store the total so far
    }
    return result;
}

int main() {
    vector<int> nums = {1, 2, 3, 4};
    vector<int> ans = runningSum(nums);
    for (int x : ans) cout << x << " ";   // prints: 1 3 6 10
}

How it works, in simple language: We walk through the list once, carrying a sum variable like a lunch tray — every element we pass gets added onto the tray, and after each addition we write down the tray's current total. reserve() tells the vector "you'll need exactly this much room," so it never has to stop and re-allocate mid-loop.

Why it's the most efficient way: Each element is touched exactly once → O(n) time, and you can't do better because you must at least read every element. A naive version that re-adds elements 0..i for every i would be O(n²) — 100× slower on a 100-element list.

Debugger exercise: breakpoint on result.push_back(sum);, watch sum and result grow with each F10.

Problem 1.2 (Level 2): Reverse In Place with Two Pointers

Task: Reverse a vector without creating a second vector. {1,2,3,4,5} → {5,4,3,2,1}.

Reveal solution 
void reverseInPlace(vector<int>& nums) {
    int left = 0;                       // finger on the first element
    int right = (int)nums.size() - 1;   // finger on the last element
    while (left < right) {
        swap(nums[left], nums[right]);  // trade the two elements
        left++;                         // move fingers toward the middle
        right--;
    }
}

How it works: Imagine two fingers, one on each end of the row. Swap what's under the fingers, then walk both fingers one step toward the center. When the fingers meet (or cross), everything has been mirrored. This "two pointers" pattern is one of the most reused tricks in all of programming — it comes back in strings, linked lists, and sorting problems.

Why it's the most efficient way: n/2 swaps → O(n) time, and O(1) extra memory (just two ints), versus O(n) extra memory if you copied into a new vector. In-place algorithms matter when data is huge.

Problem 1.3 (Level 3): Maximum Subarray Sum (Kadane's Algorithm)

Task: Given {-2, 1, -3, 4, -1, 2, 1, -5, 4}, find the largest sum of any contiguous chunk. (Answer: {4,-1,2,1} → 6.)

Reveal solution 
int maxSubArray(const vector<int>& nums) {
    int best = nums[0];      // best sum found anywhere so far
    int current = nums[0];   // best sum of a chunk ENDING right here
    for (size_t i = 1; i < nums.size(); i++) {
        // Either extend the previous chunk, or start fresh at nums[i] —
        // whichever gives a bigger value.
        current = max(nums[i], current + nums[i]);
        best = max(best, current);
    }
    return best;
}

How it works: Walk the list once asking one question at each step: "Is the chunk I've been carrying helping me, or hurting me?" If the running chunk's sum has gone negative, dragging it along only makes future sums worse — so we drop it and start a fresh chunk. best remembers the highest value current ever reached.

Why it's the most efficient way: One pass, O(n) time, O(1) memory. The brute-force approach (try every start and end position) is O(n²) or O(n³). Kadane's algorithm is also your first taste of dynamic programming: solving a big problem by carrying forward the answer to a smaller version of it.

Part 2 — Strings

How it works

A std::string is basically a vector<char> with text-friendly helpers. Same memory story: characters sit side by side, indexing is O(1), appending is amortized O(1), inserting in the middle is O(n). One extra wrinkle: characters are numbers under the hood ('a' is 97, 'b' is 98 in ASCII), which lets you do arithmetic like c - 'a' to turn a letter into an index 0–25 — a trick used constantly.

Real-world uses

  • Every search box, URL parser, and compiler tokenizer is string processing.
  • XSLT/XML transformation work (very relevant to integration development) is heavy string parsing.
  • DNA sequence analysis, spam filtering, autocomplete — all string algorithms.

Problem 2.1 (Level 1): Is It a Palindrome?

Task: Return true if a string reads the same forwards and backwards ("racecar" → true, "hello" → false). Ignore nothing — exact match version.

Reveal solution 
bool isPalindrome(const string& s) {
    int left = 0, right = (int)s.size() - 1;
    while (left < right) {
        if (s[left] != s[right]) return false;  // mismatch = not a palindrome
        left++;
        right--;
    }
    return true;   // fingers met without any mismatch
}

How it works: The same two-finger walk from Problem 1.2 — but instead of swapping, we compare. First letter vs last letter, second vs second-to-last. Any mismatch ends it immediately.

Why it's the most efficient way: O(n) time, O(1) memory, and it exits early on the first mismatch. The tempting alternative — build a reversed copy and compare — also works but costs O(n) extra memory for no benefit.

Problem 2.2 (Level 2): First Non-Repeating Character

Task: In "swiss", find the first character that appears exactly once (answer: 'w').

Reveal solution 
char firstUnique(const string& s) {
    int counts[26] = {0};              // one counter box per letter a–z

    for (char c : s)                   // pass 1: count every letter
        counts[c - 'a']++;

    for (char c : s)                   // pass 2: first letter whose count is 1
        if (counts[c - 'a'] == 1) return c;

    return '\0';                       // no unique character found
}

How it works: Picture 26 tally boxes labeled a–z. First pass: walk the string and put a tick in each letter's box. Second pass: walk the string again in original order and return the first letter whose box holds exactly one tick. The second pass must go through the string (not the boxes) because the question asks for the first unique character in the string's order.

Why it's the most efficient way: Two passes = O(n) time, and the counting array is fixed-size O(1) memory. The naive way — for each character, scan the whole string to count it — is O(n²). This "counting array" idea is a mini hash table, previewing Part 6.

Problem 2.3 (Level 3): Valid Anagram Groups Warm-up — Are Two Strings Anagrams?

Task: "listen" and "silent" use exactly the same letters → true. "hello"/"world" → false.

Reveal solution 
bool isAnagram(const string& a, const string& b) {
    if (a.size() != b.size()) return false;  // different lengths can't match

    int counts[26] = {0};
    for (char c : a) counts[c - 'a']++;      // add ticks for string a
    for (char c : b) counts[c - 'a']--;      // remove ticks for string b

    for (int n : counts)
        if (n != 0) return false;            // any imbalance = not anagrams
    return true;
}

How it works: Same 26 tally boxes. String a deposits ticks, string b withdraws them. If the two strings are perfect rearrangements of each other, every box ends at exactly zero — every deposit was matched by a withdrawal.

Why it's the most efficient way: O(n) time, O(1) space. The common alternative — sort both strings and compare — is O(n log n) and modifies/copies the data. Counting wins whenever the "alphabet" is small and known.

Part 3 — Linked Lists

How it works

A linked list gives up the array's "boxes side by side" layout. Instead, each element is a little package (a node) floating anywhere in memory, containing two things: the data, and the address of the next node (a pointer). The list is held together like a treasure hunt — each clue tells you where the next clue lives. You only ever hold the address of the first node (the head); everything else is reached by following next pointers.

struct Node {
    int data;
    Node* next;
    Node(int d) : data(d), next(nullptr) {}
};
  • Insert/remove at the front: O(1) — just rewire one pointer. This is what arrays are terrible at.
  • Access element #k: O(k) — no address math possible; you must walk the chain.
  • Memory: each node costs an extra pointer, and nodes scattered in memory are cache-unfriendly.

Rule of thumb: vectors win most of the time in real code; linked lists win when you constantly insert/remove at the ends or middle while already standing at that spot, and they're the concept behind many bigger structures (queues, hash-table buckets, adjacency lists).

Real-world uses

  • The Undo history in editors, browser back/forward chains, music playlists with next/previous.
  • OS schedulers keep processes in linked queues.
  • Hash tables (Part 6) classically use linked lists to handle collisions.
  • Blockchain is conceptually a linked list where "next" is a cryptographic hash.

Problem 3.1 (Level 1): Build a List and Print It

Task: Turn {1,2,3} into the chain 1 → 2 → 3 → nullptr and print it.

Reveal solution 
#include <iostream>
#include <vector>
using namespace std;

struct Node {
    int data;
    Node* next;
    Node(int d) : data(d), next(nullptr) {}
};

Node* buildList(const vector<int>& values) {
    Node* head = nullptr;              // start with an empty chain
    Node* tail = nullptr;              // pointer to the last node built
    for (int v : values) {
        Node* n = new Node(v);         // create the node on the heap
        if (!head) {                   // first node: it is both head and tail
            head = tail = n;
        } else {
            tail->next = n;            // hook it onto the end of the chain
            tail = n;                  // and it becomes the new tail
        }
    }
    return head;
}

void printList(Node* head) {
    for (Node* cur = head; cur != nullptr; cur = cur->next)
        cout << cur->data << " -> ";
    cout << "null\n";
}

void freeList(Node* head) {            // always clean up heap memory
    while (head) {
        Node* nxt = head->next;
        delete head;
        head = nxt;
    }
}

int main() {
    Node* head = buildList({1, 2, 3});
    printList(head);                   // 1 -> 2 -> 3 -> null
    freeList(head);
}

How it works: We keep two bookmarks: head (never moves after the first node — it's how we find the list later) and tail (always the last node, so attaching a new node is instant instead of walking the whole chain each time). Printing is the classic traversal loop: start at head, keep hopping cur = cur->next until you fall off the end (nullptr).

Why it's the most efficient way: Keeping a tail pointer makes building the list O(n) total. Without it, you'd re-walk the list for every insertion → O(n²).

Debugger exercise (do this one!): breakpoint on tail->next = n;, add head to the Watch window, and expand next arrows after each F10 — you'll literally watch the chain grow link by link.

Problem 3.2 (Level 2): Reverse a Linked List

Task: 1 → 2 → 3 → null becomes 3 → 2 → 1 → null. The most famous interview question in existence.

Reveal solution 
Node* reverseList(Node* head) {
    Node* prev = nullptr;     // the part already reversed (starts empty)
    Node* cur  = head;        // the node we're processing now
    while (cur) {
        Node* nxt = cur->next; // 1. save where we were going next
        cur->next = prev;      // 2. flip this node's arrow backwards
        prev = cur;            // 3. this node joins the reversed part
        cur  = nxt;            // 4. move on using the saved address
    }
    return prev;              // prev is the new head
}

How it works: Walk the chain flipping each arrow to point backwards. The danger: the moment you flip a node's arrow, you've destroyed your only route forward — so step 1 saves the forward address before step 2 flips the arrow. Three pointers march down the list together: prev (done), cur (working on), nxt (saved escape route).

Why it's the most efficient way: One pass, O(n) time, O(1) memory — we only rewire pointers, never copy data. Alternatives like copying values into a vector and rebuilding cost O(n) extra memory.

Problem 3.3 (Level 3): Detect a Cycle (Floyd's Tortoise & Hare)

Task: If a list's last node secretly points back to an earlier node, traversal loops forever. Detect this without extra memory.

Reveal solution 
bool hasCycle(Node* head) {
    Node* slow = head;                     // moves 1 step at a time
    Node* fast = head;                     // moves 2 steps at a time
    while (fast && fast->next) {
        slow = slow->next;
        fast = fast->next->next;
        if (slow == fast) return true;     // they met: must be a loop
    }
    return false;                          // fast fell off the end: no loop
}

How it works: Two runners on the same track. If the track is a straight road, the fast runner reaches the end and it's over. If the track contains a loop, both runners eventually end up inside it — and a runner gaining one position per step on a circular track must eventually lap the slow one and land on the same node. Meeting = cycle.

Why it's the most efficient way: O(n) time and O(1) memory. The obvious alternative — remember every visited node in a hash set — also works in O(n) time but costs O(n) memory. Floyd's trick removes the memory cost entirely.

Part 4 — Stacks

How it works

A stack is a rule, not a memory layout: Last In, First Out (LIFO). Like a stack of plates — you can only add to the top (push) and take from the top (pop). You never reach into the middle. C++ gives you std::stack (#include <stack>), which is a thin wrapper over a deque or vector.

  • push, pop, top: all O(1).

The magic of stacks: they naturally remember "what was I in the middle of?" — perfect for anything nested or reversible.

Real-world uses

  • The call stack: every function call in every program pushes a frame; returning pops it. (Stack overflow = you pushed too many.)
  • Undo/Redo (each action pushed; undo pops).
  • Browser back button, matching brackets in your IDE, evaluating expressions in compilers and calculators.
  • Depth-first search (Part 9) is "explore using a stack."

Problem 4.1 (Level 1): Reverse a String Using a Stack

Task: Use a stack to reverse "hello" → "olleh".

Reveal solution 
#include <stack>
#include <string>
using namespace std;

string reverseWithStack(const string& s) {
    stack<char> st;
    for (char c : s) st.push(c);   // pile the letters up: h,e,l,l,o (o on top)

    string out;
    out.reserve(s.size());
    while (!st.empty()) {
        out.push_back(st.top());   // read the top letter...
        st.pop();                  // ...then remove it
    }
    return out;                    // letters come off in reverse order
}

How it works: Pushing letters piles them up with the last letter on top; popping then hands them back newest-first. Any LIFO container reverses order for free — that's the takeaway, not the reversal itself (Problem 1.2's two-pointer swap is the leaner way to actually reverse).

Why this exercise matters: it burns in the LIFO behavior with something you can print and verify instantly. Note top() and pop() are separate calls in C++ — pop() returns nothing (a deliberate design choice for exception safety).

Problem 4.2 (Level 2): Valid Brackets

Task: Is "{[()]}" properly nested? ("{[(])}" is not.) This is exactly what your IDE does as you type.

Reveal solution 
bool isValid(const string& s) {
    stack<char> st;
    for (char c : s) {
        if (c == '(' || c == '[' || c == '{') {
            st.push(c);                          // remember every opener
        } else {
            if (st.empty()) return false;        // closer with nothing open
            char open = st.top(); st.pop();      // most recent opener
            if ((c == ')' && open != '(') ||
                (c == ']' && open != '[') ||
                (c == '}' && open != '{'))
                return false;                    // wrong closer type
        }
    }
    return st.empty();   // leftovers mean unclosed openers
}

How it works: Openers get pushed as promises ("I owe you a closing brace"). Every closer must pay off the most recent unpaid promise — which is exactly what top() holds, because nesting is LIFO by nature: the last thing opened must be the first thing closed. Three failure modes: closer with an empty stack, closer of the wrong type, and openers left over at the end.

Why it's the most efficient way: One pass, O(n) time, O(n) worst-case stack space. There is no way to validate nesting without remembering unclosed openers, and a stack remembers exactly that and nothing more.

Problem 4.3 (Level 3): Min Stack

Task: Design a stack that can also report its minimum element in O(1) at any moment.

Reveal solution 
class MinStack {
    stack<int> data;   // the real values
    stack<int> mins;   // mins.top() = smallest value in data right now
public:
    void push(int x) {
        data.push(x);
        if (mins.empty() || x <= mins.top())
            mins.push(x);          // new minimum takes the throne
    }
    void pop() {
        if (data.top() == mins.top())
            mins.pop();            // the current minimum is leaving
        data.pop();
    }
    int top()    { return data.top(); }
    int getMin() { return mins.top(); }
};

How it works: A second "shadow" stack records the reigning minimum. When a new value is pushed, it joins the shadow stack only if it ties or beats the current champion. When the champion itself is popped from the real stack, it's popped from the shadow stack too — automatically re-crowning the previous champion. The shadow stack's top is therefore always the minimum of what remains.

Why it's the most efficient way: All four operations are O(1). The naive getMin — scan the whole stack — is O(n) per call. We're trading a little memory for a lot of speed, one of the most common engineering trades there is.

Part 5 — Queues & Deques

How it works

A queue is the opposite rule: First In, First Out (FIFO) — a checkout line. Add at the back (push), serve from the front (pop). C++: std::queue (#include <queue>). A deque ("deck", double-ended queue, #include <deque>) allows O(1) add/remove at both ends.

  • push, pop, front, back: all O(1).

Real-world uses

  • Print job queues, message queues (Kafka/RabbitMQ/Azure Service Bus — the backbone of enterprise integrations), keyboard input buffers.
  • CPU task scheduling, call-center hold lines, streaming buffers.
  • Breadth-first search (Part 9) is "explore using a queue" — how GPS finds shortest routes.

Problem 5.1 (Level 1): Ticket Counter Simulation

Task: People arrive as {"Ana","Ben","Che"}; serve them in arrival order, printing each.

Reveal solution 
#include <queue>
#include <string>
#include <iostream>
using namespace std;

void serveCustomers(const vector<string>& arrivals) {
    queue<string> line;
    for (const string& name : arrivals)
        line.push(name);                       // join the back of the line

    while (!line.empty()) {
        cout << "Now serving: " << line.front() << "\n";
        line.pop();                            // they leave the front
    }
}

How it works: Exactly a real line: first to arrive is first served. front() peeks at who's next; pop() removes them. Compare with Problem 4.1 — identical code shape, but swapping the stack for a queue changes the output order from reversed to original. That contrast is the whole lesson of Parts 4 and 5.

Problem 5.2 (Level 2): Implement a Queue Using Two Stacks

Task: Build FIFO behavior using only LIFO stacks. A classic "do you really understand both?" test.

Reveal solution 
class QueueFromStacks {
    stack<int> inbox;    // where new arrivals land
    stack<int> outbox;   // where departures leave from
    void transferIfNeeded() {
        if (outbox.empty()) {              // only when outbox runs dry
            while (!inbox.empty()) {
                outbox.push(inbox.top());  // pour inbox into outbox,
                inbox.pop();               // which reverses the order
            }
        }
    }
public:
    void push(int x) { inbox.push(x); }
    int pop() {
        transferIfNeeded();
        int v = outbox.top();
        outbox.pop();
        return v;
    }
    int front() { transferIfNeeded(); return outbox.top(); }
    bool empty() { return inbox.empty() && outbox.empty(); }
};

How it works: One stack reversal turns order backwards; two reversals restore it. New items pile into inbox (newest on top — wrong order for a queue). When someone must leave, we pour inbox into outbox, flipping it so the oldest item sits on top — exactly FIFO. Crucially, we only pour when outbox is empty, so items already in correct order aren't disturbed.

Why it's the most efficient way: Each element is pushed and popped at most twice in its lifetime, so operations are amortized O(1) — pouring is rare, not per-call. A version that transfers on every operation would be O(n) per call.

Problem 5.3 (Level 3): Sliding Window Maximum (Monotonic Deque)

Task: For {1,3,-1,-3,5,3,6,7} and window size 3, output the max of each window: {3,3,5,5,6,7}.

Reveal solution 
#include <deque>

vector<int> maxSlidingWindow(const vector<int>& nums, int k) {
    deque<int> dq;            // stores INDEXES; values at those indexes
                              // are kept in decreasing order
    vector<int> result;
    for (int i = 0; i < (int)nums.size(); i++) {
        // 1. Evict the index that slid out of the window's left edge
        if (!dq.empty() && dq.front() <= i - k)
            dq.pop_front();
        // 2. New value kicks out everything smaller than it (from the back)
        while (!dq.empty() && nums[dq.back()] <= nums[i])
            dq.pop_back();
        dq.push_back(i);
        // 3. Front of deque = index of the window's maximum
        if (i >= k - 1)
            result.push_back(nums[dq.front()]);
    }
    return result;
}

How it works: The deque is a VIP list of "candidates who could still be a window maximum," kept in decreasing value order. When a new number arrives, anyone smaller than it can never be a future maximum (the newcomer is bigger AND will stay in the window longer) — so they're ejected from the back. Numbers that expire out of the window's left edge are ejected from the front. The front survivor is always the current champion.

Why it's the most efficient way: Every index enters and leaves the deque at most once → O(n) total. The obvious approach — rescan each window for its max — is O(n·k). For a million prices with a 10,000-wide window, that's the difference between instant and minutes. This exact pattern powers real-time monitoring dashboards ("max latency in the last 60 seconds").

Part 6 — Hash Tables (unordered_map / unordered_set)

How it works

A hash table answers "have I seen this before?" and "what's stored under this key?" in O(1) average time. The trick:

  1. A hash function turns your key ("apple") into a big number.
  2. number % table_size picks a bucket (a slot in an internal array).
  3. The value is stored in that bucket. Lookup repeats the same math and jumps straight there — no searching.

Two keys can land in the same bucket (a collision); the standard fix is a tiny linked list per bucket (see — Part 3 pays off). When buckets get crowded, the table grows and re-distributes ("rehashes"), just like vector doubling.

C++: unordered_map<Key, Value> (dictionary) and unordered_set<Key> (membership only). Both in #include <unordered_map> / <unordered_set>.

  • Insert / lookup / erase: O(1) average, O(n) pathological worst case.
  • Trade-off: no ordering. If you need sorted traversal, use map (a red-black tree, O(log n), Part 7's cousin).

Real-world uses

  • Database indexes, caches (Redis is essentially a giant hash table), session stores.
  • Compilers' symbol tables, spell-checker dictionaries, deduplication.
  • Counting anything: word frequencies, votes, page hits.
  • In integration work: keyed lookups like "employee ID → record" while merging two files — the difference between an O(n²) nested-loop merge and an O(n) hash-join.

Problem 6.1 (Level 1): Word Frequency Counter

Task: Count how many times each word appears in {"apple","banana","apple","cherry","banana","apple"}.

Reveal solution 
#include <unordered_map>
#include <string>
#include <iostream>
using namespace std;

void countWords(const vector<string>& words) {

    for (const string& w : words)
        freq[w]++;    // if w is new, it's auto-created with 0, then ++ makes it 1

How it works: freq[w]++ does three things in one stroke: hash the word, find (or create) its slot, and bump the counter. This one-liner is probably the most typed line in practical programming.

Problem 6.2 (Level 2): Two Sum

Task: In {2, 7, 11, 15} with target 9, find the two indexes whose values add to the target (answer: 0 and 1). The single most famous programming problem on the internet.

Reveal solution 
vector<int> twoSum(const vector<int>& nums, int target) {
    unordered_map<int, int> seen;   // value -> index where we saw it
    for (int i = 0; i < (int)nums.size(); i++) {
        int need = target - nums[i];        // the partner we're looking for
        auto it = seen.find(need);
        if (it != seen.end())
            return { it->second, i };       // partner was seen earlier: done
        seen[nums[i]] = i;                  // remember me for future partners
    }
    return {};   // no pair exists
}

How it works: Walk the list once. For each number, compute its required partner (target − me) and ask the hash map "has that partner already walked past?" If yes, finished. If no, register myself so a future number can find me. Every number is simultaneously a searcher and a potential answer.

Why it's the most efficient way: One pass, O(n) time, O(n) space. Brute force checks all pairs: O(n²). The pattern — "check the map, then add yourself to the map" — solves dozens of problems and is worth memorizing as a reflex.

Problem 6.3 (Level 3): Longest Consecutive Sequence

Task: In {100, 4, 200, 1, 3, 2}, the longest run of consecutive integers is 1,2,3,4 → length 4. Do it in O(n), unsorted.

Reveal solution 
#include <unordered_set>

int longestConsecutive(const vector<int>& nums) {
    unordered_set<int> s(nums.begin(), nums.end());  // O(1) membership checks
    int best = 0;
    for (int x : s) {
        if (s.count(x - 1)) continue;   // x has a left neighbor:
                                        // not the START of a run, skip it
        int length = 1;                 // x starts a run; walk it upward
        while (s.count(x + length)) length++;
        best = max(best, length);
    }
    return best;
}

How it works: Dump everything into a set so "does 5 exist?" is instant. Then the clever part: only count a run starting from its leftmost number (a number with no x−1 present). That guarantees each run is walked exactly once from its true beginning, instead of being re-walked from every member.

Why it's the most efficient way: Despite the nested-looking loops, every number is visited at most twice → O(n). Sorting first would give O(n log n). The start-detection guard (if (s.count(x-1)) continue;) is the entire trick — remove it and the algorithm silently degrades to O(n²).

Part 7 — Trees & Binary Search Trees

How it works

A tree is a linked structure where each node points downward to children instead of sideways to one next. A binary tree allows at most two children (left, right). Top node = root; childless nodes = leaves.

A Binary Search Tree (BST) adds one ordering rule: everything in a node's left subtree is smaller; everything in its right subtree is bigger. That rule turns every lookup into a game of "higher or lower": each comparison discards half the remaining tree.

struct TreeNode {
    int val;
    TreeNode *left, *right;
    TreeNode(int v) : val(v), left(nullptr), right(nullptr) {}
};
  • Search / insert / delete in a balanced BST: O(log n) — 1,000,000 items in ~20 steps.
  • Worst case (inserting sorted data creates a "vine"): O(n). Self-balancing variants (red-black trees — what std::map/std::set use internally) guarantee O(log n).
  • In-order traversal (left → node → right) of a BST visits values in sorted order — a beautiful, exam-favorite fact.

Trees are also where recursion becomes natural: a tree is "a node plus two smaller trees," so most tree algorithms are five lines that call themselves.

Real-world uses

  • File systems (folders in folders), HTML/XML DOM (every web page and every XML integration payload is a tree), JSON documents.
  • Database indexes (B-trees — fat BSTs tuned for disks), std::map/std::set.
  • Org charts, decision trees in ML, compiler syntax trees.

Problem 7.1 (Level 1): Insert & In-Order Print

Task: Insert {50, 30, 70, 20, 40, 60, 80} into a BST, then print in-order (should come out sorted).

Reveal solution 
TreeNode* insert(TreeNode* root, int v) {
    if (!root) return new TreeNode(v);   // empty spot found: plant here
    if (v < root->val)
        root->left = insert(root->left, v);    // smaller: go left
    else
        root->right = insert(root->right, v);  // bigger: go right
    return root;                         // hand the (unchanged) node back up
}

void inorder(TreeNode* root) {
    if (!root) return;        // fell off the tree: nothing to do
    inorder(root->left);      // 1. everything smaller first
    cout << root->val << " "; // 2. then me
    inorder(root->right);     // 3. then everything bigger
}

int main() {
    TreeNode* root = nullptr;
    for (int v : {50, 30, 70, 20, 40, 60, 80})
        root = insert(root, v);
    inorder(root);            // prints: 20 30 40 50 60 70 80
}

How it works: Insertion plays higher/lower down from the root until it falls off the tree — that empty spot is exactly where the value belongs, and new TreeNode(v) plants it there. The return root line re-attaches each node to its parent as the recursion unwinds. In-order traversal prints "all smaller things, me, all bigger things" — applied recursively, that is sorted order.

Why it's efficient: Each insert follows one root-to-leaf path: O(log n) when balanced. In-order visits each node once: O(n) — you can't print n things faster.

Debugger exercise: F11 (Step Into) through inorder and watch the Call Stack window grow and shrink — recursion made visible. This is the best recursion intuition-builder there is.

Problem 7.2 (Level 2): Max Depth of a Tree

Task: Return how many levels deep the tree goes.

Reveal solution 
int maxDepth(TreeNode* root) {
    if (!root) return 0;                    // an empty tree has depth 0
    int leftDepth  = maxDepth(root->left);
    int rightDepth = maxDepth(root->right);
    return 1 + max(leftDepth, rightDepth);  // me + my taller child
}

How it works: Ask each subtree "how deep are you?", trust the answers, take the taller one, and add 1 for yourself. The recursion bottoms out at empty branches, which report 0. This "trust the recursive call and combine" shape is the template for a huge share of tree problems: count nodes (1 + left + right), sum values, check balance — all the same skeleton.

Why it's efficient: Each node answers exactly once → O(n). No faster way exists, since depth could hide anywhere.

Problem 7.3 (Level 3): Validate a BST

Task: Check that a binary tree truly obeys the BST rule everywhere. Trap: checking only left->val < val < right->val at each node is not enough — a grandchild can violate a grandparent's rule.

Reveal solution 
#include <climits>

bool validate(TreeNode* root, long low, long high) {
    if (!root) return true;                        // empty = trivially valid
    if (root->val <= low || root->val >= high)
        return false;                              // outside allowed window
    return validate(root->left,  low, root->val)   // left: ceiling tightens
        && validate(root->right, root->val, high); // right: floor tightens
}

bool isValidBST(TreeNode* root) {
    return validate(root, LONG_MIN, LONG_MAX);
}

How it works: Every node lives inside an allowed window (low, high) inherited from all its ancestors. The root can be anything. Going left says "you must stay below me," shrinking the ceiling; going right raises the floor. A node like 55 hiding in the left subtree of 50 gets caught because its inherited window is (−∞, 50) — even if its immediate parent is fine with it.

Why it's the most efficient way: One visit per node, O(n). The window-passing technique — carrying constraints down the recursion — is a major tree pattern. (Alternative with the same cost: in-order traverse and confirm the output is strictly increasing, using Part 7.1's sorted-order fact.)

Part 8 — Heaps & Priority Queues

How it works

A heap answers one question extremely fast: "what's the most important item right now?" A max-heap keeps the largest on top; a min-heap the smallest. It's a binary tree with two rules:

  1. Heap rule: every parent outranks its children. (Only parent↔child — siblings are unordered. A heap is NOT a sorted structure.)
  2. Shape rule: the tree fills level by level, left to right — which lets it live inside a plain vector with zero pointers: for the node at index i, children are at 2i+1 and 2i+2, parent at (i−1)/2. Array math instead of pointer-chasing — arrays strike again.

Insert: drop at the end, bubble up while beating your parent. Remove top: move the last element to the top, sink down swapping with your stronger child. Both walk one root-leaf path → O(log n); peeking at the top is O(1).

C++: priority_queue<int> (max-heap) in #include <queue>; min-heap: priority_queue<int, vector<int>, greater<int>>.

Real-world uses

  • OS schedulers ("highest-priority process next"), hospital triage, airline standby lists.
  • Dijkstra's shortest path (the capstone project!) — "which unvisited station is currently cheapest?"
  • Event simulation, bandwidth management, "Top 10" leaderboards over massive streams.

Problem 8.1 (Level 1): Hospital Triage

Task: Patients arrive with severity scores {3, 9, 1, 7}. Always treat the most severe first.

Reveal solution 
#include <queue>

int main() {
    priority_queue<int> triage;              // max-heap: biggest on top
    for (int severity : {3, 9, 1, 7})
        triage.push(severity);

    while (!triage.empty()) {
        cout << "Treating severity " << triage.top() << "\n";
        triage.pop();
    }   // prints 9, 7, 3, 1
}

How it works: No matter what order patients arrive, top() always holds the current maximum, because every push/pop repairs the parent-beats-child rule along one path. Compare with Parts 4–5: stack = newest first, queue = oldest first, priority queue = most important first. Three containers, three definitions of "next."

Why it's efficient: Each push/pop is O(log n). Keeping a sorted vector instead would make insertion O(n) — the heap deliberately stays "just organized enough," and that laziness is what makes it fast.

Problem 8.2 (Level 2): Kth Largest Element in a Stream

Task: Numbers arrive endlessly; after each arrival, report the k-th largest so far.

Reveal solution 
class KthLargest {
    priority_queue<int, vector<int>, greater<int>> minHeap; // smallest on top
    int k;
public:
    KthLargest(int k) : k(k) {}
    int add(int val) {
        minHeap.push(val);
        if ((int)minHeap.size() > k)
            minHeap.pop();          // evict the smallest of the k+1
        return minHeap.top();       // smallest of the top-k = k-th largest
    }
};

How it works: The counter-intuitive move: to track the k largest, use a min-heap capped at size k. The heap is a VIP room holding the k biggest values seen; its top is the weakest VIP — i.e., exactly the k-th largest. Each newcomer enters, and if the room exceeds k, the weakest is bounced in O(log k).

Why it's the most efficient way: O(log k) per arrival with O(k) memory — independent of how many millions of values stream past. Re-sorting on every arrival is O(n log n) each time and requires storing everything. This "size-capped opposite-heap" is the pattern for every Top-K problem (trending topics, top spenders, hottest products).

Problem 8.3 (Level 3): Merge K Sorted Lists (vectors version)

Task: Merge {{1,4,5}, {1,3,4}, {2,6}} into one sorted list.

Reveal solution 
struct Item {
    int value, listIdx, elemIdx;
    bool operator>(const Item& o) const { return value > o.value; }
};

vector<int> mergeK(const vector<vector<int>>& lists) {
    priority_queue<Item, vector<Item>, greater<Item>> heap;

    for (int i = 0; i < (int)lists.size(); i++)         // seed: each list's
        if (!lists[i].empty())                          // first element
            heap.push({lists[i][0], i, 0});

    vector<int> result;
    while (!heap.empty()) {
        Item cur = heap.top(); heap.pop();
        result.push_back(cur.value);                    // overall smallest
        int nextIdx = cur.elemIdx + 1;
        if (nextIdx < (int)lists[cur.listIdx].size())   // that list sends up
            heap.push({lists[cur.listIdx][nextIdx],     // its next element
                       cur.listIdx, nextIdx});
    }
    return result;
}

How it works: Picture k conveyor belts, each already sorted. Only the front item of each belt can possibly be the overall next-smallest, so the heap holds just those k candidates. Take the winner, and its belt advances one item into the heap. Each Item remembers which belt (listIdx) and position (elemIdx) it came from so we know whose turn advances.

Why it's the most efficient way: n total elements each pass through a size-k heap once → O(n log k). Concatenate-then-sort is O(n log n) — noticeably worse when k is small and n is huge. This is literally how databases do multi-way merge joins and how external sorting merges chunks too big for RAM. It also exercises three parts at once: structs, heaps with custom comparison, and index bookkeeping.

Part 9 — Graphs

How it works

A graph is the most general structure of all: things (nodes/vertices) plus connections between them (edges). Unlike trees, connections can go anywhere — cycles allowed, multiple routes allowed. Edges can be one-way (directed) or two-way (undirected), and can carry costs (weighted), like travel minutes between stations.

The standard in-memory representation is the adjacency list: for every node, a list of its neighbors. In modern C++ that's usually:

unordered_map<string, vector<string>> graph;         // unweighted
unordered_map<string, vector<pair<string,int>>> g;   // weighted: (neighbor, cost)

Notice: it's a hash map of vectors — Parts 1 and 6 stacked together. Bigger structures are always built from smaller ones.

The two fundamental algorithms are just Part 4 and Part 5 wearing hats:

  • BFS (Breadth-First Search) = explore with a queue → visits nodes ring by ring by distance → finds shortest paths when every edge counts as 1.
  • DFS (Depth-First Search) = explore with a stack (or recursion, which uses the call stack) → dives deep before backtracking → great for "is this reachable?", connected components, cycle detection.

Both are O(V + E) — each node and edge is touched once. Both need a visited set (Part 6 again) or cycles cause infinite loops.

Real-world uses

  • Google Maps (cities + roads), social networks (people + friendships), the internet itself (routers + links).
  • Dependency resolution: build systems, package managers, and integration job chains ("run B only after A") are directed graphs.
  • Recommendation engines ("people who bought X…"), fraud-ring detection, airline routing.

Problem 9.1 (Level 1): Build a Graph and List Neighbors

Task: Model friendships: Ana–Ben, Ana–Che, Ben–Dev. Print everyone's friends.

Reveal solution 
#include <unordered_map>
#include <vector>
#include <string>
using namespace std;

int main() {
    unordered_map<string, vector<string>> graph;
    auto addFriend = [&](const string& a, const string& b) {
        graph[a].push_back(b);   // undirected: record the edge
        graph[b].push_back(a);   // in BOTH directions
    };

    addFriend("Ana", "Che");
    addFriend("Ben", "Dev");

}

How it works: Each person's map entry holds their contact list. Friendship goes both ways, so one addFriend writes two entries. That's the whole thing — a graph is just this lookup table; all the famous algorithms are ways of walking it.

Why adjacency lists are the efficient choice: memory is O(V + E) — only real connections are stored. The alternative (an adjacency matrix, a V×V grid of yes/no) costs O(V²) even when nearly empty: a million users with ~200 friends each would need a trillion-cell matrix vs. ~200M list entries.

Problem 9.2 (Level 2): Shortest Path Hop Count with BFS

Task: Fewest friendship hops from "Ana" to "Dev" (answer: 2 — Ana → Ben → Dev).

Reveal solution 
#include <queue>
#include <unordered_set>

int shortestHops(unordered_map<string, vector<string>>& graph,
                 const string& start, const string& goal) {
    queue<pair<string,int>> q;       // (person, distance from start)
    unordered_set<string> visited;
    q.push({start, 0});
    visited.insert(start);

    while (!q.empty()) {
        auto [person, dist] = q.front(); q.pop();
        if (person == goal) return dist;
        for (const string& next : graph[person]) {
            if (!visited.count(next)) {
                visited.insert(next);        // mark BEFORE queueing:
                q.push({next, dist + 1});    // prevents duplicates in queue
            }
        }
    }
    return -1;   // unreachable
}

How it works: BFS explores like a ripple in a pond: first everyone 1 hop away, then everyone 2 hops away, and so on — the queue's FIFO order enforces this ring-by-ring sweep. Because rings are processed in increasing distance, the first time you reach the goal is guaranteed to be via a shortest route. The visited set stops us from circling (Ana → Ben → Ana → …).

Why it's the most efficient way: O(V + E), touching each person and friendship once. Note the details that separate correct BFS from buggy BFS: mark visited when queueing (not when popping), and carry the distance inside the queue.

Problem 9.3 (Level 3): Course Schedule — Cycle Detection with DFS

Task: Courses with prerequisites: can you finish them all? Impossible exactly when prerequisites form a cycle (A needs B, B needs A).

Reveal solution 
// state: 0 = never visited, 1 = currently being explored, 2 = fully done
bool hasCycleFrom(int node, vector<vector<int>>& adj, vector<int>& state) {
    state[node] = 1;                        // I'm on the current DFS path
    for (int next : adj[node]) {
        if (state[next] == 1) return true;  // reached someone on my own
                                            // path: that's a loop!
        if (state[next] == 0 &&
            hasCycleFrom(next, adj, state)) return true;
    }
    state[node] = 2;                        // finished; I'm proven safe
    return false;
}

bool canFinish(int numCourses, vector<pair<int,int>>& prereqs) {
    vector<vector<int>> adj(numCourses);
    for (auto& [course, needs] : prereqs)
        adj[needs].push_back(course);       // edge: prerequisite -> course

    vector<int> state(numCourses, 0);
    for (int c = 0; c < numCourses; c++)
        if (state[c] == 0 && hasCycleFrom(c, adj, state))
            return false;
    return true;
}

How it works: DFS dives down a chain of prerequisites, marking each node "1 = I'm currently standing on this path." If the dive runs into a node already marked 1, the path has looped back onto itself — a cycle. Nodes marked "2" have been fully explored and certified cycle-free, so future dives skip them instantly. The three states are the key: plain visited/unvisited can't tell "on my current path" (cycle!) apart from "explored earlier via another route" (harmless).

Why it's the most efficient way: O(V + E) — the state-2 shortcut ensures no node is ever fully explored twice. This exact algorithm is inside build tools, package managers, spreadsheet formula engines (circular reference detection), and integration schedulers.

    // hands us the unfinished station with the smallest known time.
    vector<string> fastestRoute(const string& start, const string& goal,
                                int& totalMinutes) const {
        unordered_map<string, int> dist;      // best known minutes so far
        unordered_map<string, string> parent;
        for (const auto& [name, _] : graph)
            dist[name] = numeric_limits<int>::max();   // "infinity"
        dist[start] = 0;

        using State = pair<int, string>;      // (minutes so far, station)
        priority_queue<State, vector<State>, greater<State>> heap;
        heap.push({0, start});

        while (!heap.empty()) {
            auto [d, cur] = heap.top(); heap.pop();
            if (d > dist[cur]) continue;      // stale leftover entry: skip
            if (cur == goal) break;           // goal finalized: done early
            for (const auto& [next, cost] : graph.at(cur)) {
                int candidate = d + cost;     // time via cur
                if (candidate < dist[next]) { // found a better route?
                    dist[next] = candidate;   // record improvement
                    parent[next] = cur;
                    heap.push({candidate, next});
                }
            }
        }
        totalMinutes = dist[goal];
        return rebuildPath(parent, start, goal);
    }

private:
    // Walk parent links goal -> start, then flip. (Part 1.2's reverse!)
    static vector<string> rebuildPath(
            const unordered_map<string,string>& parent,
            const string& start, const string& goal) {
        vector<string> path;
        string cur = goal;
        while (cur != start) {
            path.push_back(cur);
            auto it = parent.find(cur);
            if (it == parent.end()) return {};   // goal was never reached
            cur = it->second;
        }
        path.push_back(start);
        reverse(path.begin(), path.end());
        return path;
    }
};

// ------------------------------------------------------------
// TRIP HISTORY: a stack. Newest trip on top; undo pops it. (Part 4)
// ------------------------------------------------------------
class TripHistory {
    stack<string> trips;
public:
    void record(const string& description) { trips.push(description); }
    void undoLast() {
        if (trips.empty()) { cout << "No trips to undo.\n"; return; }
        cout << "Removed from history: " << trips.top() << "\n";
        trips.pop();
    }
    void show() {
        if (trips.empty()) { cout << "History is empty.\n"; return; }
        stack<string> copy = trips;          // copy so display doesn't
        cout << "\n--- Trip history (newest first) ---\n";
        while (!copy.empty()) {              // destroy the real history
            cout << "  " << copy.top() << "\n";
            copy.pop();
        }
    }
};

// ------------------------------------------------------------
// TICKET WINDOW: a queue. First to line up is first served. (Part 5)
// ------------------------------------------------------------
class TicketWindow {
    queue<string> line;
public:
    void join(const string& name) {
        line.push(name);
        cout << name << " joined the line (position "
             << line.size() << ").\n";
    }
    void serveNext() {
        if (line.empty()) { cout << "Line is empty.\n"; return; }
        cout << "Now serving: " << line.front() << "\n";
        line.pop();
    }
};

// Helpers

static void printPath(const vector<string>& path) {
    if (path.empty()) { cout << "No route found.\n"; return; }
    for (size_t i = 0; i < path.size(); i++) {
        cout << path[i];
        if (i + 1 < path.size()) cout << " -> ";
    }
    cout << "\n";
}

    MetroNetwork metro;
    // Build the map: addTrack(A, B, minutes)
    metro.addTrack("Central",   "Museum",    4);
    metro.addTrack("Central",   "Riverside", 7);
    metro.addTrack("Museum",    "Old Town",  3);
    metro.addTrack("Riverside", "Old Town",  2);
    metro.addTrack("Old Town",  "Airport",  12);
    metro.addTrack("Riverside", "Airport",   9);
    metro.addTrack("Museum",    "Stadium",   6);
    metro.addTrack("Stadium",   "Airport",   5);

    while (true) {

             << "3. Fastest route in minutes (Dijkstra)\n"
             << "4. Show trip history\n"

             << "6. Join ticket line\n"

             << "0. Exit\n"
             << "Choice: ";
        int choice;
        if (!(cin >> choice)) break;
        cin.ignore();                        // clear leftover newline

        if (choice == 0) break;

        if (choice == 1) metro.listStations();

        else if (choice == 2 || choice == 3) {
            string from, to;
            cout << "From: "; getline(cin, from);
            cout << "To:   "; getline(cin, to);
            if (!metro.hasStation(from) || !metro.hasStation(to)) {
                cout << "Unknown station name.\n"; continue;
            }
            if (choice == 2) {
                vector<string> path = metro.fewestStops(from, to);
                cout << "Fewest stops: ";
                printPath(path);
                if (!path.empty())
                    history.record(from + " -> " + to + " ("
                        + to_string(path.size() - 1) + " stops)");
            } else {
                int minutes = 0;
                vector<string> path = metro.fastestRoute(from, to, minutes);
                cout << "Fastest route: ";
                printPath(path);
                if (!path.empty()) {
                    cout << "Total time: " << minutes << " minutes\n";
                    history.record(from + " -> " + to + " ("

                }

        }
        else if (choice == 4) history.show();
        else if (choice == 5) history.undoLast();
        else if (choice == 6) {

How the whole thing works, piece by piece

The graph (MetroNetwork::graph). The city map is unordered_map<string, vector<pair<string,int>>>: hash a station name (O(1)) and you're holding its departure board — a vector of (neighbor, minutes) pairs. addTrack writes each track twice because trains run both ways. This is Part 9.1 with weights attached.

Fewest stops (fewestStops). Pure BFS from Part 9.2. The queue guarantees ring-by-ring exploration, so reaching the goal early means reaching it with the minimum number of hops. The one addition: a parent map recording "I arrived at X from Y." That breadcrumb trail is what lets rebuildPath reconstruct the actual route rather than just its length — walk backwards goal → start, then reverse the vector (Problem 1.2's in-place reverse pattern via std::reverse).

Fastest route (fastestRoute) — Dijkstra's algorithm. BFS treats every track as equal, but a 12-minute track shouldn't count the same as a 2-minute one. Dijkstra fixes this by replacing the FIFO queue with a min-heap ordered by total minutes so far (Part 8): we always continue from the unfinished station with the smallest known travel time. When we pop a station, its time is provably final — any other route to it would have to pass through something already more expensive. Two subtleties in the code: - dist starts at "infinity" for everyone; a neighbor is only re-queued when we improve its best-known time (candidate < dist[next]). That comparison is called relaxation. - The heap may hold stale entries (a station pushed earlier with a now-beaten time). The line if (d > dist[cur]) continue; discards them cheaply. This "lazy deletion" trick avoids needing a fancy heap that supports updating priorities.

Why Dijkstra is the efficient choice: O((V + E) log V) with the heap. Brute force — enumerating all possible routes — explodes exponentially; even a modest network has thousands of route combinations, while Dijkstra touches each track once. This is, at its core, the algorithm inside every mapping app.

Trip history (TripHistory). A stack, because "undo the last thing" is LIFO by definition (Part 4). Note show() copies the stack before popping through it — displaying shouldn't destroy the history. Copying to display is fine for a small stack; the O(n) copy is the honest price of the stack's strict top-only access.

Ticket window (TicketWindow). A queue, because fairness is FIFO (Part 5). Nothing fancy — and that's the point: the right structure makes the feature almost write itself.

Alphabetical listing (listStations). Copies station names into a std::map, which is a self-balancing red-black tree — the industrial-strength version of Part 7's BST. Iterating a map performs an in-order traversal internally, so names come out sorted with zero sorting code from us. (Sorting a vector would be equally valid; this route is chosen to show the BST fact in action.)

Why the overall design is efficient: every user action hits the theoretically best structure for its job — O(1) station lookups (hash map), O(V+E) stop counting (BFS/queue), O(E log V) time routing (Dijkstra/heap), O(1) history and line operations (stack/queue), O(n log n) sorted listing (tree). Swap any of them for a plain vector-with-loops design and you'd get O(n) lookups, exponential routing, and hand-written sorting — the project is a live demonstration that choosing the structure is most of the engineering.

Final Cheat Sheet

Structure Best at Cost of its superpower Grab it when...
Vector O(1) index access, cache-fast loops O(n) middle insert default choice for "a bunch of things"
String text + all vector powers same as vector any text processing
Linked list O(1) insert/remove at a known spot O(n) to find that spot building blocks for other structures
Stack O(1) newest-first no middle access undo, nesting, backtracking, DFS
Queue O(1) oldest-first no middle access fairness, buffering, BFS
Hash map/set O(1) lookup by key no ordering "have I seen this?", key → value
BST / std::map O(log n) everything, sorted slower constants than hash need order + fast lookup together
Heap O(1) peek best, O(log n) push/pop only the top is visible top-K, scheduling, Dijkstra
Graph modeling relationships needs algorithms to query networks, routes, dependencies
