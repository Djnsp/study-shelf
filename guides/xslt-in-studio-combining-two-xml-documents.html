STEP 1Understand the scenario and the two documents

Before writing a line of XSLT, know exactly what trees you are working with.

The integration has two XML documents in memory inside a Studio mediation, each held in a variable:

VariableContentRoot elementNamespace URI
inputPECI payroll extractpeci:Workers_Effective_Stackurn:com.workday/peci
reportdatavarRaaS report outputwd:Report_Dataurn:com.workday.report/INT044_Time_and_absence_tracking

The PECI side is a stack of peci:Worker elements, each with a Worker_Summary (containing Employee_ID) and a series of Effective_Change blocks. The report side is a flat list of wd:Report_Entry rows, each carrying a wd:PID that holds the same employee number.

Key fact You cannot simply concatenate the two files. An XML document has exactly one root element and at most one <?xml ... ?> declaration, which must be the very first bytes. Two documents glued together is not XML — every parser downstream will reject it. Combining always means building a new single tree that contains material from both.

STEP 2Namespaces — the #1 source of silent failure

Nine out of ten “my XPath returns nothing” problems live here.

A namespace is identified by its URI, not its prefix. The prefix (wd:, peci:) is only a local nickname declared with xmlns:prefix="uri". Two consequences matter enormously:

First: your stylesheet must declare the same URIs as the source documents, or nothing will ever match. The prefix can differ; the URI cannot:

<xsl:stylesheet version="2.0"
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
    xmlns:peci="urn:com.workday/peci"
    xmlns:wd="urn:com.workday.report/INT044_Time_and_absence_tracking">

Second: an element with no prefix in the source is only “no namespace” if no default namespace is in force. In Workday output everything is prefixed, so always write prefixed XPath: peci:Worker, never Worker.

Classic symptom The transform runs without error but the output is empty or missing sections. Cause: the namespace URI in the stylesheet differs by one character from the source (RaaS namespaces embed the report name — change the report, and urn:com.workday.report/INT044_... changes with it). Fix the URI, not the XPath.
Tip Use exclude-result-prefixes="wd" on the stylesheet element to stop unused namespace declarations leaking into your output once you have renamed elements away from that namespace.

STEP 3How Studio actually runs your XSLT

The mediation message is the input tree. Everything else must be fetched.

An xslt step in a Studio mediation transforms the current message rootpart. Whatever document is “the message” when the step executes becomes / inside the stylesheet. So the assembly pattern for our scenario is:

<!-- 1. report XML is the message here -->
<cc:copy id="Copy" output="variable" output-variable="reportdatavar"/>

<!-- 2. PECI XML becomes the message -->
<cc:copy id="Copy0" output="variable" output-variable="input" input="message"/>

<!-- 3. transform runs with PECI as the input tree -->
<cc:xslt id="Xslt" url="NewStylesheet.xsl"/>

That gives the stylesheet one of the two documents for free. The whole challenge of this scenario is getting the second document (the variable) into the stylesheet — Step 6 covers the three ways to do it, and Step 7 dissects the famous error you get when it goes wrong.

Studio protocol worth knowing Studio resolves special URL schemes at runtime. mctx:vars/<name> reads a mediation-context variable — usable in component attributes (url="mctx:vars/xslt.file") and from inside a stylesheet via document('mctx:vars/reportdatavar'). This is the cleanest bridge between Studio variables and XSLT.

STEP 4The XSLT mental model: templates, not scripts

XSLT is pattern → action, driven by the input tree.

XSLT is not a procedural script that walks the file top to bottom. It is a set of template rules. The processor starts at the document node (/), finds the best-matching template, and executes it. Inside a template, <xsl:apply-templates/> says “now go process my children the same way.” Output is whatever the executed templates emit.

InstructionWhat it doesWhen to use
<xsl:template match="...">Declares a rule for nodes matching the patternThe building block of everything
<xsl:apply-templates/>Recursively processes child nodesDefault way to descend the tree
<xsl:copy>Shallow copy: the current node only, no children, no attributesInside identity transforms
<xsl:copy-of select="...">Deep copy: the selected nodes with everything inside themGrabbing whole subtrees unchanged
<xsl:element name="...">Creates a brand-new element, name/namespace under your controlRenaming elements (Step 9)
<xsl:value-of select="...">Emits the string value of the selectionText output, not structure

The most important distinction in merge scenarios is copy vs copy-of: copy-of transplants a subtree exactly as-is (namespaces included), while copy + apply-templates rebuilds the tree node by node — which is what lets you intervene at any level, e.g. to inject extra content into peci:Worker.

STEP 5The identity transform — your default starting point

Copy everything through, then override only what should change.

<xsl:template match="@*|node()">
    <xsl:copy>
        <xsl:apply-templates select="@*|node()"/>
    </xsl:copy>
</xsl:template>

This one rule matches every attribute and every node, copies it, and recurses. On its own it reproduces the input exactly. Its power is that XSLT prefers a more specific template over a generic one — so adding a second template for peci:Worker means workers get special handling while everything else flows through untouched:

<xsl:template match="peci:Worker">
    <xsl:copy>
        <xsl:apply-templates select="@*|node()"/>
        <!-- extra content is injected here, after the worker's own children -->
    </xsl:copy>
</xsl:template>
Rule of thumb “Keep the document mostly the same, change these bits” = identity transform + targeted overrides. “Build a completely new shape” = a single match="/" template that constructs the output explicitly. Our scenario uses the first pattern for the per-worker merge, and the second for the simple wrap-both-documents variant.

STEP 6Getting the second document into the stylesheet

Three approaches, from most robust to most manual.

Approach A — document('mctx:vars/...') (recommended in Studio)

<xsl:variable name="report" select="document('mctx:vars/reportdatavar')"/>

The XSLT document() function loads an external document via a URI, and Studio's resolver understands mctx:vars/<variable>. The result is a genuine document node — XPath works on it immediately ($report/wd:Report_Data/wd:Report_Entry). No parameters to configure, no string parsing, works in XSLT 1.0/2.0/3.0.

Approach B — stylesheet parameter

Declare <xsl:param name="reportdata"/> and bind it on the xslt step. The catch: the binding must actually exist on the step, and Studio hands variables over as strings, so in 2.0 you still cannot do $reportdata/wd:Report_Data — see Step 7 for the exact failure, and Step 11 for the 3.0 fix (parse-xml()).

Approach C — combine before the XSLT

Build one physical document in the mediation first (a write step producing <Combined_Data> around both payloads — with the inner <?xml?> declarations removed), then run the XSLT on the single combined tree with no second document at all. Crude but processor-version-proof, and a good fallback if the mctx protocol is unavailable.

ApproachProsCons
A: document('mctx:vars/…')No config, real nodes, any XSLT versionStudio-specific URI scheme
B: xsl:paramPortable concept, testable outside StudioArrives as string; needs 3.0 parse-xml(); easy to leave unbound
C: pre-combineBulletproof, version-agnosticExtra assembly steps; must strip XML declarations

STEP 7Anatomy of the XPTY0019 string error

The exact error from this scenario, decoded word by word.

The error Required item type of first operand of '/' is node(); supplied value has item type xs:string

Translation: you wrote $reportdata/wd:Report_Data. The / operator's left side must be a node (something with children to step into). But $reportdata contained a string — a flat piece of text. XML text that has not been parsed is just characters; XPath cannot navigate it.

How the string gets there — two routes, same crash:

RouteMechanism
Parameter never boundAn <xsl:param name="reportdata"/> with no select and no binding defaults to the empty string "". The xslt step in the assembly was <cc:xslt id="Xslt" url="NewStylesheet.xsl"/> — no parameter passed — so $reportdata was "", a string. Crash.
Parameter bound to a stringEven with a binding, Studio hands the variable's text to Saxon. A string of XML is still a string. Same crash, just with content in it.
The lesson that generalizes In XSLT 2.0+, every value has a type. When an error names two types (“required node() … supplied xs:string”), the question is never “how do I silence this?” but “where did my node turn into a string?” — usually at a parameter boundary or a value-of that should have been copy-of. The mctx document() approach avoids the boundary entirely, which is why it is the recommended fix.

STEP 8Joining the two documents (PID = Employee_ID)

A relational join, expressed as an XPath predicate.

Inside the peci:Worker template, select exactly the report rows whose wd:PID equals this worker's peci:Employee_ID:

<xsl:copy-of select="$report/wd:Report_Data/wd:Report_Entry[
    normalize-space(wd:PID) =
    normalize-space(current()/peci:Worker_Summary/peci:Employee_ID)]"/>

Three details deserve attention:

current() vs . — inside a predicate the context dot refers to the wd:Report_Entry being tested, so ./peci:Worker_Summary would look for a PECI child inside the report row and find nothing. current() reaches back to the node the template matched: the worker. This is the single most common join bug.

normalize-space() — report values often carry stray whitespace or line breaks. Comparing trimmed strings makes the join immune to it. (If one side is zero-padded — "208611" vs "0208611" — compare number() instead.)

Scaling with xsl:key — the predicate above rescans the report for every worker (O(workers × entries)). For thousands of rows, index once and look up in constant time:

<xsl:key name="repByPid" match="wd:Report_Entry" use="normalize-space(wd:PID)"/>

<!-- XSLT 2.0: third argument points key() at the report document -->
<xsl:copy-of select="key('repByPid',
    normalize-space(peci:Worker_Summary/peci:Employee_ID), $report)"/>

STEP 9Renaming namespaces with modes

Requirement: wrap the report in <peci:reportdata> and turn every wd:* into peci:*.

copy-of cannot do this — it preserves names exactly. To change names you must rebuild each element, and to keep the renaming rules separate from the main identity rules you put them in a mode. A mode is a parallel universe of templates: only apply-templates calls that name the mode will use them.

<!-- inside the peci:Worker template -->
<peci:reportdata>
    <xsl:apply-templates mode="wd-to-peci"
        select="$report/wd:Report_Data/wd:Report_Entry[...]/node()"/>
</peci:reportdata>

<!-- every element gets rebuilt in the peci namespace, same local name -->
<xsl:template match="*" mode="wd-to-peci">
    <xsl:element name="peci:{local-name()}" namespace="urn:com.workday/peci">
        <xsl:apply-templates select="@*|node()" mode="wd-to-peci"/>
    </xsl:element>
</xsl:template>

<!-- attributes and text pass through unchanged -->
<xsl:template match="@*|text()|comment()|processing-instruction()" mode="wd-to-peci">
    <xsl:copy/>
</xsl:template>

Piece by piece: match="*" catches every element; local-name() is its name without any prefix (totalLOADays, not wd:totalLOADays); the attribute value template peci:{local-name()} builds the new prefixed name; and the namespace attribute pins the actual URI. Because the template recurses in the same mode, nested structures like Leave_of_Absence_Requests_group are converted at every depth automatically.

The trailing /node() in the select drops the Report_Entry wrapper itself so its fields sit directly inside peci:reportdata — remove it to keep peci:Report_Entry as an inner wrapper.

STEP 10The final tested stylesheet, line by line

The complete solution — verified against the real sample documents.

<?xml version="1.0" encoding="UTF-8"?>
<xsl:stylesheet version="2.0"
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
    xmlns:peci="urn:com.workday/peci"
    xmlns:wd="urn:com.workday.report/INT044_Time_and_absence_tracking"
    exclude-result-prefixes="wd">

    <xsl:output method="xml" indent="yes" encoding="UTF-8"/>

    <!-- [1] second document, read from the Studio variable -->
    <xsl:variable name="report" select="document('mctx:vars/reportdatavar')"/>

    <!-- [2] identity: PECI flows through untouched -->
    <xsl:template match="@*|node()">
        <xsl:copy><xsl:apply-templates select="@*|node()"/></xsl:copy>
    </xsl:template>

    <!-- [3] per-worker merge: join + wrap + rename -->
    <xsl:template match="peci:Worker">
        <xsl:copy>
            <xsl:apply-templates select="@*|node()"/>
            <peci:reportdata>
                <xsl:apply-templates mode="wd-to-peci"
                    select="$report/wd:Report_Data/wd:Report_Entry[
                        normalize-space(wd:PID) =
                        normalize-space(current()/peci:Worker_Summary/peci:Employee_ID)]/node()"/>
            </peci:reportdata>
        </xsl:copy>
    </xsl:template>

    <!-- [4] rename wd:* to peci:* at every depth -->
    <xsl:template match="*" mode="wd-to-peci">
        <xsl:element name="peci:{local-name()}" namespace="urn:com.workday/peci">
            <xsl:apply-templates select="@*|node()" mode="wd-to-peci"/>
        </xsl:element>
    </xsl:template>

    <!-- [5] leaves pass through -->
    <xsl:template match="@*|text()|comment()|processing-instruction()" mode="wd-to-peci">
        <xsl:copy/>
    </xsl:template>

</xsl:stylesheet>

Execution walkthrough for the sample data: the processor starts at /, the identity rule [2] copies Workers_Effective_Stack and Summary through. Reaching peci:Worker, rule [3] wins (more specific than [2]): it copies the worker, replays all its children through the identity, then opens <peci:reportdata> and applies the join — PID 208611 matches Employee_ID 208611, one Report_Entry selected. Its child nodes enter mode wd-to-peci: rule [4] rebuilds wd:totalLOADays as peci:totalLOADays and recurses; rule [5] copies the text values. Result: the original PECI, with a fully converted report block inside each worker.

STEP 11XSLT 3.0 — what it buys you in these scenarios

If your Studio's Saxon accepts version="3.0", three upgrades apply.

FeatureReplacesWhy it matters here
parse-xml($string)nothing in 2.0 (dead end) Turns a string of XML into a document node — makes the parameter approach (Step 6B) viable: parse-xml($reportdata)//wd:Report_Entry
<xsl:mode on-no-match="shallow-copy"/> the 4-line identity template One declaration gives you identity behaviour; you write only the overrides
$x instance of xs:string guards
(2.0 has this too; 3.0 makes it useful with parse-xml)		 runtime type crashes Accept a param as string or node: if ($p instance of xs:string) then parse-xml($p) else $p
<!-- 3.0 flavour of the same solution, parameter-based -->
<xsl:param name="reportdata"/>
<xsl:variable name="report" select="
    if ($reportdata instance of xs:string)
    then parse-xml(replace($reportdata, '^[^&lt;]+', ''))
    else $reportdata"/>
<xsl:mode on-no-match="shallow-copy"/>

The replace(..., '^[^<]+', '') strips any leading whitespace or carriage returns before the <?xml declaration — Studio write steps and variables frequently carry &#xD; noise that would otherwise make parse-xml() fail, since an XML declaration must be the first thing in the string.

STEP 12Debugging playbook & error decoder

Work the checklist top to bottom; most merge failures fall out at line one or two.

SymptomLikely causeFix
XPTY0019 — first operand of '/' is node(); supplied xs:string Unbound param (empty-string default) or variable passed as text Use document('mctx:vars/…'), or bind the param and parse-xml() it (3.0)
Runs clean, report section empty Namespace URI mismatch, or join values differ (padding/whitespace) Recheck URIs character-by-character; wrap both sides of the join in normalize-space()
Runs clean, everything empty Wrong document is the message when the xslt step runs Check step order; the last copy/write before cc:xslt decides the input tree
XTSE0110 / “3.0 not supported” style compile errors Studio's Saxon build predates XSLT 3.0 Stay on 2.0 + the mctx document() approach
Duplicate or missing namespace declarations in output Prefixes leaking from source or stylesheet exclude-result-prefixes; create elements with explicit namespace=
Join matches the wrong rows / all rows . used inside a predicate where current() was meant Step 8 — current() refers to the matched node, . to the candidate

Verification habits that catch problems early

Test the stylesheet outside Studio first — any Saxon (oXygen, a local Saxon jar, SaxonC) will reproduce Studio's behaviour for everything except the mctx: protocol; substitute a local file path in document() for the test and swap the mctx URI back for deployment. Make failures loud: an <xsl:message terminate="yes"> when the second document is empty beats silently shipping half a file to payroll. And keep a golden pair of sample inputs (like the PECI and report used throughout this guide) with the expected output, so any future edit to the stylesheet can be checked in seconds.

The one-paragraph summary Combining two in-memory XML documents in Studio = make one document the message, reach the other with document('mctx:vars/<variable>'), keep the main document flowing with an identity transform, inject at the right spot with a specific template, join with a normalized predicate or key, and rebuild elements via a mode when names or namespaces must change. Every error you meet on the way is one of: a string where a node was needed, a namespace URI that doesn't match, or the wrong document in the message slot.
