01What is Workday Studio?

Workday Studio is a unified, Eclipse-based IDE that lets customers and partners develop, deploy, debug, and support their own complex integrations running inside the Workday Cloud. It ships as a set of Eclipse plug-ins and gives you a graphical Assembly Editor where you drag reusable components onto a canvas and wire them together. The components handle the plumbing — transports, paging, document storage, eventing — so you focus on business logic.

Workday itself has used Studio for years to build its packaged integrations, connectors, and even the EIB framework. Studio has been available to customers since Workday 12.

Develop

Drag-and-drop Assembly Editor plus full source view of the underlying assembly.xml. Content assist (Ctrl+Space) surfaces Javadoc for MVEL helpers.

Deploy & launch

Cloud Explorer connects Studio to your tenants. Deploy a project as a WSAR to the Integration Cloud, then launch from Studio or from Workday.

Debug & support

Process Monitor, log files, consolidated reports, and the Assembly Debugger let you inspect every message, property, and variable at runtime.

02When to use Studio (vs EIB vs Core Connectors)

Choosing the right tool is the first architecture decision on any Workday integration.

ToolBest forTrade-offs
EIBSimple inbound/outbound patterns: one data source, one transformation, one destination. Report-based extracts, spreadsheet loads.Single transform, single delivery. Limited branching, error handling, and orchestration.
Core Connectors / PICOF / PECIPackaged, configurable connector frameworks for common vendor patterns (payroll, benefits) driven by integration services, attributes, and maps.Configuration over code — fast, but bounded by what the template supports.
StudioComplex logic: multiple sources/targets, conditional routing, looping, aggregation, custom error handling, large-volume paging, custom audit files, multi-format output.Requires a developer skill set; you own the design, scalability, and support model.
TIP

A common enterprise pattern: use a Core Connector (e.g. PECI) to produce the canonical change file, then a Studio assembly or XSLT layer for the vendor-specific transformation and delivery that the connector can't express.

03Anatomy of an assembly

An assembly describes a message-oriented processing chain. The processing style is always the same: take in a message, process it, and route it on. Messages arrive over an in-transport, pass through mediation components and steps, and exit over an out-transport.

async-mediation

PutIntegrationMessage
A minimal outbound chain: receive launch event → transform → deliver → report status to the integration event
  • In-transports define where processing starts. Every assembly needs at least one workday-in; more than one gives you multiple entry points. local-in defines a reusable sub-assembly (a subroutine); local-out calls it.
  • Mediation components (sync/async) hold ordered lists of steps — the units that validate, transform, manipulate, and log messages.
  • Advanced components — route, splitter, aggregator — dynamically control how the runtime traverses the chain.
  • Common components are Workday-delivered sub-assemblies (PagedGet, PutIntegrationMessage, Ftp, GetIntegrationSystems…). Dropping one onto the canvas inserts a local-out pointing at the packaged endpoint.
  • Out-transports take the current MediationMessage and send it somewhere: SFTP/FTPS, HTTP/S, email, XMPP, or back to Workday via workday-out-soap / workday-out-rest.

04The MediationMessage

An assembly processes data as messages. A message enters at an in-transport, follows the connector paths, and leaves through an out-transport. A message consists of one or more parts (MIME-style): a single document is a one-part message; attachments become parts 1, 2, 3… Parts can hold textual or binary data, and every part carries a MIME type and headers.

// Address parts by index — part 0 is always the root part
parts[0].text                 // content of the root part
parts[1].text                 // content of the first attachment
parts[0].mimeType             // MIME type of the root part
parts[0].getHeader('someHeader')

05The MediationContext

The framework passes everything between components inside an instance of MediationMessageContext. When an in-transport creates a message, it's wrapped in this context, which lets every component in the chain share state. Its key sub-components:

MediationMessage

The current message and its parts. Ultimately exchanged with an external system via an out-transport.

Variables

Temporary holders for message data. Classic pattern: copy the message into a variable now, use it later in the chain — e.g. vars['raw'] = message.

Properties

A map for temporary values and Java objects — flags, counters, attribute values. Accessed as props.name or props['name'].

The context also carries the error flag and errorHandled boolean, the assembly audit, the customer ID, and the dynamic endpoint. In MVEL you reach it via the context variable; a mctx URL protocol also lets other components reference context values.

06Synchronous vs asynchronous

The distinction runs through transports and mediations, and it's a favourite exam topic:

  • Sync in-transport expects a response; async in-transport discards any response returned to it.
  • Sync out-transport returns a response; async out-transport does not.
  • SyncMediation has two step lists — request-steps (push phase) and response-steps (pop phase). AsyncMediation has a single steps list that runs during the push phase only. An async mediation is exactly a sync one with no response steps.
TIP

Use a SyncMediation around a workday-out-soap call when you need to process the web-service response (pop phase). Use AsyncMediation for one-way work like logging, transforming, and delivering.

07Runtime lifecycle of an integration

  1. Processing starts at a workday-in transport, which receives a launch integration event document containing the integration event ID and any launch-time parameters.
  2. The workday-in transparently calls Get_Integration_Systems to fetch attribute/map settings for services you defined, populating wd.int.sys for the intsys MVEL helper.
  3. The message flows through mediations, routes, splitters, and steps; state accumulates in properties and variables.
  4. Out-transports deliver the payload; PutIntegrationMessage writes status, messages, and output-file links back onto the Integration Event; the store step persists documents to the Workday document store (the "Blobitory" / W: drive).
  5. Errors raise the context error flag; error handlers (local or global) fire, and the event completes, completes-with-warnings, or fails.

08Scalability rules

Every integration must assume its data extract can be arbitrarily large. If you process employee data, assume the population can grow without bound. The two sanctioned approaches:

  • Split → process → aggregate: use a splitter to break bulk documents into individual records, process each, and re-batch with an aggregator.
  • Page the web service: use the PagedGet common component so responses are retrieved and processed page by page instead of one giant payload.
!

XPath methods (xpath, xpathB, xpathF) are processed in memory with a 1,000,000-character limit. On large messages use streaming — e.g. the write step's xml-stream element — or you'll hit "Output greater than limit of 1,000,000" and the integration terminates.

03Bindings & security

Transport bindings shape how a transport speaks a protocol: rest-binding, wsdl-http-binding, and wsdl-soap-binding. The SOAP binding supports ws-security, ws-ut (WS-UsernameToken, configurable on both in- and out-transports), and custom-policy. HTTP transports support basic and custom authentication with automatic handler selection.

04Mediations step containers

A mediation defines a sequential ordering of steps that operate on the message as it passes through. Steps cannot be dropped directly onto the canvas — they must live inside a mediation. The routes-to attribute names the next transport, mediation, or service in the chain.

async-mediation

One steps list, executed during the push (request) phase. The workhorse for one-way flows.

sync-mediation

Two lists: request-steps (push) and response-steps (pop). Use when you must handle a response — e.g. after workday-out-soap.

05Route — conditional flow

A route consists of one or more sub-routes plus a strategy that picks which sub-route runs during the push phase. Content-based strategies:

  • xpath — choose a sub-route from an XPath expression against the message.
  • regex — choose from a regular-expression match.
  • mvel — choose from an MVEL Boolean expression (the most flexible; pair with choose-route conditions).
  • round-robin — rotate through sub-routes on each execution.

Routes can also iterate or loop: all executes every sub-route in turn, loop uses MVEL to set context properties that drive iteration, and failover tries an alternate sub-route when one errors.

06Splitter — divide bulk data

The splitter processes bulk messages containing many records, feeding them one (or a group) at a time down a sub-route. Like a route, it has strategies and sub-routes added from the hover toolbar. Splitter flavours:

  • xpath-splitter — split on a repeating XPath node (e.g. each wd:Report_Entry).
  • xml-stream-splitter — streaming split for very large XML, avoiding in-memory limits.
  • standard-splitter, custom-splitter, unzip-splitter — delimiter/standard formats, developer logic, and archive entries respectively.
// Detect the last record emitted by a splitter
props['is.last.record'] = util.isLastMessageInBatch()

07Aggregator — reassemble batches

The aggregator concatenates mediation messages into a single batch message and routes it onward. Configure a batch strategy (custom, size-based, or time-based, via force-batch-when) and a collator strategy (collate-when) defining how messages are merged. Splitter + aggregator is the canonical scalable pattern: split employees → transform each → aggregate into the final file.

10Error handlers

When a step fails, the runtime raises the context error flag and interrupts the flow. Error handlers can be placed inside a mediation (local scope) or globally (outside any mediation). Locally-scoped handlers fire for errors in their mediation; unhandled and downstream errors bubble to global handlers. A handler can mark errorHandled = true, stopping further error processing and letting the flow continue.

  • log-error — writes an error log entry (contains a log-message element you configure).
  • send-error — routes the error to a destination; classic pattern is routing to a local-out that calls PutIntegrationMessage, so the failure is visible on the Integration Event.
  • custom-error-handler — a Spring bean you supply for programmatic handling.

Add a handler by hovering over a mediation and picking the handler type from the context toolbar. The delivered Global Error Handler module drops a preconfigured global handler (set severity, e.g. CRITICAL) into the assembly in one step.

11Modules — assembly templates

Modules are templates for whole assemblies or assembly fragments implementing a pattern. Drag one from the palette, answer the prompts (e.g. paste a SOAP request, specify web-service details), preview what will be inserted, and finish. You can also build your own: right-click a project → Create Assembly Module…, walk the wizard, and Studio generates an .xmi file whose parameters you reference in the assembly text as ${Parameter1}. Register module directories under Preferences → Workday → Assembly Editor → Modules.

01Build 1 — MyHelloCloud (the minimum viable assembly)

Concept introduced: the workday-in → PutIntegrationMessage backbone that every integration shares.

workday-in

  1. Create the project.

    File → New → Assembly Project, named MyHelloCloud. Click Next, change the collection name to MyHelloCloudCollection, click Finish.

  2. Drop the two components.

    From the palette, drag a Workday In transport and a PutIntegrationMessage (PIM) onto the blank Assembly Diagram. When PIM shows its "Select Parameter" dialog, click Finish.

  3. Wire them.

    Draw a connector from Workday In to the PIM.

  4. Configure the summary message.

    In the PIM's Properties → Parameters, set is.message.summary to a value like 'My Hello Cloud' — don't forget the single quotes: parameter values are MVEL expressions, so an unquoted word is treated as a variable reference.

  5. Save, deploy, launch.

    Check the event on the Process Monitor and View Log File. In Workday, the integration event now shows your summary message.

02Build 2 — add a Log step (steps need mediations)

Concept introduced: steps can't sit on the canvas alone; they live inside a mediation, and every step with output uses the Message Builder.

  1. Try dragging a Log step straight onto the diagram.

    It won't attach — that's the lesson. A step must be dropped into a mediation.

  2. Add an AsyncMediation, then drop the Log step inside it.

    Drag an AsyncMediation onto the canvas; drag a Logging step into the mediation body.

  3. Configure the Message Builder.

    Select the Log step → Properties → Message Builder. Remove the default message-content element, add a text element, type your message, and save. (message-content logs the current message; text logs a literal/MVEL template.)

  4. Re-wire, save, deploy, launch.

    Route workday-in → AsyncMediation → PIM. Your text appears in the event's log file.

04Build 4 — MyHelloRaaS (call a custom report)

Concepts introduced: Reports-as-a-Service, workday-out-rest, and the extra path.

  1. Enable a custom report as a web service.

    Create an Advanced custom report, tick Enable as Web Service. Workday generates a fixed RaaS namespace: urn:com.workday.report/Report_Name. It stays stable across owner or name changes (editable, but Workday doesn't verify uniqueness — and existing integrations must be updated if you change it). All columns, prompts, and related business objects need labels.

  2. Create project MyHelloRaaS

    Components: Workday In · WorkdayOutRest · AsyncMediation with a Log step (logging the response) · PIM. Wire in order.

  3. Configure the extra path.

    On WorkdayOutRest, the REST path is customreport2/<tenant>/<owner>/<report name>. Easiest source of truth: open the report in the tenant → related actions → Web Service → View URLs and copy the Workday XML (REST) URL.

  4. Or bind via the report service.

    Define a report service on the workday-in and reference it from WorkdayOutRest; Studio then inserts the MVEL expression @{intsys.reportService.getExtrapath('report-alias-name')} into the Extra Path property, decoupling the assembly from tenant/owner specifics.

  5. Deploy and launch.

    The report rows appear in the logged response.

05Build 5 — store the output & attach it to the event

Concepts introduced: the store step, the document store ("Blobitory" / W: drive), and document links on the Integration Event.

  1. Add a Store step.

    In MyHelloRaaS, drop a Store step into the existing AsyncMediation after the Log step.

  2. Configure output to a variable.

    Set Output = variable, Output-Variable = StoredReportResults. Give it a Title — that's the filename; if omitted it defaults to the external filename of what's being stored. The variable lands in the MediationContext and is available to anything downstream.

  3. Decide who creates the document reference.

    Create Document Reference defaults to true: the store step itself calls PutIntegrationMessage with severity INFO, summary = the reference description, and is.document.deliverable = false. Need different parameters? Set it to false and call PIM explicitly.

  4. Attach the file on your own PIM.

    Set the PIM's is.document.variable.name parameter to 'StoredReportResults'. Don't also set is.document.file.name when a store step is in play — the store title wins.

  5. Deploy, launch, verify.

    The integration event now shows an output file link to your stored report.

06Build 6 — transform with XSLT

Concepts introduced: the xslt step and passing context properties into the stylesheet as parameters.

  1. Create the stylesheet in the project.

    Add an .xsl file under the project (e.g. inside WSAR-INF) that transforms the RaaS/WWS response — the output.xml you saved in Build 3 is your development sample.

  2. Add an XSLT step.

    Drop an xslt step into the mediation between the response and the store/delivery, pointing at your stylesheet.

  3. Feed it configuration the clean way.

    MediationContext properties are automatically passed into the transformation as stylesheet parameters — just declare a matching <xsl:param name="ia.include.job.code"/>. Set the property first in an eval step: props['ia.include.job.code'] = intsys.getAttribute('Include Job Code'). This beats calling extension functions like is:getIntegrationAttributeValue(...) from inside the XSLT, which ties the stylesheet to the IntegrationSharedComponents project and makes it hard to debug in an external editor like Oxygen.

  4. Store/deliver the transformed output.

    Route the transformed message to the store step or an sftp-out, exactly as in Build 5.

Concepts introduced: the scalable splitter/aggregator pattern plus content-based routing — the Day-6 router activity.

  1. Split the bulk document.

    Add a splitter (xpath-splitter on the repeating worker node, or xml-stream-splitter for very large files) so each record flows individually.

  2. Prepare two transformations.

    Duplicate the worker-summary XSLT; in the copy for non-male workers, strip it down (e.g. keep only wd:ReferenceID and wd:Gender). Build two AsyncMediations, one per stylesheet.

  3. Add a router with an MVEL strategy.

  4. Aggregate and deliver.

08Build 8 — error handling done properly

  1. Drop the Global Error Handler module.

    Drag the Global Error Handler module from the palette to an empty area of the assembly; configure severity CRITICAL; review what it inserted. Global handlers catch errors that bubble back unhandled from anywhere in the assembly.

  2. Add local handlers to every mediation.

    Hover over each mediation → add a send-error handler → route it to a PIM so every failure surfaces on the Integration Event with a meaningful message. A log-error handler alongside gives the console detail.

  3. Understand the scoping rules.

    An error in a step fires the handlers of that mediation first. Handlers can set errorHandled to stop propagation and allow processing to continue at the next step; otherwise the error flows to global handlers. A property controls whether locally-scoped handlers may also handle downstream errors (default: they don't — downstream errors belong to global handlers).

  4. Report clean summaries.

    When writing failure text into XML (e.g. a PIM summary sourced from a property), wrap it: @{util.cleanString(props['is.message.summary'])} so the output stays well-formed.

09Debugging checklist

  • Process Monitor → View Log File is your first stop; log steps with message-content are your printf.
  • Consolidated Report Viewer shows the run's aggregated diagnostics, including memory-limit failures.
  • Assembly Debugger lets you step through and inspect properties/variables; setting attribute values into properties (rather than XSLT extension calls) makes them visible here.
  • Ctrl+Space in property fields opens content assist with the MVEL helper Javadoc.
  • Common gotchas: unquoted string parameters on PIM, missing web-service version, steps outside mediations, RaaS report missing column labels, intsys used without a service defined on workday-in, dots in property names, and the 1M-character XPath limit.

MVEL is a Java-friendly expression language the assembly runtime uses pervasively for dynamic configuration — from a one-line property binding to full scripts in an eval step. The Workday runtime supports MVEL 1.3 (compatible with 1.2).

04Auto-conversion syntax

MVEL auto-converts between strings, lists, parts, variables, and whole messages — this is the fastest way to move data around an assembly. The inline-list syntax [ content, mimeType ] supplies content and MIME type together; the default MIME type is text/xml.

variables
vars['fred'] = '<hello>world</hello>'        // new var, text/xml
vars['fred'] = [ 'Hello World', 'text/plain' ] // content + mime type
vars['fred'] = [ 23 + 5, 'text/plain' ]        // any expression as content
vars['fred'] = parts[1]                        // copy from first attachment
vars['fred'] = message                         // copy the whole message
vars['fred'] = parts[0].xpathF('/dink/donk')   // an XPath fragment
vars['fred'] = null                            // remove the variable
message parts
parts[0] = '<hello>world</hello>'
parts[1] = [ 'Hello World', 'text/plain' ]   // created if missing —
                                             // but parts must stay sequential (no part 9 without part 8)
parts[0] = vars['fred']
parts[2] = parts[1]                          // copy attachment 1 → 2
parts[0] = null                              // remove root: attachment 1 becomes root;
                                             // if none, root resets to '' text/xml
whole messages — assign to context.message
context.message = '<hello>world</hello>'
context.message = [ 'Hello World', 'text/plain' ]
context.message = vars['fred']
context.message = parts[0]     // multi-part message becomes single-part

05Integration attributes & maps

The GetIntegrationSystems sub-assembly parses your integration system config; its ParseIntegrationSystems component creates the intsys helper. (The workday-in also populates this transparently — but only for attributes/maps declared in services on the transport. Using intsys without a defined service fails at runtime.)

// classic eval step: copy attributes into properties
props['ia.include.job.code'] = intsys.getAttribute('Include Job Code')

// prompt-based attribute → a specific reference ID type
props['ia.business.contact.profile.type.reference'] =
  intsys.getAttributeReferenceData('Business Contact Profile Type',
                                   'Communication_Usage_Type_ID')
TIP

Have one eval step that copies all integration attribute values into context properties up front. Properties flow into XSLT automatically as stylesheet parameters (<xsl:param name="ia.include.job.code"/>), which keeps stylesheets debuggable in Oxygen and values visible in the Assembly Debugger. Direct XSLT extension functions exist — declare xmlns:is="java:com.workday.esb.intsys.xpath.ParsedIntegrationSystemFunctions" then call is:getIntegrationAttributeValue('Entity Name') or is:getIntegrationMapValue('Employee Type', $type) — but they couple the XSLT to IntegrationSharedComponents.

07Gotchas that cost real debugging hours

Dots in property names

props['SplitQ.last.in.batch'] = props['mediation.splitter.last.in.batch'] throws org.mvel.CompileException: unterminated '[' in Studio's MVEL. Workaround: assign via context.setProperty('name.with.dots', value).

1M-character XPath limit

xpath/xpathB/xpathF run in memory with a 1,000,000-character ceiling. Large messages: switch to streaming (write step's xml-stream) or split first.

MVEL version

The runtime is MVEL 1.3 (1.2-compatible) — modern MVEL 2.x syntax you find online may not compile.

getLatestWWSVersion()

Deprecated practice. Always pin explicit, versioned WWS requests; latest-version lookups cause unexpected failures as tenants roll forward.

Quotes on parameters

PIM parameter fields are MVEL. 'My Hello Cloud' is a string; My Hello Cloud is three undefined identifiers.

Non-sequential parts

You can't create part 9 unless part 8 exists. Attachments are created in order.
