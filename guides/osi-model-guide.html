Networking field guide

The OSI Model, in plain English

Seven layers, one job each. Every message your computer sends — a web page, an email, a Workday SFTP file drop — travels down this stack on the way out and back up it on the way in. Click a layer to jump to it.

The big idea: a postal system for data

The OSI model is not software you install — it's a mental map. It says: sending data across a network involves seven distinct jobs, and each job only needs to talk to the job directly above and below it. Your browser doesn't need to know whether you're on Wi-Fi or fiber; the Wi-Fi chip doesn't need to know you're loading a cat video. Each layer trusts its neighbors and ignores everything else.

The best analogy is mailing a letter. You write the message (Application). You translate it into a language the recipient reads (Presentation). You agree you're having an ongoing correspondence (Session). You number the pages so nothing gets lost (Transport). You write the destination address (Network). The postal truck carries it to the next sorting facility (Data link). And physically, it's just paper moving on roads (Physical).

Encapsulation — each layer adds an envelope

As data moves down the stack on the sending machine, each layer wraps it with its own header — like envelopes inside envelopes. The receiving machine opens them in reverse. Step through it:

Layer 7 · PDU: Data

Application

The layer you can see — where apps make and answer requests.

In plain English: this is the layer humans touch. When your browser asks for a page, your mail app sends an email, or a Workday integration calls a REST API, that conversation happens in an application-layer protocol. It defines what the messages mean: "GET me this page", "here's a file", "what's the IP for this hostname?"

A common trip-up: Layer 7 is not the app itself. Chrome isn't Layer 7 — HTTP, the language Chrome speaks, is.

Analogy

The conversation itself. Two people talking: "Can I get a menu?" — "Here you go." Everything below Layer 7 is just the machinery that carries the words.

Real-world examples

  • Loading a website — your browser speaks HTTP/HTTPS to the server
  • "What's the address of google.com?" — DNS turns names into IP addresses
  • Sending an email — SMTP sends it; IMAP fetches it to your phone
  • A Workday Studio integration calling a SOAP/REST endpoint or dropping a file via SFTP
  • Remote server admin — SSH gives you a secure terminal on another machine

Layer 6 · PDU: Data

Presentation

The translator — makes sure both sides read the same language, safely.

In plain English: computers store and send data in wildly different formats. This layer handles three jobs: translation (character encodings like UTF-8, file formats like JPEG), encryption (scrambling data so eavesdroppers see gibberish — this is where TLS conceptually lives), and compression (shrinking data so it travels faster).

In modern practice this layer is mostly absorbed into applications and libraries — but the jobs are very real. Every time you see the padlock in your browser, "Layer 6 work" is happening.

Analogy

A diplomatic interpreter with a locked briefcase: translates your words into the other side's language, seals them so only the recipient can open them, and shortens the message where possible.

Real-world examples

  • The padlock in your browser — TLS encrypts everything between you and the site
  • Emoji arriving intact — both ends agree on UTF-8 encoding
  • Streaming video — compressed with codecs (H.264, VP9) so it fits your bandwidth
  • A photo opening on any device — JPEG/PNG are agreed-upon presentation formats
  • An integration file that opens as garbage characters — classic encoding mismatch (UTF-8 vs ISO-8859-1)

Layer 5 · PDU: Data

Session

The conversation manager — opens a dialogue, keeps it alive, closes it cleanly.

In plain English: one connection is rarely one message. When you log into a site and browse ten pages, something has to remember "this is still the same conversation with the same person." The session layer establishes that dialogue, keeps it alive (with checkpoints and keep-alives), and tears it down when you're done.

Like Layer 6, it's mostly folded into applications today (think login sessions, auth tokens, RPC frameworks) — but the concept explains why you don't have to re-enter your password on every click.

Analogy

A phone call. You dial (establish), you talk with pauses and "are you still there?" checks (maintain), and you say goodbye and hang up (terminate). The call is the session; the sentences are the data.

Real-world examples

  • Staying logged into Workday while clicking through dozens of pages — one session, many requests
  • A video call — the call setup/teardown is session work; the video itself is data
  • Resuming a large file download after a drop, thanks to checkpointing
  • "Your session has expired, please log in again" — a session terminated by timeout
  • Database connections held open in a connection pool between an app and its DB

Layer 4 · PDU: Segment

Transport

The delivery service — breaks data into pieces and gets every piece there (or gets it there fast).

In plain English: big messages don't travel in one piece. The transport layer chops data into numbered segments, sends them, and — if you're using TCP — tracks every one: lost segments get re-sent, out-of-order segments get re-assembled, and a fast sender slows down for a slow receiver. UDP is the no-frills alternative: fire the pieces and don't look back. Slower but perfect? TCP. Fast but lossy is fine? UDP.

This layer also introduces ports — the apartment numbers of networking. An IP address gets you to the building (the machine); the port gets you to the right door (the program): 443 for HTTPS, 22 for SSH/SFTP, 53 for DNS.

Analogy

TCP is registered mail with tracking: every page numbered, signature on delivery, lost pages re-sent. UDP is confetti from a parade float: fast, cheap, and nobody re-throws the pieces that missed you.

Real-world examples

  • Downloading a file — TCP guarantees every byte arrives, in order, uncorrupted
  • A live game or video call — UDP, because a late packet is worse than a lost one
  • "Connection refused" on port 22 — the machine is up, but nothing is listening at that door
  • An SFTP transfer surviving flaky Wi-Fi — TCP quietly re-sending lost segments underneath
  • DNS lookups — mostly UDP: tiny question, tiny answer, no ceremony needed

Layer 3 · PDU: Packet

Network

The GPS — gives every machine an address and finds a route between any two of them.

In plain English: this is the layer that makes the Internet an inter-net — a network of networks. Every device gets an IP address (like 142.250.72.14), and routers pass packets from network to network, each one deciding only the next hop. No single router knows the whole path; each just moves the packet one step closer, like handing a letter between postal hubs.

Your data may cross 10–20 routers between your laptop and a server — you can watch this with traceroute. And ping, the most-used diagnostic on Earth, is a pure Layer 3 tool: "does this IP answer at all?"

Analogy

The international postal system. Your local post office doesn't know the street layout of Tokyo — it just knows to hand Japan-bound mail to the next hub. Each hub repeats that logic until the letter arrives.

Real-world examples

  • Your home router handing traffic between your Wi-Fi network and your ISP
  • ping 8.8.8.8 — the classic "is the network path alive?" test
  • A VPN — your packets get a new Layer 3 route through an encrypted tunnel
  • NAT — dozens of home devices sharing one public IP address
  • "No route to host" — a router genuinely doesn't know how to reach that address

Layer 2 · PDU: Frame

Data link

The local courier — moves data one hop, device to device, on the same network.

In plain English: Layer 3 plans the cross-country route; Layer 2 does each individual leg. On your local network, devices identify each other by MAC address — a hardware serial number burned into every network card (like a4:83:e7:2f:91:0c). Data is bundled into frames stamped with source and destination MAC, and a switch reads those stamps to deliver each frame to exactly the right port.

Key insight: MAC addresses never leave the local network. At every router hop, the frame is unwrapped and re-wrapped with fresh MAC addresses for the next leg — while the IP addresses inside stay the same end to end.

Analogy

The relay race. The baton (packet) travels the whole race, but each runner (frame) only covers their own leg, then hands off. New runner every leg — same baton the whole way.

Real-world examples

  • Plugging into an office switch — frames go only to your port, not everyone's
  • Wi-Fi — the whole 802.11 protocol (association, retries, collision avoidance) is Layer 2
  • MAC filtering on a home router — allowing only known hardware addresses
  • ARP — "who has IP 10.0.0.1? Tell me your MAC" — the glue between L3 and L2
  • VLANs — one physical switch split into isolated virtual networks

Layer 1 · PDU: Bits

Physical

The wire — where data stops being an idea and becomes electricity, light, or radio.

In plain English: everything above this layer is abstraction. Here, the 1s and 0s finally become something physical: voltage changes on copper, light pulses in fiber, radio waves in the air. This layer defines the boring-but-critical stuff — connector shapes, voltages, frequencies, cable lengths, how fast bits can be pushed.

It's also where a shocking number of real problems live. Seasoned network engineers check the cable first — because the fanciest configuration in the world can't fix a chewed wire or a loose plug.

Analogy

The roads and trucks of the postal system. Not the letters, not the addresses — the literal asphalt. If the road is washed out, no amount of clever addressing gets the mail through.

Real-world examples

  • The Ethernet cable behind your desk — Cat 5e/6 twisted-pair copper
  • Undersea fiber optic cables — ~99% of intercontinental internet traffic rides on light
  • Wi-Fi radio at 2.4 GHz / 5 GHz / 6 GHz — bits as electromagnetic waves
  • The blinking link light on a switch port — literal Layer 1 status
  • "Have you tried a different cable?" — the oldest and most effective fix in IT

Putting it together: one click, all seven layers

You type workday.com and hit Enter. In a few hundred milliseconds:

LayerWhat actually happens
7 · ApplicationBrowser resolves the name via DNS, then builds an HTTP GET request.
6 · PresentationTLS handshake completes; the request is encrypted. 🔒 appears.
5 · SessionA session is established — your login cookie ties this to you.
4 · TransportTCP splits the data into segments, addressed to port 443, tracking each one.
3 · NetworkEach segment becomes a packet with your IP and the server's IP; routers hop it across the internet.
2 · Data linkEach hop wraps the packet in a fresh frame with local MAC addresses.
1 · PhysicalFrames become radio waves to your router, then light in fiber under the ocean.

The server's stack runs the whole thing in reverse, bottom to top — and then sends the page back down its own stack. Every click, every API call, every file drop: the full round trip.

Reality check: OSI vs TCP/IP

Here's the honest truth: the internet doesn't run on OSI. It runs on the simpler TCP/IP model, which collapses layers 5–7 into one "Application" layer — because in practice, apps handle sessions and presentation themselves. OSI survives because it's a superb vocabulary for teaching and troubleshooting.

The troubleshooting ladder

The model's biggest practical payoff: debug bottom-up, ruling out one layer at a time. Each question isolates a layer — the first "no" tells you where the problem lives.

CheckQuestionTool / signal
L1Is there a physical connection at all?Link light, cable, Wi-Fi signal bars
L2Am I on the local network?ip addr — do I have a MAC and a link? Right VLAN/SSID?
L3Can I reach other machines?ping the gateway, then 8.8.8.8; traceroute to see where hops die
L4Is the specific service reachable?telnet host 443 / nc -zv host 22 — port open or refused?
L5–6Do sessions and TLS work?Cert errors, handshake failures, instant logouts

Integration-world translation: when a Studio integration fails — connection timeout is usually L3/L4 (routing, firewall, port). Certificate error is L6. 401/403 is L7 auth. Garbled file content is L6 encoding. Naming the layer tells you which team to call.
