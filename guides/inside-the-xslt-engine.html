SECTION 01

The Big Idea: Transformation, Not Editing

XSLT (eXtensible Stylesheet Language Transformations) never changes your original XML file. It reads it, and following the instructions in a second file — the stylesheet — it manufactures a brand-new document from scratch. The source is read-only raw material; the output is a completely separate product.

Kitchen analogy

Think of the XML file as a basket of ingredients, the XSLT stylesheet as a recipe card, and the XSLT engine as the chef. The chef never alters the ingredients in the basket — she picks what the recipe asks for, prepares it the way the recipe says, and plates an entirely new dish. Same basket + different recipe = different dish. Same recipe + different basket = the same style of dish made from new ingredients.

The second big idea is that XSLT is declarative and rule-based, not a step-by-step script. You don't tell the engine "loop over line 4, then print line 7." You hand it a set of rules of the form "whenever you encounter a thing that looks like X, produce Y." The engine decides when and in what order each rule fires as it walks through your data. This is the single biggest mental shift for people coming from procedural languages like Java or Python.

The third idea: the engine never works on raw text. Both files are first converted into trees — in-memory structures of connected nodes — and every operation (matching, selecting, copying) happens on trees. Text only reappears at the very last step.

SECTION 02 · ENGINE STAGE 1

Parsing: Text Becomes a Tree

Your XML file is, physically, just a long string of characters on disk. The first component of the engine — the XML parser — reads that string character by character and breaks it up in two passes:

Pass A — Tokenizing (the lexer)

The lexer slices the character stream into meaningful chunks called tokens: "here is an opening tag", "here is an attribute name", "here is a quoted value", "here is plain text", "here is a closing tag." It's like reading a sentence and identifying which words are nouns and which are verbs before worrying about meaning.

Pass B — Tree building (the parser)

The parser consumes those tokens and assembles the document tree. Every time it sees an opening tag it creates a node and steps down into it; every closing tag steps back up to the parent. While doing this it enforces well-formedness: every tag must close, tags must nest properly, attribute values must be quoted, there must be exactly one root element. If any rule is broken, the whole transformation stops with a fatal error — XML parsers are deliberately unforgiving.

The tree the engine builds follows a formal specification — in XSLT 1.0 it's called the XPath data model; in 2.0+ it's the XDM (XQuery and XPath Data Model). A few surprising things happen during this conversion:

  • Entities are resolved — &amp; in the file becomes a plain & character in the tree.
  • CDATA sections disappear — their contents become ordinary text nodes.
  • Adjacent text merges — you never get two text nodes side by side.
  • Attribute order is not preserved — attributes hang off their element as an unordered set.
  • Whitespace between tags becomes text nodes too — the indentation in a pretty-printed file is real data unless the engine is told to strip it (<xsl:strip-space>).
Why a tree and not a search through text? Because a tree gives every piece of data an address and a family: each node knows its parent, its children, and its siblings. That family structure is exactly what XPath expressions like order/item navigate. String-searching raw text could never answer a question like "give me the second child of this node's grandparent."
SECTION 03 · THE DATA MODEL

The Seven Node Types

When the document is broken up into a tree, every fragment of the file becomes one of exactly seven kinds of node. Everything XSLT ever touches is one of these:

SECTION 04 · ENGINE STAGE 2

Compiling the Stylesheet

Here's a fact many people miss: the XSLT stylesheet is itself an XML file, so it goes through the exact same parser and becomes a tree too. But the engine doesn't stop there — it compiles that tree into an efficient internal program:

  • Template rules are extracted. Every <xsl:template match="…"> becomes a rule: a compiled pattern (the condition) plus a body (what to produce).
  • Rules are indexed. Templates get sorted into fast lookup buckets — typically by the node name they match — so the engine doesn't have to test every rule against every node. Saxon, for instance, builds a hash table keyed on element names.
  • XPath expressions are pre-compiled. Every select="…" and match="…" string is parsed once, up front, into an expression tree — never re-parsed during the run.
  • Includes and imports are resolved. <xsl:include> pastes rules in as equals; <xsl:import> pulls rules in at a lower precedence, like a base class that can be overridden.
  • Global variables, parameters, keys and output settings (<xsl:output>, <xsl:key>) are registered.
Analogy

Compilation is the chef reading the whole recipe card before touching any ingredients — memorizing the steps, laying out the tools, and putting sticky-tabs on the pages so she can flip to "how to handle onions" instantly the moment an onion shows up.

Performance tip that falls out of this: because compilation is separate from execution, good processors let you compile once and run many times. In Workday Studio or Saxon, transforming 10,000 documents with one stylesheet costs one compilation, not 10,000.
SECTION 05 · ENGINE STAGE 3

The Transformation Loop: How the Engine Walks the Tree

Now the real work. The engine runs one beautifully simple loop, over and over, until there's nothing left to process. It works from a to-do list of nodes (formally the current node list):

In plain words:

  1. The engine puts a single node on its to-do list: the root node /.
  2. It asks, "which template rule matches this node best?" and runs that rule's body.
  3. Inside the body, the instruction <xsl:apply-templates/> means "now go do the same thing for my children" — those children get queued, and the loop continues.
  4. Anything a template body produces — literal tags, copied values, computed text — is stitched into the growing result tree.
Analogy

Imagine a mail-sorting office. Envelopes (nodes) arrive on a conveyor. Each envelope is held up against a wall of pigeonhole rules ("addressed to Finance → do this", "marked Urgent → do that"). Handling one envelope often shakes more envelopes out of it — the ones inside — and they go back on the conveyor. The office closes when the conveyor is empty.

Context: the engine's "you are here" marker

At every moment inside the loop, the engine maintains a context — three pieces of situational awareness that every XPath expression silently depends on:

Context partMeaningHow you see it
Context nodeThe node being processed right nowRelative paths like item or . start from it
Context positionWhere this node sits in the current batch (1-based)position()
Context sizeHow many nodes are in the batchlast()

Every <xsl:apply-templates> and <xsl:for-each> swaps in a fresh context, which is why the same expression can mean different things in different templates — it's always answered relative to where the engine is standing.

SECTION 06 · THE PATTERN MATCHER

Template Matching & Conflict Resolution

Step 2 of the loop — "find the best template" — deserves its own section, because several templates can legitimately match the same node. The engine breaks ties with a strict, deterministic ladder:

The clever part is default priority: if you don't write a priority attribute, the engine assigns one from how specific the pattern looks. The rule of thumb — the more you had to type, the more you meant it:

PatternDefault priorityReads as
node() / *−0.5 / −0.25"anything at all" — weakest claim
order0"any element named order"
order[@status='open']0.5"an order with a condition" — strongest claim

So if a node is an open order, all three templates above match it — but the engine picks the conditional one, because it's the most specific promise the stylesheet author made.

Modes: parallel sets of rules

A template can carry a mode (e.g. mode="summary"). Think of modes as separate rule books for the same data: the engine only consults rules from the book named in <xsl:apply-templates mode="summary">. This is how one stylesheet can render the same nodes twice — once as a table of contents, once as full detail.

SECTION 07 · THE SAFETY NET

Built-in Rules: Why Text "Leaks" Through

What if a node reaches step 2 and no template in your stylesheet matches it? The engine never shrugs — it falls back on invisible built-in template rules baked into every processor:

Node with no matchBuilt-in behaviour
Root, elementsKeep walking — silently apply templates to the children. Produces no output itself.
Text, attributesCopy the value into the output.
Comments, processing instructionsDo nothing — dropped.

Combined, these two behaviours explain the classic beginner mystery: run an empty stylesheet against any XML file and you get all the text content, concatenated, with every tag stripped. The built-ins tunneled down through every element (rule 1) and copied out every text node (rule 2). That "leaking text" isn't a bug — it's the safety net firing.

Debugging heuristic: unexpected stray text in your output almost always means a node you forgot to write a template for, and the built-in rules carried its text through. Adding <xsl:template match="text()"/> (an empty rule) silences the net.
SECTION 08 · THE NAVIGATOR

The XPath Evaluator: How the Engine Finds Things

Every match and select attribute contains an XPath expression — a little address written in its own mini-language. Inside the engine, a dedicated component (the XPath evaluator) executes these addresses against the tree. An expression is built from steps, each with three parts:

axis :: node-test [ predicate ]

e.g.   child::order[@status='open']
       "from where I stand, look at my CHILDREN,
        keep only ones named ORDER,
        keep only those whose status attribute says open"

The axis is the direction of travel from the context node. Thirteen exist; these cover 95% of real work:

How the evaluator executes a path

A path like /orders/order[qty > 1]/item runs left to right, and each step filters and re-feeds the next:

  1. / — start at the root node. Working set: {root}.
  2. orders — from each node in the set, collect children named orders. Set: {<orders>}.
  3. order[qty > 1] — collect order children, then run the predicate on each one: momentarily make it the context node, evaluate qty > 1, keep it only if the test is true.
  4. item — from the survivors, collect item children. That final set is the answer.

The result of an XPath expression is always one of four value types (1.0 model): a node-set, a string, a number, or a boolean — and the evaluator freely converts between them (a node-set used where a boolean is needed becomes "true if non-empty," which is exactly how predicates like order[note] work).

SECTION 09 · THE TOOLBOX

The Function Library

Bolted onto the XPath evaluator is a function library — the built-in tools an expression can call. These are the ones an engine reaches for constantly:

Asking "where am I?"

position()My number in the current batch (great for striping table rows, or "add a comma unless last").
last()The batch size.
current()The node the template is processing — useful inside predicates where . has temporarily moved.
name() / local-name()The node's tag name, with / without its namespace prefix.

Working with text

string(x)Convert anything to text. For an element: all its descendant text glued together.
concat(a,b,…)Glue strings together.
substring(s,start,len)Slice a string (1-based, not 0-based!).
substring-before / -afterSplit around a separator — the classic way to peel apart "2026-07-05".
contains(s, t)Is t anywhere inside s?
normalize-space(s)Trim ends and collapse inner runs of whitespace to single spaces — the #1 data-cleaning tool.
translate(s, from, to)Character-by-character swap; the 1.0 trick for case conversion and stripping characters.
string-length(s)Count characters.

Numbers and node-sets

number(x), sum(set)Convert to a number; total a node-set (e.g. sum(order/qty)).
count(set)How many nodes matched.
round / floor / ceilingThe usual rounding family.
format-number(n, '#,##0.00')XSLT's number formatter for money and reports.
id(x) / key(name, val)Fast lookups. key() reads a pre-built index declared with <xsl:key> — the engine builds a hash table on first use, turning slow cross-file searches into instant lookups.
boolean / not / true / falseLogic helpers, mostly inside predicates and <xsl:if test="…">.
generate-id(node)A unique, stable ID the engine invents for any node — handy for building anchors and links.
document(uri)Pull in a second XML file mid-transform; it gets parsed into its own tree.
XSLT 2.0/3.0 grew this toolbox enormously — regular expressions (matches(), replace(), tokenize()), real date/time arithmetic (format-date(), current-dateTime()), proper case functions (upper-case(), lower-case()), sequences, and user-defined <xsl:function>s callable from any XPath expression.
SECTION 10 · ENGINE STAGES 4–5

The Result Tree & Serialization

Notice what templates have been doing all along: they don't print text — they emit nodes. Literal tags in a template body, <xsl:element>, <xsl:attribute>, <xsl:value-of>, <xsl:copy-of>… all of them add branches to a third tree growing in memory: the result tree.

Only when the last template finishes does the final component — the serializer — walk that result tree top to bottom and write it out as actual characters. The <xsl:output> declaration is its instruction sheet:

SettingWhat the serializer does
method="xml"Writes strict XML: every tag closed, special characters escaped (& → &amp;), optional XML declaration.
method="html"Writes browser-friendly HTML: knows <br> has no closing tag, doesn't escape inside <script>.
method="text"Writes only text node values — no tags, no escaping. This is how XSLT produces CSVs, fixed-width payroll files, and EDI documents.
indent="yes"Pretty-prints with line breaks and indentation.
encoding="UTF-8"Chooses the byte encoding of the file.
omit-xml-declarationSuppresses the <?xml …?> first line.
Analogy

The result tree is the finished dish being assembled on the plate; serialization is the waiter carrying it out and describing it in the language the diner speaks — formal French (XML), casual English (HTML), or just the bare list of ingredients (text).

Why the escaping "just works": because output goes through a tree, you physically cannot produce malformed XML by accident — if your data contains <, the serializer escapes it, since in the tree it was only ever a character inside a text node, never a tag. The tree model is the safety mechanism.
SECTION 11 · END TO END

A Full Worked Example, Traced Step by Step

Let's watch the engine run a real transformation from first byte to last, using the loop from Section 05. Here are the two inputs:

Input · orders.xml 
<orders>
  <order id="7"><item>Tea</item><qty>2</qty></order>
  <order id="8"><item>Coffee</item><qty>1</qty></order>
</orders>
Input · report.xsl 
<xsl:stylesheet version="1.0"
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform">
  <xsl:output method="html" indent="yes"/>

  <!-- Rule A : the whole document -->
  <xsl:template match="/">
    <html><body><h1>Order Report</h1>
      <xsl:apply-templates select="orders/order"/>
    </body></html>
  </xsl:template>

  <!-- Rule B : each order -->
  <xsl:template match="order">
    <p>
      <xsl:value-of select="position()"/>. 
      <xsl:value-of select="item"/> × 
      <xsl:value-of select="qty"/>
    </p>
  </xsl:template>
</xsl:stylesheet>

The engine's diary

TickTo-do listWhat the engine does
0—Parses both files into trees. Compiles Rule A and Rule B; indexes B under the name "order". Reads <xsl:output>: serializer will speak HTML.
1{ / }Takes the root node. Pattern matcher: Rule A (match="/") fits. Runs its body: writes <html><body><h1>Order Report</h1> into the result tree, then hits apply-templates select="orders/order". XPath evaluator walks the tree and returns both <order> nodes → they join the to-do list as one batch of 2.
2{ order#7, order#8 }Takes order id=7. Context: node = order#7, position = 1, size = 2. Matcher: Rule B fits (name index makes this instant). Body writes <p>1. Tea × 2</p> — position() answered 1, item and qty selected the children and value-of took their text.
3{ order#8 }Takes order id=8. Same rule, new context (position = 2). Writes <p>2. Coffee × 1</p>. Rule B contains no apply-templates, so nothing new is queued.
4{ }List empty → transformation over. Serializer walks the result tree and prints the HTML below.
Output · report.html 
<html>
  <body>
    <h1>Order Report</h1>
    <p>1. Tea × 2</p>
    <p>2. Coffee × 1</p>
  </body>
</html>

Notice what didn't get any special code: the id attributes and the fact that there were exactly two orders. The stylesheet never says "loop twice" — it says "here is what an order looks like when plated," and the engine's loop applied it as many times as the data demanded. Ten thousand orders would need zero changes.

Push vs pull: two ways to drive the same engine

The example above is push style — small templates, and apply-templates pushes nodes at them; the data's shape drives the output. The alternative is pull style: one big template that uses <xsl:for-each> and <xsl:value-of> to reach in and pull exactly the values it wants; the output's shape drives the walk. Pull suits rigid, predictable documents (an integration file with a fixed layout); push shines when data is variable, deeply nested, or document-like. Under the hood both use the same loop, matcher, and evaluator.

SECTION 12 · EVOLUTION

XSLT 1.0 vs 2.0 vs 3.0 — What Changed in the Engine

VersionEngine-level changes, in plain terms
1.0 (1999)The model described on this page. Four value types, one output file per run, no regex, no real dates. Ubiquitous — it's what browsers and many embedded processors (including Workday Studio's XSLT steps at 1.0 level via Xalan-type engines) support.
2.0 (2007)The data model is rebuilt on sequences (ordered lists of nodes and plain values) with optional schema-aware typing. Adds regex, date/time math, grouping (xsl:for-each-group), multiple output files (xsl:result-document), and user-defined functions. Saxon is the reference engine.
3.0 (2017)The headline is streaming: with <xsl:mode streamable="yes"> the engine can transform a file without building the full source tree — it processes nodes as they fly past the parser, in one forward pass, using constant memory. Gigabyte files become feasible. Also adds xsl:try/catch, maps and arrays, JSON support, and packages.
Streaming is the one change that breaks the mental model on this page: a streaming transform gives up the freedom to look backwards or sideways (no preceding-sibling::, no revisiting), because the tree behind the read head no longer exists. It's the difference between studying a printed map and navigating from a moving train window.
SECTION 13 · REFERENCE

Glossary

Parser / lexerThe component that turns raw XML text into tokens, then into a node tree, while checking well-formedness.
Well-formedObeys XML's grammar rules (matching tags, one root, quoted attributes). Distinct from valid, which means "also matches a schema/DTD."
NodeOne unit of the tree — root, element, attribute, text, comment, processing instruction, or namespace.
Template ruleA pattern ("when you see this…") plus a body ("…produce this").
Pattern matcherThe component that picks the single best template for a node, using import precedence → priority → document order.
Context (node / position / size)The engine's "you are here" marker; the silent starting point of every relative XPath expression.
XPath evaluatorThe component that executes address expressions (axes, node-tests, predicates) against a tree.
PredicateThe filter in square brackets: order[qty > 1].
Built-in template rulesInvisible fallback rules that walk through unmatched elements and copy out unmatched text.
Result treeThe output document under construction, in memory, as nodes.
SerializerThe component that converts the result tree into characters, per <xsl:output>.
Push / pullTwo authoring styles: data drives templates via apply-templates (push) vs one template pulls values with for-each/value-of (pull).
Streaming (3.0)Transforming during a single forward pass of the parser, without materializing the whole source tree.
